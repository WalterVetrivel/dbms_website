5.1 Distributed Databases: Architecture

Centralized and distributed databases

In one line: A centralized database keeps all data at one site. A distributed database spreads it over several sites linked by a network, so it keeps working when one site fails.

Centralized database compared with distributed database
PointCentralized databaseDistributed database
Where data is storedAt one siteAt many sites
If the site failsThe whole system stopsOther sites keep working
Speed for local usersRemote users must use the networkData can be kept near its users
GrowthBuy a bigger computerAdd more sites
Control and designSimpleComplex
SecurityOne place to protectMany sites and a network to protect
Exam tip

Draw both: one database with many users around it, and three sites joined by a network, each with its own database.

Replication and fragmentation

In one line: Replication stores copies of the same data at several sites. Fragmentation splits the data into parts and stores each part at a different site.

Replication and fragmentation
BasisReplicationFragmentation
MeaningA copy (replica) of a relation or fragment is kept at two or more sitesA relation is split into fragments, and each fragment is kept at one site
KindsFull, partial or no replicationHorizontal, vertical or mixed
Same data at many sites?YesNo (only the key repeats in vertical fragments)
ReadsFast: a copy is often local; sites can answer in parallelFast when a site needs only its own fragment
UpdatesCostly: every copy must changeCheap: one site holds each row
If a site failsAnother copy is usedThat fragment cannot be reached
Disk spaceMoreNo extra
Rebuilding the relationNot needed: each copy is wholeUnion (horizontal) or natural join (vertical)
Used together?Yes: fragments can also be replicatedYes
Exam tip

Replication answers “how many copies?”, fragmentation answers “which part goes where?”, and allocation is the choice of sites.

Horizontal, vertical and mixed fragmentation

In one line: Horizontal fragmentation splits a relation by rows with a selection (σ). Vertical fragmentation splits it by columns with a projection (π), and mixed fragmentation does both.

Fragmenting Student(RollNo, Name, Dept, City, Marks)
BasisHorizontalVerticalMixed (hybrid)
Splits byRows (tuples)Columns (attributes)Columns, then rows (or rows, then columns)
Defined withSelection σProjection πσ and π together
Rebuilt withUnion ∪Natural join ⋈ on the keyJoin and union, in reverse order
Must keepEvery row in exactly one fragmentThe primary key in every fragmentBoth rules
Each fragment hasAll the columns, some rowsAll the rows, some columnsSome rows and some columns
SuitsEach site uses its own rows (for example, its own city)Each site uses different columns (office, exam cell)Both needs at once
ExampleF1 = σCity = 'Salem'(Student)F1 = πRollNo, Name, Dept(Student)F2 = σCity = 'Chennai'(πRollNo, City, Marks(Student))

Syntax side by side

Horizontal fragment 
-- F1 at the Salem site
SELECT *
FROM Student
WHERE City = 'Salem';

-- rebuild:
-- F1 UNION F2 UNION F3
Vertical fragment 
-- F1 at the college office
SELECT RollNo, Name, Dept
FROM Student;

-- rebuild:
-- F1 JOIN F2 USING (RollNo)
Mixed fragment 
-- F2 at the Chennai site
SELECT RollNo, City, Marks
FROM Student
WHERE City = 'Chennai';

-- rebuild:
-- F1 JOIN (F2 UNION F3)
--   USING (RollNo)
Exam tip

Draw one small table, then each fragment with its σ or π expression, then the rebuild formula: ∪ for horizontal and ⋈ for vertical.

Homogeneous, heterogeneous and federated distributed databases

In one line: In a homogeneous system every site runs the same DBMS and schema. In a heterogeneous system the sites may differ, and a federated system joins independent databases that share only some data.

PointHomogeneousHeterogeneousFederated
DBMS at each siteSameMay differMay differ
SchemaSame global schemaMay differEach site has its own; only shared parts form the global view
Do sites know each other?YesNot alwaysOnly through the federation layer
CooperationFullLimitedVoluntary
Local autonomyLowMedium to highHigh
Translation neededNoYes (middleware)Yes (federation layer)
How it is builtDesigned as one system (top-down)Joined from existing systems (bottom-up)Joined from existing systems (bottom-up)
ExampleOne bank on MySQL at all branchesMerged banks on Oracle and MySQLHospitals sharing data with a health department

5.3 Transaction Processing

Single-phase, two-phase and three-phase commit

In one line: Single-phase commit just tells sites to commit. 2PC first asks every site to vote, and 3PC adds a pre-commit phase so that sites need not block when the coordinator fails.

Single-phase, two-phase and three-phase commit
PointSingle-phaseTwo-phase (2PC)Three-phase (3PC)
Rounds of messagesOneTwoThree
PhasesCommitPrepare (voting), then commit or abort (decision)Prepare (voting), pre-commit, then commit
Extra log recordNone<ready T> at each site; <commit T> or <abort T> at the coordinatorAlso <precommit T>
Can a site vote no?NoYesYes
AtomicityNot guaranteedGuaranteedGuaranteed
Blocking when the coordinator failsNot applicablePossibleAvoided (if no partition)
Network partitionNot handledSafe, but sites may blockNot handled: assumes no partition
CostLowestMediumHighest
Used in practiceRarelyWidelyRarely

The messages side by side

2PC messages 
Coordinator         Site
  <prepare T>  --->
               <---  <ready T>
  <commit T>   --->
               <---  ack
3PC messages 
Coordinator         Site
  <prepare T>  --->
               <---  <ready T>
  <precommit T> -->
               <---  ack
  <commit T>   --->
               <---  ack
Exam tip

Draw the message diagram for each protocol. Then explain what happens when the coordinator fails after sending <prepare T>.

5.4 NoSQL Databases: Introduction

Relational (SQL) and NoSQL databases

In one line: A relational database stores tables with a fixed schema and uses SQL and ACID transactions. A NoSQL database uses flexible models and scales out over many servers.

Relational databases and NoSQL databases
PointRDBMSNoSQL
Data modelTables of rows and columnsDocuments, key-value pairs, wide columns or graphs
SchemaFixed; defined before inserting dataFlexible or schema-free
Query languageSQL, a standard languageDifferent for each product (APIs or SQL-like languages)
RelationshipsForeign keys and joinsData kept together (embedded) or linked in the app; graph databases use edges
ScalingMostly vertical (bigger server)Horizontal (more servers)
TransactionsACIDMostly BASE; some offer ACID for one item or more
Kind of dataStructuredStructured, semi-structured and unstructured
NormalizationNormalized to remove redundancyOften denormalized for fast reads
Best forComplex queries and strict correctnessVery large data, high traffic and fast-changing data
ExamplesMySQL, Oracle, PostgreSQL, SQL ServerMongoDB, Redis, Cassandra, Neo4j

ACID and BASE

In one line: ACID puts correct data first; BASE (basically available, soft state, eventually consistent) puts availability and speed first.

ACID and BASE
PointACIDBASE
Main goalCorrect data at all timesAlways available and fast
ConsistencyStrong: every read sees the latest writeEventual: copies agree after some time
AvailabilityMay refuse requests during a failureKeeps answering during a failure
ScalingHarder across many serversEasy across many servers
Used byRelational databases (MySQL, Oracle)Many NoSQL databases (Cassandra, DynamoDB)
Good forBanking, exam results, bookingsLikes, comments, product views, logs
Exam tip

Expand BASE in full: Basically Available, Soft state, Eventually consistent. Then link it to AP systems in the CAP theorem.

5.5 CAP Theorem

CP and AP systems

In one line: During a network partition, a CP system refuses some requests to keep data consistent. An AP system keeps answering, even if some answers are old.

CP and AP systems
BasisCP systemAP system
Keeps during a partitionConsistency and partition toleranceAvailability and partition tolerance
Gives up during a partitionAvailability: some requests wait or failConsistency: some reads return old data
ConsistencyStrongEventual
Transaction styleCloser to ACIDBASE
After the partition healsNormal service resumesCopies are brought into agreement
ExamplesHBase, MongoDB (default settings), Redis ClusterCassandra, CouchDB, DynamoDB
Good forBank balances, ticket booking, stock levelsLikes, feeds, shopping carts
The three pairs of the CAP theorem
TypeDuring a partitionExamplesGood for
CP (consistency + partition tolerance)Some servers refuse or wait, so no one sees old dataHBase, MongoDB (default settings), Redis ClusterBanking, ticket booking, stock levels
AP (availability + partition tolerance)All servers keep answering; some answers may be old; copies sync laterApache Cassandra, CouchDB, Amazon DynamoDBSocial media feeds, likes, shopping carts
CA (consistency + availability)Cannot handle a partition; works only on one siteMySQL or PostgreSQL on a single serverSmall systems on one server
Exam tip

Partitions cannot be avoided in a distributed system, so the real choice is between C and A while a partition lasts.

5.13 SQL Injection

Dynamic SQL and prepared statements

In one line: Dynamic SQL joins user input into the query text, so input can change the query. A prepared statement fixes the query first and sends input only as values.

Dynamic SQL and prepared statements
BasisDynamic SQL (string concatenation)Prepared statement (parameterized query)
How the query is builtUser input is joined into the SQL textThe SQL has ? placeholders; input is bound to them later
When the query is parsedAfter the input is addedBefore the input arrives
Can input change the query?Yes: quotes and keywords in the input become SQLNo: input is always treated as a value
SQL injectionPossiblePrevented
Repeated runsParsed again each timeParsed once, run many times
Input ' OR '1'='1 as the passwordLogs in without the passwordNo row matches; the login fails
In code"... WHERE username = '" + user + "'""... WHERE username = ?" and setString(1, user)

Syntax side by side

Unsafe: dynamic SQL (Java) 
String sql =
  "SELECT * FROM users" +
  " WHERE username = '" + user +
  "' AND password = '" + pass +
  "'";
ResultSet rs =
  stmt.executeQuery(sql);
Safe: prepared (Java) 
String sql =
  "SELECT * FROM users" +
  " WHERE username = ?" +
  " AND password = ?";
PreparedStatement ps =
  conn.prepareStatement(sql);
ps.setString(1, user);
ps.setString(2, pass);
ResultSet rs = ps.executeQuery();
Safe: prepared (MySQL) 
PREPARE login FROM
  'SELECT * FROM users
   WHERE username = ?
   AND password = ?';
SET @u = 'anitha',
    @p = ''' OR ''1''=''1';
EXECUTE login USING @u, @p;
-- no rows: the attack fails
DEALLOCATE PREPARE login;
Exam tip

A prepared statement is safe only if every input goes into a ?. Joining input into the text before calling prepareStatement is still unsafe.

5.14 Encryption and Public Key Infrastructures

Symmetric and asymmetric encryption

In one line: Symmetric encryption uses one shared secret key and is fast. Asymmetric encryption uses a public and a private key, which makes key sharing and signatures easy but is slow.

Symmetric and asymmetric encryption
PointSymmetricAsymmetric
KeysOne shared secret keyA public key and a private key
SpeedFastSlow (hundreds of times slower)
Key sharingHard: the key must reach the other side secretlyEasy: the public key can be shared openly
Keys for n users to talk in pairsn(n − 1)/22n (one pair each)
Used forBulk data: disks, tables, backupsSharing keys, digital signatures, certificates
ExamplesAES, DES (old)RSA, elliptic curve (ECC)

Syntax side by side

Symmetric (AES in MySQL) 
SET @key = 'k3y-0f-16-bytes!';
SELECT AES_ENCRYPT('Anitha', @key)
  INTO @c;
SELECT CAST(
  AES_DECRYPT(@c, @key)
  AS CHAR);
-- Anitha (same key both ways)
Asymmetric (idea) 
Sender:   C = encrypt(M,
            receiver's PUBLIC key)
Receiver: M = decrypt(C,
            receiver's PRIVATE key)

Signature: sign with the sender's
  PRIVATE key; anyone checks it
  with the sender's PUBLIC key
Exam tip

In practice both are used together: asymmetric encryption shares a symmetric key safely, then the symmetric key encrypts the data.
