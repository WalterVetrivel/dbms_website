3.3 Schedules

Serial and concurrent schedules

In one line: A serial schedule runs transactions one after another. A concurrent schedule interleaves them. It is faster, but correct only if it is serializable.

Serial and concurrent schedules
BasisSerial scheduleConcurrent (non-serial) schedule
MeaningAll instructions of one transaction run before the next transaction startsInstructions of several transactions are interleaved
Number possible for n transactionsn! (each order is one schedule)Many more than n!
ConsistencyAlways keeps the database consistentConsistent only if it is serializable
ThroughputLow; the CPU waits during each disk readHigh; one transaction uses the CPU while another waits for the disk
Waiting timeShort transactions wait behind long onesShort transactions can finish early
Needs concurrency controlNoYes
Example (funds transfer)T1 then T2: A + B stays 3000Schedule 3 keeps A + B = 3000; Schedule 4 does not

Overwriting uncommitted dataAllowedAllowedNot allowed
RecoveryPossible, but may need many rollbacksRoll back only the failed transactionSimplest: restore the before-image of each item
Produced byAny correct protocolStrict 2PLStrict 2PL
Types of schedules and their role in transaction processing
TypeRuleRole

3.4 Serializability

Conflict and view serializability

In one line: Conflict serializability looks at the order of conflicting instructions and is easy to test. View serializability looks at reads and final writes. It is wider but hard to test.

Conflict serializability and view serializability
PointConflict serializabilityView serializability
Based onOrder of conflicting instructionsInitial reads, reads-from and final writes
TestPrecedence graph has no cycle (easy)Compare with every serial schedule (hard, NP-complete)
Which is wider?Smaller set of schedulesLarger set: includes every conflict serializable schedule
Blind writesNot neededThe extra schedules it accepts always have blind writes
Used in practiceYes, through locking protocolsRarely
Exam tip

Every conflict serializable schedule is view serializable, but not the other way round. The extra view serializable schedules always contain blind writes.

3.5 Concurrency Control and Need for Concurrency

Lost update, dirty read, unrepeatable read and phantom

In one line: Each problem comes from a different conflict. Write-write gives a lost update, write-read a dirty read and read-write an unrepeatable read. Inserts give phantoms.

Problems and how they are prevented
ProblemConflictPrevented by
Lost updateWrite-writeExclusive locks held until commit
Dirty readWrite-readReading only committed data (strict 2PL)
Unrepeatable readRead-writeShared locks held until commit
Incorrect summaryRead-writeShared locks on every item summed
PhantomInsert or delete in a rangeIndex (range) locks, or the SERIALIZABLE isolation level

3.7 Two Phase Locking

Basic, strict, rigorous and conservative two phase locking

In one line: All four keep a growing and a shrinking phase, so all are serializable. They differ in when locks are taken and released, which decides cascading rollbacks and deadlocks.

Basic, strict, rigorous and conservative two phase locking
TypeWhen locks are releasedSerializableCascadelessDeadlock-free
Basic 2PLAny time after the lock pointYesNoNo
Strict 2PLX locks at commit or abort; S locks after the lock pointYesYesNo
Rigorous 2PLAll locks at commit or abortYes (in commit order)YesNo
Conservative 2PLAll locks taken before it startsYesOnly if also strictYes

3.8 Deadlock

Deadlock, livelock and starvation

In one line: In a deadlock, transactions are blocked waiting for each other. In a livelock, they keep running and restarting but never finish. In starvation, one transaction is passed over again and again.

Deadlock, livelock and starvation
DeadlockLivelockStarvation
MeaningEach transaction in a cycle waits for a lock held by the next, so none can go onTransactions keep changing state (rolling back and restarting) in response to each other, but none finishesA transaction waits a very long time, or forever, while others are served
State of the transactionsBlocked, waitingRunning, but no progressOne waits or restarts while others progress
Who is affectedAll transactions in the cycleThe transactions that keep collidingUsually one transaction
Uses the CPUNo; the transactions are idleYes; work is done and thrown away again and againOthers use it; the starved one gets little or none
Detected byA cycle in the wait-for graph, or a timeoutHard to detect; no cycle in the wait-for graphCounting how often or how long a transaction has waited
Ends on its own?No; the DBMS must roll back a victimPossibly, by chancePossibly, once the others finish
ExampleT3 holds B and waits for A; T4 holds A and waits for BT1 and T2 both restart after a clash, then clash again at the same point each timeThe same young transaction is chosen as the victim every time
CurePrevention, or detection and rollbackRandom delay before restart; fair victim choiceFair lock queue; count rollbacks in victim cost; keep old timestamps
Exam tip

Livelock is a special case of starvation. Say this, then give one example of each.

Wait-die and wound-wait

In one line: In both schemes the younger transaction is rolled back. In wait-die an older requester waits; in wound-wait an older requester rolls back the younger holder.

Younger Ti asksTi dies: Ti is rolled backTi waits
Who may wait for whomOlder waits for youngerYounger waits for older
Who is rolled backAlways the younger one (the requester)Always the younger one (the holder)
RollbacksMore; a young transaction may die many timesFewer
After restartKeeps its old timestamp, so it cannot starveKeeps its old timestamp, so it cannot starve
Memory aidThe old one waits, the young one diesThe old one wounds, the young one waits
What happens when Ti asks for a lock held by Tj
Requester Ti isWait-dieWound-wait
Older than TjTi waitsTj is rolled back (wounded)
Younger than TjTi is rolled back (dies)Ti waits

The rules side by side

Wait-die rule

    Ti waits
else                 -- Ti younger
    roll back Ti (dies)
Wound-wait rule 
if TS(Ti) < TS(Tj)   -- Ti older
    roll back Tj (wounded)
else                 -- Ti younger
    Ti waits

3.9 Transaction Recovery

Volatile, non-volatile and stable storage

In one line: Volatile storage loses its data in a crash, non-volatile storage survives a crash but not every disk failure and stable storage is built to lose nothing.

Storage types and what survives
TypeExamplesSurvives a crash?
Volatile storageMain memory, cacheNo. Contents are lost when power goes off.
Non-volatile storageHard disk, SSD, magnetic tapeSurvives a system crash, but can still be lost in a disk failure.
Stable storageCopies on several disks, often at different sitesIn theory, never lost. Built by keeping several copies of each block on independent non-volatile media.
Exam tip

The log must be written to stable storage. Say why: recovery depends on it surviving every failure.

In one line: Deferred update writes to the database only after commit. Immediate update writes at any time. Shadow paging keeps an old copy of the page table and needs no log.

3.10 Save Points

COMMIT, ROLLBACK and ROLLBACK TO SAVEPOINT

In one line: COMMIT makes all changes of a transaction permanent; ROLLBACK undoes all of them; ROLLBACK TO SAVEPOINT undoes only the changes made after that savepoint.

COMMIT, ROLLBACK and ROLLBACK TO SAVEPOINT
BasisCOMMITROLLBACKROLLBACK TO SAVEPOINT
EffectMakes all changes permanentUndoes all changesUndoes only the changes after the savepoint
Transaction afterwardsEndsEndsStays open
LocksAll releasedAll releasedLocks taken after the savepoint may be released (InnoDB keeps them)
Savepoints afterwardsAll removedAll removedThat savepoint is kept; later ones are removed
ACID propertyDurabilityAtomicityAtomicity, for part of a transaction
Can be undone?NoNoYes, by a later ROLLBACK of the whole transaction

Syntax side by side

SQL 
START TRANSACTION;
SAVEPOINT SP1;
DELETE FROM CUSTOMERS WHERE ID = 1;
SAVEPOINT SP2;
DELETE FROM CUSTOMERS WHERE ID = 2;
DELETE FROM CUSTOMERS WHERE ID = 3;

ROLLBACK TO SP2;
-- IDs 2 and 3 are back; ID 1 is
-- still deleted
COMMIT;
-- now ID 1 is gone for good
Other forms 
ROLLBACK;
-- undo everything since
-- START TRANSACTION

RELEASE SAVEPOINT SP1;
-- forget the savepoint;
-- no change is undone

3.11 Isolation Levels

READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ and SERIALIZABLE

In one line: Each higher isolation level blocks one more problem: dirty reads, then non-repeatable reads, then phantoms. More isolation means less concurrency.

Phenomena each SQL isolation level allows
Isolation levelDirty readNon-repeatable readPhantom
READ UNCOMMITTEDPossiblePossiblePossible
READ COMMITTEDNot possiblePossiblePossible
REPEATABLE READNot possibleNot possiblePossible
SERIALIZABLENot possibleNot possibleNot possible
Isolation levels compared
LevelConsistencyConcurrencySuits
READ UNCOMMITTEDLowestHighestApproximate counts and reports where small errors do not matter
READ COMMITTEDLowHighMost web pages and short updates; the default in many systems
REPEATABLE READHighMediumReports that read the same rows more than once
SERIALIZABLEHighestLowestMoney transfers, seat booking, anything that must never be wrong

Syntax side by side

Set the level 
SET TRANSACTION ISOLATION LEVEL
  READ COMMITTED;
START TRANSACTION;
-- ...
COMMIT;
For the whole session 
SET SESSION TRANSACTION
  ISOLATION LEVEL SERIALIZABLE;

SELECT @@transaction_isolation;
-- MySQL's default is
-- REPEATABLE-READ
Exam tip

MySQL's default level is REPEATABLE READ, while Oracle and SQL Server use READ COMMITTED. Name both if the question asks for examples.

3.13 Backup and Recovery System

Full, incremental and differential backups

In one line: A full backup copies everything; an incremental backup copies changes since the last backup of any kind; a differential backup copies changes since the last full backup.

Backup types compared
FullIncrementalDifferential
CopiesAll dataChanges since the last backupChanges since the last full backup
Backup time and spaceMostLeastGrows each day until the next full backup
To restore, you needThat one backupThe last full backup and every incremental after it, in orderThe last full backup and the latest differential
Restore speedFastestSlowestMedium
RiskLowIf one incremental is lost, later ones are uselessLow
Exam tip

Use a weekly example: full on Sunday, then incremental or differential each day. Ask which backups are needed to restore on Thursday.
