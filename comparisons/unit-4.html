4.1 RAID

RAID levels 0 to 6

In one line: The RAID levels differ in how they use striping, mirroring and parity, which decides their speed, cost and how many disk failures they survive.

RAID levels compared (n is the number of disks)
LevelHow data is storedDisk failures it survivesSpace for dataUsed today?
RAID 0Block stripingNoneAll n disksYes, for data that can be lost
RAID 1Mirroring1 in each pairn / 2 disksYes
RAID 2Bit striping with ECC disks1Fewer than n − 1No
RAID 3Bit striping, one parity disk1n − 1 disksRarely
RAID 4Block striping, one parity disk1n − 1 disksRarely
RAID 5Block striping, parity spread over all disks1n − 1 disksYes, very common
RAID 6Block striping, P and Q spread over all disks2n − 2 disksYes, for large arrays
Common choices
NeedGood choiceWhy
Speed only; the data can be created againRAID 0Fastest, no extra disks
Many small writes, such as a transaction logRAID 1 (or 1 + 0)A write needs no parity update
Mostly reads, large amounts of dataRAID 5Low cost, good read speed
Very large disks or very important dataRAID 6Survives a second failure during a long rebuild

Striping, mirroring and parity

In one line: Striping spreads data over disks for speed. Mirroring copies it for safety. Parity stores an XOR of the data, so a lost block can be rebuilt at a lower cost.

The three ideas behind RAID
BasisStripingMirroringParity
GoalSpeedSafetySafety at a lower cost
How it worksBlock i goes to disk i mod n, so one file is spread over all disksEvery block is written to two disksA parity block P = A1 ⊕ A2 ⊕ ... is stored for each stripe
Extra disksNoneOne for each data disk (double)One (or two for RAID 6) for the whole array
Survives a disk failureNo; losing one disk loses the dataYes; the copy is usedYes; XOR of the other blocks rebuilds the lost one
Read speedHigh (all disks at once)High (either copy can be read)High
Write speedHighGood (two writes at once)Lower: each write also updates the parity
RAID levels0, and part of 2 to 61 (and 1 + 0)3, 4, 5 and 6

4.3 Organization of Records in Files

Fixed-length and variable-length records

In one line: Fixed-length records all have one size, so they are easy to find but waste space; variable-length records save space but need a slotted page to be found.

Fixed-length compared with variable-length records
PointFixed-length recordsVariable-length records
SizeEvery record has the same size.Records can have different sizes.
Finding a recordRecord i starts at byte n × (i − 1), so it is easy to find.Needs (offset, length) pairs and a slotted page to find each record.
SpaceShort values are padded, so space is wasted.Uses only the space it needs.
ExampleExample: CHAR(10) fields.Example: VARCHAR(50) fields.
Deleting a recordThe slot goes on a free list; any new record fits itFree space in the page is packed together; other records may move
SuitsFields that always have the same sizeVARCHAR fields, fields that may be NULL, repeating fields
Exam tip

Draw the slotted page: the header with entries at the start, free space in the middle and records packed at the end.

4.4 Indexing and Hashing

Ordered indexing and hashing

In one line: An ordered index keeps keys sorted, so it handles both exact lookups and ranges. Hashing jumps straight to a bucket, so it is best for exact lookups only.

Ordered indexing compared with hashing
Ordered indexingHashing
How it finds a recordSearches the sorted search-key values (for example, goes down a B+ tree).Computes a hash function on the value to get the bucket.
Exact value (RollNo = 126)A few disk reads (the height of the tree).About one disk read.
Range (RollNo 110 to 125)Fast: find 110, then read on in order.Slow: the values are scattered over all buckets.
Sorted output (ORDER BY)Free, because the keys are already in order.Needs a separate sort.
GrowthGrows smoothly (B+ tree).Static hashing overflows; dynamic hashing is needed.

Syntax side by side

B+ tree index (InnoDB) 
CREATE INDEX idx_roll
ON student (roll_no);
-- good for = and ranges:
SELECT * FROM student
WHERE roll_no BETWEEN 110 AND 125;
Hash index (MEMORY engine) 
CREATE TABLE s_mem (
  roll_no INT,
  INDEX USING HASH (roll_no)
) ENGINE = MEMORY;
-- good for = only:
SELECT * FROM s_mem
WHERE roll_no = 126;
Exam tip

InnoDB ignores USING HASH and builds a B+ tree. Only the MEMORY engine builds a real hash index.

Space and upkeepNeeds more space and more upkeep on inserts and deletes.Needs less space and less upkeep.
Works withCan be used with any file.Only when the file is sorted on the search key.

Clustering (primary) and non-clustering (secondary) indices

In one line: A clustering index is on the key the file is sorted by, so there is only one. A non-clustering index is on any other key, so there can be many and each must be dense.

Clustering index compared with non-clustering index
PointClustering (primary) indexNon-clustering (secondary) index
Order of the fileThe file is sorted on the same search key as the index.The file is sorted on a different key.
Number for each fileOnly one for each file.A file can have many.
Dense or sparseCan be sparse.Must be dense.
Range queriesRecords with nearby keys are in the same block, so range queries read few blocks.Records with nearby keys can be in different blocks, so a range query may read one block per record.
Also calledPrimary indexSecondary index
In MySQL (InnoDB)The PRIMARY KEY index; rows are stored in its orderEvery other index; each entry holds the primary key value of its row

4.7 B Tree Index Files

B tree and B+ tree

In one line: A B tree stores each key once, in any node. A B+ tree keeps every key in the linked leaves, so it is shorter and much better for range queries.

B tree compared with B+ tree
B treeB+ tree
Where keys are storedEach key once, in a leaf or an internal nodeEvery key in a leaf; some keys also in internal nodes
Record pointersIn every nodeOnly in the leaves
Leaves linked?NoYes, in key order
SearchMay stop early at an internal nodeAlways goes down to a leaf
Range queries and sorted readsSlow: must move up and down the treeFast: read along the linked leaves
Fan-outLower, because internal nodes also hold record pointersHigher, so the tree is shorter
Split of a full nodeMiddle key moves upLeaf: middle key is copied up; internal node: moved up
DeletionHarder: the key may be in an internal nodeSimpler: the key is always deleted from a leaf
SpaceSlightly less: no repeated keysSlightly more: some keys appear twice
Exam tip

Build both trees for the same few keys, side by side. Then point out the repeated keys and the leaf links in the B+ tree.

4.8 Static Hashing

Overflow chaining (closed hashing) and linear probing (open hashing)

In one line: Overflow chaining puts extra records in overflow buckets linked to the full bucket; linear probing puts them in the next bucket that has space.

Two ways to handle bucket overflow (Silberschatz's names)
BasisOverflow chaining (closed hashing)Linear probing (open hashing)
Where an extra record goesAn overflow bucket linked to its own bucketThe next bucket with free space
Set of bucketsFixed; chains growFixed; records spill into other buckets
SearchRead the bucket, then follow its chainProbe bucket after bucket until found or an empty slot is met
When the file is fullNew overflow buckets can always be addedNo record can be added
DeletionEasyHard: removing a record can break other keys' probe paths
Clustering of full bucketsNoYes, so searches get longer
Used inDatabase systemsIn-memory tables, for example in compilers
Exampleh(K) = K mod 5: bucket 0 holds 10 and 15, and its chain holds 20 and 25h(K) = K mod 10: 105 tries buckets 5, 6 and 7, then goes to 8
Exam tip

Some books swap the names open and closed hashing. Always name the method too: overflow chaining or linear probing.

4.9 Dynamic Hashing

Static and dynamic hashing

In one line: Static hashing has a fixed number of buckets, so a growing file overflows; dynamic (extendible) hashing splits buckets as the file grows.

Static hashing compared with dynamic (extendible) hashing
PointStatic hashingDynamic hashing
Number of bucketsThe number of buckets is fixed when the file is created.The number of buckets grows and shrinks with the data.
Hash functionThe hash function never changes.The function uses more or fewer bits of the hash value.
When the file growsA growing file causes bucket overflow and long chains.A full bucket splits, so overflow is rare.
Cost of growingGrowing means reorganizing the whole file.Growing changes only one bucket (and sometimes doubles the directory).
DirectorySimple; no directory.Needs a directory (bucket address table), one extra step on each lookup.
SpaceWastes space if built large for the future.Uses space in step with the data.
Exampleh(K) = K mod 5 with five fixed bucketsExtendible hashing, with a global depth and a local depth for each bucket
Exam tip

For the 16-mark question, show the same keys inserted both ways: an overflow chain forms in static hashing, while a bucket splits in extendible hashing.

4.10 Query Processing Overview

Nested-loop, block nested-loop, indexed nested-loop, merge and hash joins

In one line: The join algorithms find matching tuples in different ways. They test every pair, use an index, sort both inputs or hash both inputs into partitions.

Join algorithms and their costs (worst case, with little memory)
AlgorithmHow it worksBlock transfersSeeks
Nested-loop joinFor each tuple of r, read all of s and test each pair.nr × bs + brnr + br
Block nested-loop joinFor each block of r, read all of s and test the pairs block by block.br × bs + br2 × br
Indexed nested-loop joinFor each tuple of r, use an index on s to find the matching tuples.br × (tT + tS) + nr × c, where c is the cost of one index lookup
Merge joinSort both relations on the join attribute, then read them together once, like merging two sorted lists. Only for equi-joins and natural joins.br + bs (plus the cost of sorting)⌈br/bb⌉ + ⌈bs/bb⌉
Hash joinUse a hash function on the join attribute to split both relations into partitions; join each pair of matching partitions in memory.3(br + bs) + 4nh2(⌈br/bb⌉ + ⌈bs/bb⌉)

Try it

See the plan in MySQL 
EXPLAIN FORMAT=TREE
SELECT s.name, d.dept_name
FROM student s
JOIN department d
  ON s.dept_id = d.dept_id;
-- shows a nested loop
-- or a hash join
Exam tip

Learn the block nested-loop formula, br × bs + br. Then say that the smaller relation should be the outer one.

4.11 Query Optimization using Heuristics and Cost Estimation

Heuristic and cost-based optimization

In one line: Heuristic optimization applies fixed rules to the query tree; cost-based optimization estimates the cost of many plans from statistics and picks the cheapest.

Heuristic optimization compared with cost-based optimization
PointHeuristicCost-based
How it choosesApplies fixed rules to the query treeCompares the estimated cost of many plans
Uses statisticsNoYes: nr, br, V(A, r), histograms
Time to optimizeShortLonger, because many plans are compared
Quality of the planGood in most cases, but may miss the best planUsually finds a better plan, if the statistics are up to date
Merits (advantages)Simple and fast; needs no statisticsAdapts to the real data; chooses algorithms and join order well
Demerits (disadvantages)Ignores the actual data, so a rule can make a plan slowerCosts time and memory to optimize; poor estimates give poor plans

Each one at work

Heuristic rule: select early 
π name (σ dept = 'CSE'
  (student ⋈ marks))

-- becomes
π name ((σ dept = 'CSE'
  (student)) ⋈ marks)
Cost-based: statistics 
ANALYZE TABLE student;
-- refresh the statistics

EXPLAIN SELECT name
FROM student
WHERE dept = 'CSE';
-- estimated rows and cost
Exam tip

Real optimizers use both: heuristics to cut down the plans, then cost estimates to choose among the rest.
