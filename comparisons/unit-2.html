2.1 Entity-Relationship Model

In one line: A strong entity set has a primary key of its own; a weak entity set has only a partial key and depends on an owner entity set.

Strong and weak entity sets
Strong entity setWeak entity set

Drawn as a single rectangleDrawn as a double rectangle
Its key is underlinedIts discriminator has a dashed underline
Takes part in ordinary relationships (single diamond)Joined to its owner by an identifying relationship (double diamond)
Participation may be total or partialAlways total participation in the identifying relationship
Example: CourseExample: Section of a course; Payment of a loan

2.3 ER-to-Relational Mapping

Specialization and generalization

In one line: Specialization splits one entity set into subclasses (top-down); generalization joins several entity sets into one superclass (bottom-up). Both give the same ISA picture.

Specialization and generalization
BasisSpecializationGeneralization
DirectionTop-downBottom-up
Starts fromOne higher-level entity setSeveral lower-level entity sets
ResultNew subclasses (lower-level entity sets)A new superclass (higher-level entity set)
Why it is doneSome entities have attributes or relationships that others do notSeveral entity sets share common attributes
AttributesSubclasses add their own attributes and inherit the restThe common attributes move up to the superclass
SymbolISA triangle under the superclassThe same ISA triangle
ConstraintsDisjoint or overlapping; total or partialUsually total: every lower-level entity belongs to the superclass
ExamplePerson is specialized into Student and EmployeeCar and Truck are generalized into Vehicle
Three ways to map InventoryItem, Book and DVD
MethodTablesDrawback
1. A table for the superclass and each subclassInventoryItem(ID, Name), Book(ID, Publisher), DVD(ID, Manufacturer)Needs a join to see all the data of a book
2. Tables for the subclasses onlyBook(ID, Name, Publisher), DVD(ID, Name, Manufacturer)An item that is neither a book nor a DVD has no table
3. One table for the superclass onlyInventoryItem(ID, Name, Publisher, Manufacturer)Many NULLs: a book has no Manufacturer, a DVD has no Publisher
Exam tip

The two are opposite design steps that give the same diagram. Say which way you worked: from one entity down, or from many entities up.

2.4 Functional Dependencies

Trivial, non-trivial, full, partial and transitive dependencies

In one line: A trivial FD says nothing new. A partial FD depends on part of a key. A transitive FD goes through a non-key attribute.

Types of FDs, with examples from Marks
TypeMeaningExample
TrivialY is a subset of X. It always holds.{RegNo, CourseID} → RegNo
Non-trivialY is not a subset of X.RegNo → StudentName
Completely non-trivialX and Y have no attribute in common.CourseID → CourseName
FullY depends on the whole of X; remove any attribute from X and the FD fails.{RegNo, CourseID} → Marks
PartialA non-prime attribute depends on part of a candidate key.RegNo → StudentName (RegNo is part of the key {RegNo, CourseID})
TransitiveX → Y and Y → Z give X → Z, where Y is not a key and Z is non-prime.RegNo → Dept and Dept → HOD give RegNo → HOD
MultivaluedX determines a set of Y values (X →→ Y).Covered in Multivalued Dependencies and Fourth Normal Form
Exam tip

Partial dependencies break 2NF, and transitive dependencies break 3NF. Say this when you list the types.

Functional dependency and multivalued dependency

In one line: In an FD X → Y, each X value fixes one Y value. In an MVD X →→ Y, each X value fixes a set of Y values, whatever the other attributes are.

Functional dependency and multivalued dependency
BasisFunctional dependency (FD)Multivalued dependency (MVD)
NotationX → YX →→ Y
MeaningEach X value has exactly one Y valueEach X value has a set of Y values, independent of the rest of the attributes
Tuple ruleTwo tuples that agree on X also agree on YIf two tuples agree on X, the tuples with their Y values swapped must also exist
Attributes neededAt least twoAt least three (X, Y and the rest)
Trivial whenY ⊆ XY ⊆ X, or X ∪ Y is all the attributes
RelationshipEvery FD is also an MVDAn MVD is not always an FD
Extra ruleArmstrong's axiomsComplementation: X →→ Y gives X →→ R − X − Y
Normal form it drives2NF, 3NF and BCNF4NF
ExampleRegNo → Namesid →→ course and sid →→ skill in Student(sid, course, skill)

In one line: A lossless decomposition joins back to exactly the original table; a lossy one gives extra (spurious) rows, so information is lost.

Lossless and lossy decomposition
Lossless (non-loss) decompositionLossy decomposition
The natural join gives back exactly RThe natural join gives R plus spurious tuples
No information is lostInformation is lost: we cannot tell true rows from false ones
The common attributes are a superkey of at least one partThe common attributes are a superkey of neither part
Required for every normalization stepNever acceptable
Example: Employee and Department joined on DeptIDExample: Student split on Name

Join and subquery

In one line: A join puts columns of two tables side by side. A subquery is a query inside another query that passes its result outward.

Join and subquery
BasisJoinSubquery
How it worksCombines rows of two or more tables on a conditionAn inner query gives a value, a list or a table to the outer query
Columns in the resultFrom all the joined tablesOnly from the outer query's tables
Written inThe FROM clause (JOIN ... ON)WHERE, HAVING, FROM or SELECT, inside parentheses
DuplicatesCan repeat a row once for each matchIN and EXISTS do not repeat outer rows
ReadabilityClear when you need data from both tablesClear for “a question inside a question”, such as “more than the average”
SpeedUsually well optimizedOften rewritten into a join by MySQL; a correlated subquery may run once per row
When to use which
Use a subquery whenUse a join when
You compare with a single value, such as an averageYou need columns from both tables in the result
You test whether a match exists (EXISTS, NOT EXISTS)You combine many rows from both sides
The question reads naturally as “a question inside a question”A correlated subquery would run once per row on a big table

Join

2.15 Sub Queries

Correlated and non-correlated subqueries

In one line: A non-correlated subquery runs once on its own. A correlated subquery uses a column of the outer query, so it runs again for each outer row.

BasisNon-correlated (simple) subqueryCorrelated subquery

SpeedUsually fasterCan be slow on big tables (MySQL may rewrite it as a join)
Common operators=, <, >, IN, ANY, ALLEXISTS, NOT EXISTS, or a comparison with the outer row
Example questionEmployees who earn more than the company averageEmployees who earn more than the average of their own department
Kinds of subquery
KindReturnsUsed with
Single-row (scalar)One value=, <, >, <=, >=, <>
Multiple-rowOne column, many rowsIN, NOT IN, ANY, ALL
Table (derived table)Many rows and columnsFROM clause
CorrelatedAny of the above, once per outer rowUses a column of the outer query

Syntax side by side

Non-correlated

FROM EMPLOYEE

   FROM EMPLOYEE);
Correlated

BEFORE UPDATEBefore a row is changedCheck or adjust the new values
AFTER UPDATEAfter a row is changedLog the old and new values
BEFORE DELETEBefore a row is removedStop the delete if a rule says so
AFTER DELETEAfter a row is removedCopy the row to an archive table

Syntax side by side

BEFORE: fix the new value 
CREATE TRIGGER account_fix
BEFORE INSERT ON account
FOR EACH ROW
  SET NEW.balance =
      GREATEST(NEW.balance, 0);
-- a negative balance is saved as 0
AFTER: log the change 
CREATE TRIGGER account_au
AFTER UPDATE ON account
FOR EACH ROW
  INSERT INTO balance_log
    (acc_no, action,
     old_balance, new_balance)
  VALUES (NEW.acc_no, 'UPDATE',
          OLD.balance, NEW.balance);
Exam tip

Write the event, condition and action (ECA) of your trigger in words before the code. It shows that you understand it.
