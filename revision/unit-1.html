1.1 Purpose of Database System

  • A DBMS is a collection of interrelated data and a set of programs to access that data.
  • Its goal is to store and retrieve information conveniently and efficiently, and keep it safe.
  • A file-processing system keeps data in separate files with a separate program for each task.
  • The eight file-system problems: redundancy, inconsistency, difficulty in access, isolation, integrity, atomicity, concurrent access and security.
  • Redundancy (duplicate copies) leads to inconsistency (copies that disagree).
  • A DBMS controls redundancy, enforces constraints, supports transactions and limits access.
  • Demerits of a DBMS: complex design, cost, damage that spreads, conversion cost and training.

Common mistake: A DBMS does not remove redundancy completely. It controls it. Some copies, such as a foreign key or a backup, are kept on purpose.

1.2 Views of Data

  • Data abstraction hides how data is stored and shows users only what they need.
  • Physical level: how data is stored. Logical level: what data is stored and how it is related. View level: part of the database for one user group.
  • There is one physical schema and one logical schema, but there can be many views (subschemas).
  • Schema: the overall design, which rarely changes. Instance: the data at one moment, which changes often.
  • Physical data independence: change storage without changing the logical schema.
  • Logical data independence: change the logical schema without changing views or programs.
  • Logical data independence is harder to achieve than physical data independence.

Common mistake: Do not say the view level shows “the whole database in a simple way”. That is the logical level. The view level shows only part of the database.

1.3 Data Models

  • A data model is a collection of conceptual tools for describing data, relationships, semantics and constraints.
  • Relational model: data and relationships as tables (relations).
  • E-R model: entities and relationships, drawn as a diagram for design.
  • Object-based model: the relational model plus objects, methods and inheritance.
  • Semi-structured model: items of the same type can have different attributes; XML and JSON.
  • Hierarchical model: a tree, one parent per record; cannot show many-to-many directly.
  • Network model: a graph, many parents per record, linked by pointers.

1.4 Database System Architecture

  • The two main parts are the query processor and the storage manager.
  • Query processor: DDL interpreter, DML compiler (with query optimization) and query evaluation engine.
  • Storage manager: authorization and integrity manager, transaction manager, file manager and buffer manager.
  • Disk storage: data files, data dictionary (metadata), indices and statistical data.
  • Users: naive users, application programmers, sophisticated users and the DBA.
  • The DBA defines the schema, plans storage, grants access and does routine maintenance.
  • Two-tier: the client talks to the database. Three-tier: the client talks to an application server, which talks to the database.

Common mistake: The DDL interpreter writes to the data dictionary, not to the data files. A CREATE TABLE stores the table's definition, not its rows.

1.5 Introduction to Relational Databases

  • A relational database is a collection of tables, each with a unique name.
  • A table has rows (one per item) and columns (one per property).
  • The order of rows does not matter.
  • Tables are linked by common values, not by pointers.
  • E. F. Codd proposed the relational model in 1970.
  • MySQL, Oracle, SQL Server, PostgreSQL, Db2 and SQLite are relational database products; all use SQL.

1.6 Relational Model

  • Relation = table, tuple = row, attribute = column.
  • A domain is the set of permitted values of an attribute; atomic values cannot be divided.
  • The relation schema is the structure; the relation instance is the set of tuples at one moment.
  • Degree = number of attributes; cardinality = number of tuples.
  • NULL means unknown or not applicable; it is not zero or blank.
  • A relation has no duplicate tuples, and the order of tuples does not matter.

Common mistake: Students often swap degree and cardinality. For the degree, count the column headings. For the cardinality, count the rows.

1.7 Keys

  • Super key: one or more attributes that identify each tuple uniquely.
  • Candidate key: a minimal super key.
  • Primary key: the candidate key chosen by the designer; unique and never NULL; only one per relation.
  • Alternate key: a candidate key that is not the primary key.
  • Composite key: a key with two or more attributes.
  • Foreign key: attributes in a child table that refer to the primary key of a parent table.
  • Every candidate key is a super key; not every super key is a candidate key.

1.8 Constraints

  • An integrity constraint is a rule the data must satisfy; the DBMS rejects changes that break it.
  • Domain constraint: values must come from the attribute's domain (data type, CHECK).
  • Key constraint: no two tuples share a key value (PRIMARY KEY, UNIQUE).
  • NOT NULL forces a value; UNIQUE forbids repeats; CHECK tests a condition; DEFAULT fills a missing value.
  • Entity integrity: a primary key can never be NULL.
  • Referential integrity: a foreign key must match an existing primary key, or be NULL.
  • ON DELETE and ON UPDATE choose RESTRICT, CASCADE or SET NULL for the child rows.

Common mistake: Referential integrity does not always delete the child rows. That happens only with ON DELETE CASCADE. By default, the DBMS refuses to delete a parent row that still has children.

1.9 Relational Algebra

  • Relational algebra is a procedural query language; each operation takes relations and gives a relation.
  • Fundamental operations: select σ, project π, union ∪, set difference −, Cartesian product × and rename ρ.
  • σ picks rows by a predicate; π picks columns and removes duplicates.
  • Union, intersection and difference need union-compatible relations; r − s ≠ s − r.
  • Theta join = σθ(r × s); an equijoin uses only =; a natural join matches common attributes and keeps them once.
  • Outer joins keep unmatched tuples and fill the gaps with NULL (left ⟕, right ⟖, full ⟗).
  • Division (÷) answers “for all” queries; assignment (←) stores a partial result.

Common mistake: Do not mix up σ and π. σ selects rows; π projects columns. Note that the SQL keyword SELECT does the job of π, not σ. The WHERE clause does the job of σ.

1.10 Overview of the SQL Query Language

  • SQL is the standard, declarative language of relational databases.
  • It began as SEQUEL at IBM in the 1970s; the first ANSI standard was SQL-86.
  • DDL defines the schema: CREATE, ALTER, DROP, TRUNCATE, RENAME.
  • DML works on the data: INSERT, UPDATE, DELETE, SELECT.
  • DCL controls access (GRANT, REVOKE); TCL controls transactions (COMMIT, ROLLBACK, SAVEPOINT).
  • CHAR(n) is fixed length; VARCHAR(n) is variable length.
  • DECIMAL(p, d): p digits in all, d after the decimal point.

1.11 Basic Structure of SQL Queries

  • Basic form: SELECT columns FROM tables WHERE condition.
  • SELECT ≈ π, FROM ≈ ×, WHERE ≈ σ.
  • SQL keeps duplicates unless you write DISTINCT.
  • With several tables in FROM, a join condition in WHERE (or JOIN ... ON) pairs the right rows.
  • AND needs all conditions true, OR needs one, NOT reverses a condition; IN, BETWEEN and LIKE are short forms.
  • ORDER BY sorts the result; ASC is the default, DESC is largest first.
  • Clauses run in the order FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY.

1.12 DDL

  • DDL defines the schema: CREATE, ALTER, DROP, TRUNCATE and RENAME.
  • CREATE TABLE lists each column with a data type, then any table-level constraints.
  • Constraints can be written at column level or table level; composite keys go at table level.
  • ALTER TABLE can ADD, DROP COLUMN, MODIFY or RENAME COLUMN, and add or drop constraints.
  • DROP removes the table; TRUNCATE empties it; DELETE (DML) removes chosen rows.
  • DDL is auto-committed in MySQL, so it cannot be rolled back.

1.13 DML

  • DML works on rows: INSERT, UPDATE, DELETE and SELECT.
  • INSERT can add one row, many rows, or the result of a SELECT.
  • UPDATE ... SET ... WHERE changes chosen rows; without WHERE it changes every row.
  • DELETE FROM ... WHERE removes chosen rows; without WHERE it empties the table.
  • Every INSERT, UPDATE and DELETE must satisfy the table's constraints.
  • DML can be undone with ROLLBACK before COMMIT; DDL cannot.
