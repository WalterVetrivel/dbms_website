4.1 RAID

  • RAID (Redundant Array of Independent Disks) makes many disks work as one logical disk.
  • Striping gives speed, mirroring gives safety, and parity gives safety at a lower cost.
  • Parity is the XOR of the data blocks in a stripe. XOR of the other blocks rebuilds a lost block.
  • RAID 0 has no redundancy. RAID 1 mirrors every block.
  • RAID 2 uses error-correcting codes; RAID 3 and RAID 4 use one parity disk (bit and block striping).
  • RAID 5 spreads parity over all disks, so there is no parity bottleneck.
  • RAID 6 stores P and Q in each stripe and survives two disk failures.
  • Choose a level by cost, normal performance, performance after a failure and rebuild performance.

4.2 File Organization

  • A file is a sequence of records, and a record is a sequence of fields. Data moves between disk and memory in blocks.
  • A file organization is the way the records of a file are arranged on disk.
  • Heap: records in any order. Fast inserts, slow searches.
  • Sequential: records sorted on a search key and linked by pointers. Fast ordered reads, slow inserts.
  • A sequential file puts extra records in overflow blocks and is reorganized from time to time.
  • Hashing: a hash function on an attribute gives the bucket of each record. Fast exact lookups, poor range queries.
  • Multitable clustering stores related records of several tables together, which speeds up joins.

4.3 Organization of Records in Files

  • Fixed-length records all have the same size n; record i starts at byte n × (i − 1).
  • Deleted fixed-length records are linked in a free list that starts at the file header.
  • Variable-length records store an (offset, length) pair for each variable field, a null bitmap and then the field data.
  • The slotted page has a header with the number of entries, the end of free space and the location and size of each record.
  • In a slotted page, records are packed at the end of the block and may move; pointers point to header entries.
  • The data dictionary (system catalog) stores metadata: schemas, constraints, users, indices and statistics.
  • Column-oriented storage keeps each attribute together; it suits analytics, while row storage suits transactions.

4.4 Indexing and Hashing

  • An index is an extra structure that finds records quickly, like the catalog of a library.
  • A search key is the attribute (or set of attributes) used to look up records. Any attribute can be a search key.
  • An index entry holds a search-key value and pointers to the records with that value.
  • There are two basic kinds: ordered indices (sorted values) and hash indices (values spread over buckets).
  • Indices are evaluated on access types, access time, insertion time, deletion time and space overhead.
  • Every index slows down inserts, deletes and updates, and uses space, so only useful indices are built.
  • Hashing is best for exact-value lookups; ordered indices also handle range queries and sorted output.

4.5 Ordered Indices

  • An ordered index keeps search keys in sorted order with pointers to the records.
  • A primary (clustering) index has a search key that sets the file order; a file has only one.
  • A secondary (non-clustering) index is on any other search key; it must be dense.
  • A dense index has an entry for every search-key value; a sparse index has one for only some values, usually one per block.
  • To search a sparse index, take the largest entry less than or equal to the key, then scan that block.
  • A multilevel index builds a sparse outer index on the inner index, so a search reads very few blocks.
  • A secondary index on a non-key attribute points to a bucket of record pointers for each value.

4.6 B+ Tree Index Files

  • A B+ tree is a balanced tree index: every leaf is on the same level.
  • A node has up to n pointers and n − 1 keys. Every node except the root is at least half full.
  • All keys and record pointers are in the leaves. The leaves are linked in key order.
  • A search goes from the root to one leaf, so it reads one node on each level.
  • A leaf split copies the middle key up. An internal node split moves the middle key up.
  • A deletion that leaves a node too empty borrows from a sibling, or merges with one if no sibling can lend.
  • The tree grows taller only when the root splits, and shorter only when the root loses its last key.
  • A high fan-out keeps the tree short, so a search needs few disk reads.

4.7 B Tree Index Files

  • A B tree is a balanced tree index in which each key appears only once.
  • Every key, in any node, has a pointer to its record. The leaves are not linked.
  • A node of order n has at most n − 1 keys; every node except the root has at least ⌈n / 2⌉ − 1 keys.
  • A search can stop at an internal node when it finds the key there.
  • Insertion splits a full node and moves the middle key up; a root split makes the tree taller.
  • To delete an internal key, replace it with its in-order successor; an underflow borrows from a sibling or merges.
  • B+ trees are preferred in practice: linked leaves give fast range queries, and a higher fan-out keeps the tree short.

4.8 Static Hashing

  • A hash function h maps each search-key value to a bucket; a bucket is usually one disk block.
  • In static hashing, the number of buckets is fixed, for example h(K) = K mod B.
  • A search on the hash key reads about one block.
  • A good hash function is uniform and random.
  • Bucket overflow is caused by too few buckets or by skew.
  • Overflow chaining (closed hashing) links overflow buckets to a full bucket; databases use this method.
  • Open hashing with linear probing puts the record in the next bucket with space; it causes clustering and makes deletion hard.
  • Static hashing cannot grow or shrink well, and it is poor for range queries.

4.9 Dynamic Hashing

  • Dynamic hashing changes the number of buckets as the data grows or shrinks; extendible hashing is the common form.
  • The directory (bucket address table) uses the last d bits of the hash value; d is the global depth.
  • Each bucket has a local depth d′; 2d − d′ directory entries point to it.
  • A full bucket with d′ < d splits; the directory does not change size.
  • A full bucket with d′ = d first doubles the directory (d increases by 1), then splits.
  • When a bucket becomes empty, it merges with its split image, and the directory may halve.
  • Dynamic hashing avoids overflow chains and full reorganization, at the cost of one directory lookup.

4.10 Query Processing Overview

  • Query processing has three steps: parsing and translation, optimization, and evaluation.
  • The parser checks syntax and names, and translates SQL into relational algebra.
  • A query evaluation plan is relational algebra annotated with how to evaluate each operation.
  • Query cost = b × tT + S × tS: block transfers and seeks, because disk access dominates.
  • Linear search costs br transfers + 1 seek; binary search costs ⌈log2(br)⌉ × (tT + tS).
  • External merge sort makes sorted runs that fit in memory, then merges them.
  • Join algorithms: nested-loop, block nested-loop, indexed nested-loop, merge join and hash join; the choice depends on cost.

4.11 Query Optimization using Heuristics and Cost Estimation

  • Query optimization chooses the most efficient plan from many equivalent plans.
  • A query tree shows relations as leaves and operations as internal nodes; the canonical tree is correct but slow.
  • Equivalence rules (cascade of σ, pushing σ and π through joins, join commutativity and associativity) let the optimizer rewrite a tree safely.
  • Heuristic rules: perform selections early, perform projections early, do the most restrictive operations first, and replace × followed by σ with ⋈.
  • Cost-based optimization estimates the cost of each plan from catalog statistics (nr, br, V(A, r), histograms) and picks the cheapest.
  • Selectivity is the fraction of tuples that satisfy a condition; σA = v(r) is estimated as nr / V(A, r).
  • Heuristics are fast but may miss the best plan; cost-based optimization is slower but usually better.
