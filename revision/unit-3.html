3.1 Transaction Concepts

  • A transaction is a single logical unit of work that runs completely or not at all.
  • read(X) copies X from the database to the transaction's buffer; write(X) copies it back.
  • A transaction ends with commit (changes kept) or abort (changes rolled back).
  • The five states are active, partially committed, failed, aborted and committed.
  • Partially committed means the last statement ran; the transaction can still fail.
  • After an abort, the system can restart or kill the transaction.
  • A committed transaction can only be reversed by a compensating transaction.

3.2 ACID Properties

  • ACID stands for atomicity, consistency, isolation and durability.
  • Atomicity: all operations happen or none do; old values in the log allow undo.
  • Consistency: a transaction run alone keeps the database consistent (A + B unchanged).
  • Isolation: concurrent transactions do not see each other's unfinished work.
  • Durability: committed changes survive system failures.
  • The recovery system ensures atomicity and durability.
  • The concurrency-control system ensures isolation; the programmer and integrity constraints ensure consistency.

3.3 Schedules

  • A schedule is the time order of the instructions of concurrent transactions; it keeps each transaction's own order.
  • Serial: no interleaving, always consistent; n transactions have n! serial schedules.
  • Concurrent schedules improve throughput and waiting time, but some give wrong results (schedule 4 creates ₹50).
  • A serializable schedule has the same effect as some serial schedule.
  • Recoverable: if Tj reads from Ti, Ti commits before Tj commits.
  • Cascading rollback: one abort forces other transactions that read its data to roll back.
  • Cascadeless: read only committed data. Strict: no read or write of an item until its writer ends.
  • Strict ⊂ cascadeless ⊂ recoverable.

3.4 Serializability

  • A schedule is serializable if it is equivalent to some serial schedule.
  • Two instructions conflict if they are from different transactions, use the same item, and at least one is a write.
  • Conflict serializable: can be turned into a serial schedule by swapping non-conflicting instructions.
  • View equivalence: same initial reads, same reads-from, same final writes.
  • Every conflict serializable schedule is view serializable; the extra view serializable ones have blind writes.
  • Precedence graph: edge Ti → Tj for each conflicting pair where Ti acts first.
  • No cycle means conflict serializable; topological sort gives the serial order.

3.5 Concurrency Control and Need for Concurrency

  • Concurrency gives better throughput, better resource use and shorter waiting time.
  • Concurrency control keeps concurrent schedules serializable and recoverable.
  • Lost update: a later write overwrites an earlier one (write-write).
  • Dirty read: reading uncommitted data that may be rolled back (write-read).
  • Unrepeatable read: the same item gives two values in one transaction (read-write).
  • Incorrect summary: an aggregate mixes old and new values.
  • Phantom: a repeated range query sees newly inserted rows.
  • Protocols: lock-based, timestamp-based, validation-based and multiversion.

3.6 Locking Protocols

  • A transaction must hold a lock on an item before it accesses it.
  • Shared (S): read only, many holders. Exclusive (X): read and write, one holder.
  • Compatibility: only S with S is true; any pair with X is false.
  • An incompatible request waits until the conflicting locks are released.
  • Unlocking too early can still give wrong results (T2 displays 250 instead of 300).
  • A locking protocol is a set of rules for when to lock and unlock, to ensure serializability.
  • The lock manager keeps a lock table: a hash table of items with lists of requests.
  • Starvation: a transaction waits forever; avoided by serving requests in arrival order.

3.7 Two Phase Locking

  • 2PL: a growing phase (only lock) followed by a shrinking phase (only unlock).
  • The lock point is where a transaction gets its final lock.
  • 2PL ensures conflict serializability; the serial order is the order of lock points.
  • Basic 2PL allows deadlock and cascading rollback.
  • Strict 2PL holds X locks until commit or abort, so it is cascadeless.
  • Rigorous 2PL holds all locks until commit or abort; transactions serialize in commit order.
  • Upgrade (S to X) only in the growing phase; downgrade (X to S) only in the shrinking phase.
  • Conservative 2PL takes all locks before starting, so it is deadlock-free.

3.8 Deadlock

  • Deadlock: a set of transactions each waiting for another in the set, in a circle.
  • Four conditions: mutual exclusion, hold and wait, no preemption, circular wait.
  • Prevention: lock all at start, lock in a fixed order, wait-die, wound-wait, timeout.
  • Wait-die: older waits, younger dies. Wound-wait: older wounds, younger waits.
  • The rolled back transaction keeps its old timestamp, so it does not starve.
  • Wait-for graph: edge Ti → Tj when Ti waits for Tj. A cycle means deadlock.
  • Recovery: select a victim, roll it back (total or partial), and avoid starvation.
  • Livelock: transactions keep changing state but never progress.

3.9 Transaction Recovery

  • Failures: transaction failure (logical or system error), system crash, disk failure.
  • Storage: volatile (lost on crash), non-volatile (lost on disk failure), stable (never lost).
  • Log records: start, update (item, old value, new value), commit, abort.
  • WAL: the log record reaches stable storage before the data block it describes.
  • Deferred: log new values, change the database after commit; redo only.
  • Immediate: log old and new values; undo unfinished, redo committed.
  • Checkpoint: flush the log and changed blocks, log <checkpoint L>; recovery starts there.
  • Shadow paging: copy-on-write pages; commit switches one pointer; no undo or redo.

3.10 Save Points

  • A savepoint is a named point inside a transaction that you can roll back to.
  • SAVEPOINT s creates it; ROLLBACK TO s undoes changes after it; RELEASE SAVEPOINT s removes it.
  • ROLLBACK TO keeps changes made before the savepoint and keeps the transaction open.
  • Savepoints created after s are removed by ROLLBACK TO s; s itself remains.
  • COMMIT and ROLLBACK end the transaction and remove all savepoints.
  • Savepoints need a transaction: use START TRANSACTION or turn autocommit off.

3.11 Isolation Levels

  • An isolation level is defined by which phenomena it allows.
  • Phenomena: dirty read, non-repeatable read, phantom.
  • READ UNCOMMITTED allows all three; READ COMMITTED stops dirty reads.
  • REPEATABLE READ also stops non-repeatable reads; SERIALIZABLE stops all three.
  • Higher level: more consistency, less concurrency.
  • SET TRANSACTION ISOLATION LEVEL ... chooses the level.
  • MySQL InnoDB defaults to REPEATABLE READ and uses snapshots for plain reads.

3.12 SQL Facilities for Concurrency and Recovery

  • START TRANSACTION, COMMIT and ROLLBACK mark a transaction; autocommit makes each statement its own transaction.
  • SET TRANSACTION chooses the isolation level and access mode.
  • FOR SHARE takes shared row locks; FOR UPDATE takes exclusive row locks; both last until commit.
  • LOCK TABLES locks whole tables, and commits any open transaction first.
  • Lock wait timeouts and deadlock errors should be handled by retrying the transaction.
  • Recovery: redo log for COMMIT, undo log for ROLLBACK, automatic crash recovery, backups for disk failure.

3.13 Backup and Recovery System

  • Backup: a copy of the database in a safe place. Recovery: restoring a correct state after failure.
  • Full copies everything; incremental copies changes since the last backup; differential copies changes since the last full backup.
  • Restore with incremental: full plus every incremental. With differential: full plus the latest differential.
  • Logical backups are SQL text; physical backups are file copies. Hot backups run while the database is in use.
  • Point-in-time recovery: restore the last full backup, then replay the binary log up to the chosen moment.
  • A remote backup site applies the primary's log and takes over if the primary fails.
  • RAID and replication are not backups.

3.14 SQL DCL and TCL Commands

  • DCL: GRANT gives privileges, REVOKE takes them away. GRANT ... TO; REVOKE ... FROM.
  • WITH GRANT OPTION lets the receiver pass the privilege on.
  • Roles group privileges so they can be given to many users at once.
  • TCL: COMMIT saves, ROLLBACK undoes, SAVEPOINT marks a point for a partial rollback.
  • A transaction runs from START TRANSACTION to COMMIT or ROLLBACK.
  • DCL is about security; TCL is about atomicity and durability.
