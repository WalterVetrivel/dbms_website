5.1 Distributed Databases: Architecture

  • A distributed database stores related data at several sites joined by a network, but looks like one database to users.
  • Each site has its own local DBMS and database; a DDBMS manages the whole system.
  • A request that cannot be answered locally is sent to the site that holds the data.
  • Replication keeps copies at several sites: better availability, but costly updates.
  • Horizontal fragmentation splits rows with σ and is rebuilt with union (∪).
  • Vertical fragmentation splits columns with π, keeps the key in every fragment, and is rebuilt with join (⋈).
  • Mixed fragmentation uses both splits.
  • Transparency hides fragmentation, replication and location from the user.

5.2 Types of Distributed Databases

  • The type depends on two things: whether sites use the same software (homogeneity) and how much control each site keeps (autonomy).
  • Homogeneous: same DBMS and schema at all sites; sites know each other and cooperate fully.
  • Heterogeneous: sites may use different DBMS software, schemas or data models; middleware translates between them.
  • Federated (multidatabase): each database keeps its own control and shares only some data through a common layer.
  • There are four kinds of autonomy. They are design, communication, execution and association.
  • A homogeneous system is easy to manage. A heterogeneous system lets old databases work together.

5.3 Transaction Processing

  • A global (distributed) transaction uses data at more than one site; a local transaction uses only one site.
  • The transaction coordinator starts, splits and ends transactions; the transaction manager runs them at its own site and keeps the log.
  • Failure modes: site failure, lost message, link failure and network partition.
  • 2PC phase 1: prepare T, then each site logs <ready T> or <no T> and votes.
  • 2PC phase 2: commit only if all vote ready; the coordinator logs <commit T> or <abort T> and tells every site.
  • A recovering site with no <ready T> aborts T; with <ready T> only, it must ask what was decided.
  • 2PC can block: if the coordinator fails after all sites are ready, they must wait for it.
  • 3PC adds a pre-commit phase so that a new coordinator can decide, avoiding blocking when there is no partition.

5.4 NoSQL Databases: Introduction

  • NoSQL means “not only SQL”. It is a non-relational database with a flexible schema.
  • It is needed for big data, varied data, high availability and easy scaling.
  • Relational databases mostly scale up (bigger server). NoSQL databases scale out (more servers).
  • BASE means basically available, soft state and eventual consistency. It trades strict consistency for availability.
  • The four types are document, key-value, column-based and graph databases.
  • Choose a relational database for strict correctness and complex queries. Choose NoSQL for huge, fast-changing data.

5.5 CAP Theorem

  • C: every read sees the latest write. A: every request gets an answer. P: the system works when the network splits.
  • The CAP theorem says a distributed system can guarantee at most two of C, A and P at the same time.
  • Partitions cannot be avoided across many servers, so the real choice during a partition is C or A.
  • CP systems refuse or wait (HBase, MongoDB). AP systems answer with possibly old data (Cassandra, CouchDB, DynamoDB).
  • CA is possible only on a single site, such as MySQL on one server.
  • BASE and eventual consistency are the AP choice. The C in CAP is not the C in ACID.

5.6 Document Based Systems

  • A document database stores data as JSON-like documents grouped into collections.
  • A document has fields; values can be arrays or embedded documents. _id is the unique key.
  • Documents in one collection can have different fields (flexible schema).
  • Embed data that is read together; refer to data that is shared or grows without limit.
  • MongoDB uses commands such as insertOne, find, updateOne and deleteOne.
  • MongoDB and CouchDB are the two best-known document databases.

5.7 Key Value Stores

  • A key-value store keeps data as a unique key and a value; it finds data only by key.
  • The basic operations are put, get and delete (SET, GET and DEL in Redis).
  • Keys are designed from what the app knows, such as cart:42.
  • Keys are spread over servers by hashing; consistent hashing makes adding servers easy.
  • Uses: caches, login sessions with expiry, shopping carts, counters and leaderboards.
  • Examples: Redis (in memory) and Amazon DynamoDB (managed cloud service).

5.8 Column Based Systems

  • A column-based (wide-column) database stores rows by row key, with columns grouped into column families.
  • Families are declared; columns are not. Each row can have different columns, and missing cells are not stored.
  • Cells can keep several versions with timestamps.
  • HBase uses put, get and scan; Cassandra uses CQL with a partition key and clustering columns.
  • Tables are designed around the queries; there are no joins.
  • Examples: Apache HBase and Apache Cassandra. Uses: sensor data, logs, messages, time series.

5.9 Graph Databases

  • A graph database stores nodes (entities), relationships (edges) and properties on both.
  • Labels group nodes, such as :Person; relationships are named and directed, such as KNOWS.
  • Links are stored directly (index-free adjacency), so multi-hop queries are fast.
  • Neo4j uses Cypher: MATCH (a)-[:KNOWS]->(b) RETURN b.
  • Uses: social networks, fraud detection, recommendations and routes.
  • Examples: Neo4j, Amazon Neptune, ArangoDB and JanusGraph.

5.10 Database Security: Security Issues

  • Database security protects data against unauthorized access, wrong changes and loss.
  • The issues are legal and ethical, policy, system, and data and user level issues.
  • Threats cause loss of integrity, availability or confidentiality (CIA).
  • The four control measures are access control, inference control, flow control and encryption.
  • Inference control stops users from working out private values from summary answers.
  • The DBA creates accounts, grants and revokes privileges, assigns security levels and keeps the audit log.

5.11 Access Control Based on Privileges

  • A privilege is a right to do one action on one object. DAC grants and revokes privileges at the owner's choice.
  • Privileges exist at the account level and at the table (relation) level, even down to columns.
  • The access matrix has subjects as rows, objects as columns and privileges in the cells.
  • GRANT ... ON ... TO gives privileges; REVOKE ... ON ... FROM takes them back. Views limit rows.
  • WITH GRANT OPTION lets privileges spread; REVOKE ... CASCADE removes the spread copies in standard SQL.
  • MAC uses clearance and classification levels. Bell-LaPadula: no read up, no write down.

5.12 Role Based Access Control

  • RBAC gives privileges to roles and roles to users. A user can have many roles.
  • The three parts are users, roles and permissions.
  • In a role hierarchy, a senior role inherits the privileges of junior roles.
  • Separation of duties keeps conflicting roles, such as entry and approval, apart.
  • MySQL 8.4: CREATE ROLE, GRANT ... TO role, GRANT role TO user, then SET DEFAULT ROLE or SET ROLE.
  • RBAC is easier to manage at scale than DAC and more flexible than MAC.

5.13 SQL Injection

  • SQL injection happens when user input is joined into an SQL query and changes its meaning.
  • A quote in the input closes the string early; what follows runs as SQL.
  • Classic attacks: ' OR '1'='1 (always true), admin' -- (comment) and UNION SELECT (steal data).
  • Types: in-band (tautology, UNION, error based), blind (boolean, time based), stacked, out-of-band and second order.
  • Impacts: login bypass, data theft, data change or loss, and server takeover.
  • Prevention: prepared statements first, plus allow-list validation, least privilege and hidden errors.

5.14 Encryption and Public Key Infrastructures

  • Encryption turns plaintext into ciphertext with a key; decryption reverses it.
  • Symmetric (AES): one shared key, fast, but the key is hard to share.
  • Asymmetric (RSA): public key to encrypt, private key to decrypt; slower; solves key sharing.
  • Passwords are hashed with a salt, not encrypted.
  • A digital signature is a hash encrypted with the sender's private key and checked with their public key.
  • PKI is the system of certificate authorities, certificates, policies and revocation that makes public keys trustworthy. MySQL uses it for TLS connections.

5.15 Challenges

  • Database security is never finished, because attacks, systems and laws keep changing.
  • Data quality: users must be able to trust that data is right, complete and from a known source.
  • Intellectual property: hidden marks in the data (watermarks and fingerprints) prove who owns it and trace leaks.
  • Survivability: confinement, damage assessment, reconfiguration, repair and fault treatment.
  • Privacy: removing names is not enough. Blur ages, PIN codes and similar details so each person looks like several others (k-anonymity).
  • Newer challenges include cloud settings, insiders, ransomware, NoSQL defaults, devices and AI.
