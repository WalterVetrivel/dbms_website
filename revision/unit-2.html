2.1 Entity-Relationship Model

  • The E-R model is a conceptual model built in the conceptual design step, before any table exists.
  • Entity set: rectangle. Attribute: ellipse. Relationship set: diamond.
  • Attribute types: simple or composite, single-valued or multivalued (double ellipse), stored or derived (dashed ellipse), and key (underlined).
  • Mapping cardinality: 1 : 1, 1 : N, N : 1 or M : N. It gives the largest number of partners.
  • Total participation (double line): every entity takes part. Partial (single line): some may not.
  • A weak entity set has no key of its own. Its key is the owner's key + its discriminator.
  • A relationship set can have descriptive attributes, such as Grade on Takes.

2.2 E-R Diagrams

  • Nouns become entity sets (rectangles); verbs become relationship sets (diamonds).
  • Underline the key of every strong entity set; give a weak entity set a dashed-underlined partial key.
  • A fact that needs both sides of a relationship is an attribute of the relationship.
  • Write 1, N or M on each line, and use a double line for total participation.
  • No foreign keys in an E-R diagram: the relationship line is the link.
  • Always state your assumptions under the diagram.

2.3 ER-to-Relational Mapping

  • Strong entity set: a table with its simple attributes; its key is the primary key.
  • Weak entity set: a table whose primary key is the owner's key + the partial key.
  • 1 : N: the foreign key goes into the many side. 1 : 1: into either side, preferably the total side.
  • M : N: a new table whose primary key is both foreign keys, plus the relationship attributes.
  • Multivalued attribute: a new table (owner key, value). Composite: one column per part. Derived: not stored.
  • A relationship table holds only keys and the relationship's own attributes.

2.4 Functional Dependencies

  • X → Y: tuples that agree on X must agree on Y. FDs come from the meaning of the data.
  • Types: trivial, non-trivial, full, partial (on part of a key) and transitive (through a non-key).
  • Armstrong's axioms: reflexivity, augmentation and transitivity. Union, decomposition and pseudotransitivity are derived from them.
  • F+ is every FD implied by F. X+ is every attribute X determines.
  • X is a superkey if X+ is all attributes; a candidate key if it is also minimal.
  • Attributes never on a right side are in every candidate key.
  • Canonical cover: split right sides, remove extraneous left-side attributes, remove redundant FDs, combine.

2.5 Non-loss Decomposition

  • Redundancy causes the update, insertion and deletion anomalies.
  • Decomposition splits R into R1, ..., Rn whose union is R.
  • Non-loss (lossless-join): R1 ⋈ R2 ⋈ ... ⋈ Rn = R, with no spurious tuples.
  • Two parts: lossless if R1 ∩ R2 → R1 or R1 ∩ R2 → R2 (the common attributes are a superkey of one part).
  • Three or more parts: use the tableau test; lossless if some row becomes all a's.
  • Lossless join is required; dependency preservation is desirable.

2.6 First, Second and Third Normal Forms

  • Normalization splits tables using FDs so that each fact is stored once. Every split must be lossless.
  • 1NF: every cell holds one atomic value.
  • A prime attribute is part of some candidate key; a non-prime attribute is not.
  • 2NF: 1NF and no partial dependency (no non-prime attribute depends on part of a key).
  • 3NF: 2NF and no transitive dependency. Test: for every FD X → A, X is a superkey or A is prime.
  • To fix a violation X → Y, move X and Y to a new table and keep X in the old one.
  • A table whose keys all have one attribute is in 2NF as soon as it is in 1NF.

2.7 Dependency Preservation

  • Fi, the restriction of F to Ri, holds the FDs of F+ that use only attributes of Ri.
  • Dependency preserving: (F1 ∪ ... ∪ Fn)+ = F+.
  • Test: every FD X → Y of F must have Y in X+ computed under F1 ∪ ... ∪ Fn.
  • An FD that fits inside one part is always preserved.
  • A lost FD can only be checked with a join, for example in a trigger.
  • Lossless join is required; dependency preservation is desirable. 3NF can always have both; BCNF sometimes cannot.

2.8 Boyce-Codd Normal Form

  • BCNF: for every non-trivial FD X → Y, X is a superkey.
  • 3NF also allows X → A when A is prime. BCNF removes that exception.
  • 3NF and BCNF differ only when candidate keys overlap.
  • To decompose, split on a violating X → Y into (X ∪ Y) and (R − (Y − X)), and repeat.
  • BCNF decomposition is always lossless but may lose an FD; 3NF can always keep both.
  • Every relation with two attributes is in BCNF.

2.9 Multivalued Dependencies and Fourth Normal Form

  • X →→ Y: each X value has a set of Y values, independent of the other attributes.
  • MVDs come in pairs: X →→ Y gives X →→ R − X − Y.
  • Every FD is an MVD. An MVD is trivial if Y ⊆ X or X ∪ Y = R.
  • R splits losslessly into (X ∪ Y) and (X ∪ Z) exactly when X →→ Y holds.
  • 4NF: for every non-trivial MVD X →→ Y, X is a superkey. 4NF implies BCNF.
  • A BCNF table can still repeat data when it stores two independent lists; 4NF splits them.

2.10 Join Dependencies and Fifth Normal Form

  • *(R1, ..., Rn) holds if R always equals the join of its projections on R1, ..., Rn.
  • An MVD is a join dependency with two parts.
  • Some tables are lossy for every split into two but lossless for a split into three.
  • 5NF (PJNF): every non-trivial JD is implied by the candidate keys.
  • To reach 5NF, split the table on its join dependency, one table per part.
  • 5NF ⊂ 4NF ⊂ BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF.

2.11 SQL Set Operations

  • Set operations combine two SELECT results with the same number of columns and compatible types.
  • UNION: rows in either result, duplicates removed. UNION ALL keeps duplicates.
  • INTERSECT: rows in both results. EXCEPT: rows in the first but not the second.
  • MySQL uses EXCEPT, not MINUS. INTERSECT and EXCEPT need MySQL 8.0.31 or later.
  • Put one ORDER BY at the end. Without it, the order is not guaranteed.

2.12 Aggregate Functions

  • COUNT, SUM, AVG, MIN and MAX each return one value from many rows.
  • COUNT(*) counts rows; COUNT(column) counts non-NULL values; COUNT(DISTINCT column) counts different values.
  • SUM and AVG work on numbers only. MIN and MAX also work on text and dates.
  • All aggregates except COUNT(*) skip NULL. With no rows, COUNT gives 0 and the others give NULL.
  • WHERE runs before aggregation, so aggregates cannot go in WHERE. Use HAVING.
  • A plain column beside an aggregate needs GROUP BY.

2.13 GROUP BY and HAVING

  • GROUP BY forms groups of rows with equal values; aggregates then give one result per group.
  • Each SELECT column must be in GROUP BY or inside an aggregate.
  • HAVING filters groups and can use aggregates; WHERE filters rows and cannot.
  • Order of execution: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY.
  • Put plain-column conditions in WHERE, so fewer rows are grouped.
  • GROUP BY does not sort; use ORDER BY.

2.14 Joins

  • An inner join keeps only matching pairs. NULL never matches anything.
  • Left and right outer joins also keep unmatched rows of one side, padded with NULL.
  • MySQL has no FULL OUTER JOIN; write LEFT JOIN UNION RIGHT JOIN.
  • A cross join returns every pair: rows(A) × rows(B).
  • A self join uses one table twice, with two aliases.
  • In an outer join, a condition on the optional side belongs in ON, not WHERE.

2.15 Sub Queries

  • A subquery is a SELECT in brackets inside another statement. It can be in WHERE, HAVING, FROM or SELECT.
  • A single-row subquery returns one value and works with =, <, > and the like. Using = with many rows gives error 1242.
  • A multiple-row subquery needs IN, ANY or ALL. > ANY means above the smallest; > ALL means above the largest.
  • A correlated subquery uses a column of the outer query and runs once per outer row.
  • EXISTS tests whether the subquery returns any row. NOT EXISTS is safer than NOT IN when NULL values are possible.
  • A subquery in FROM is a derived table and needs an alias.
  • ORDER BY is allowed in a subquery; it matters together with LIMIT. GROUP BY groups rows; it does not sort.
  • In MySQL, UPDATE and DELETE cannot read the table they change in a subquery (error 1093).

2.16 Views

  • A view is a stored SELECT query that acts as a virtual table. It holds no data of its own.
  • A view always shows the current data of its base tables.
  • A simple one-table view is updatable. Changes go to the base table.
  • Views with aggregates, DISTINCT, GROUP BY, HAVING or UNION are read-only.
  • WITH CHECK OPTION rejects rows that would not appear in the view.
  • Use CREATE OR REPLACE VIEW or ALTER VIEW to change a view, and DROP VIEW to remove it. Dropping a view never deletes table data.
  • Views help with security, simpler queries and logical data independence.

2.17 Triggers

  • A trigger is SQL that runs automatically on INSERT, UPDATE or DELETE on a table.
  • It follows the event-condition-action model.
  • BEFORE triggers can change NEW or stop the change. AFTER triggers react to a change already made.
  • MySQL triggers are row-level: FOR EACH ROW. They run once per changed row.
  • INSERT has only NEW, DELETE has only OLD, and UPDATE has both.
  • SIGNAL SQLSTATE '45000' raises an error and makes the whole statement fail.
  • Use DELIMITER in the mysql client for a trigger body with BEGIN ... END.
  • Keep triggers short. Prefer a CHECK constraint when it is enough.
