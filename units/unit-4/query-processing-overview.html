Query Processing Overview

When you send an SQL query, the DBMS checks it, turns it into relational algebra, picks a good plan and then runs that plan. This page follows a query through each step.

The three steps of query processing

Definition

Query processing is the set of activities that turn a high-level query (such as SQL) into steps that the system can run on the stored data. It also runs these steps to get the result.

  1. Parsing and translation. The parser checks the syntax of the query (is it written correctly?) and checks that the relations and attributes in it exist. The query is then translated into an internal form, usually a relational algebra expression.
  2. Optimization. The optimizer considers the many equivalent ways to run the query and estimates the cost of each. It uses statistics from the data dictionary, such as the number of tuples in each relation. It picks the plan with the lowest estimated cost.
  3. Evaluation. The query execution engine takes the chosen plan, runs it and returns the answer.

Example: what the parser rejects

SELECT name FORM student; is rejected for its syntax, because FORM is not a keyword. SELECT name FROM studnet; has the right syntax, but it is rejected because no relation is called studnet.

Evaluation plans

One SQL query can be written as several equivalent relational algebra expressions. Take this query from the class notes:

SQL 
SELECT balance
FROM account
WHERE balance < 1000;

It can be translated into either of these expressions. Both give the same result.

  1. σbalance < 1000(Πbalance(account))
  2. Πbalance(σbalance < 1000(account))

An expression alone does not say how to run each operation. For example, σbalance < 1000 could read the whole file, or it could use an index on balance.

Definitions

An evaluation primitive is a relational algebra operation together with instructions on how to evaluate it, for example “σ using the index on balance”.

A query evaluation plan (query execution plan) is a sequence of evaluation primitives that together evaluate a query. It is often drawn as a tree.

Each plan has a cost. The job of the optimizer (topic 4.11) is to find the plan with the lowest cost.

The results of one operation can be passed to the next in two ways. In materialization, each result is written to a temporary relation on disk and then read by the next operation. In pipelining, each tuple is passed to the next operation as soon as it is produced, so no temporary relation is written.

Measures of query cost

The cost of a query is the time it takes. Many things add to it:

  • Disk access: reading and writing blocks.
  • CPU time to run the query in memory.
  • Communication cost in distributed and parallel databases.

Disk access is much slower than work in memory, so it is usually the main cost. It is also easy to estimate. So the cost of a plan is measured by two numbers:

  • b: the number of block transfers (blocks read or written), each taking tT seconds.
  • S: the number of seeks (moving the disk head to a new place), each taking tS seconds.
Formula

Query cost = b × tT + S × tS

For example, a hard disk might have tS = 4 milliseconds and tT = 0.1 milliseconds for a 4 KB block. One seek costs as much as 40 block transfers, so reading blocks one after another is much cheaper than jumping around the disk.

Writing a block costs more than reading it, because the system reads the block back to check that the write worked. CPU time is usually left out of the estimate because it is small and hard to measure.

Algorithms for selection

A selection (σ) is done with a file scan: a search that finds the records that meet the condition. In the formulas, br is the number of blocks of relation r.

A1: Linear search

Read every block of the file and test every record against the condition.

  • Cost: br block transfers + 1 seek.
  • If the condition is an equality on a key, the search can stop at the first match. On average this costs br / 2 block transfers + 1 seek.
  • Works for any condition, on any file, sorted or not, with or without an index.

A2: Binary search

Possible when the condition is an equality on the attribute on which the file is sorted, and the blocks are stored one after another.

  • Cost to find the first matching record: ⌈log2(br)⌉ × (tT + tS). Each step of the binary search reads one block at a new place.
  • If several records match, add the transfer cost of the blocks that hold them.
Example

A sorted STUDENT file has br = 1,000 blocks. Linear search reads up to 1,000 blocks. Binary search reads ⌈log2 1000⌉ = 10 blocks.

Selection using an index

With a B+ tree index of height hi, an equality search on a key reads hi index blocks and one data block. The cost is about (hi + 1) × (tT + tS). This is often the cheapest choice (topic 4.6).

External sorting

Queries with ORDER BY, and some join methods, need sorted data. If a relation fits in memory, any normal sort works. Large relations do not fit, so the DBMS uses external sorting.

Definition

External merge sort sorts data that is too large for memory in two stages. First, it loads one memory-full of records at a time, sorts it and writes it out as a sorted run. Second, it merges the runs, again and again, until one sorted run is left.

For example, 10,000 records must be sorted, and memory holds 500 records. Stage 1 makes 20 sorted runs of 500 records each. Stage 2 merges the runs into longer and longer runs.

Example from the class notes: two-way merge sort with M = 3

Sort 20, 47, 15, 8, 9, 4, 40, 30, 12, 17, 11, 56, 28, 35, with memory for 3 records.

Each pass halves the number of runs. With N records and runs of M records, a two-way merge needs about ⌈log2(N / M)⌉ merge passes. A multiway merge merges more than two runs at a time, so it needs fewer passes.

Algorithms for joins

The join is the most costly common operation. In the formulas, r is the outer relation and s is the inner relation. nr is the number of tuples of r, and br and bs are their numbers of blocks.

Join algorithms and their costs (worst case, with little memory)
AlgorithmHow it worksBlock transfersSeeks
Nested-loop joinFor each tuple of r, read all of s and test each pair.nr × bs + brnr + br
Block nested-loop joinFor each block of r, read all of s and test the pairs block by block.br × bs + br2 × br
Indexed nested-loop joinFor each tuple of r, use an index on s to find the matching tuples.br × (tT + tS) + nr × c, where c is the cost of one index lookup
Merge joinSort both relations on the join attribute, then read them together once, like merging two sorted lists. Only for equi-joins and natural joins.br + bs (plus the cost of sorting)⌈br/bb⌉ + ⌈bs/bb⌉
Hash joinUse a hash function on the join attribute to split both relations into partitions; join each pair of matching partitions in memory.3(br + bs) + 4nh2(⌈br/bb⌉ + ⌈bs/bb⌉)

Here bb is the number of blocks read at a time (the buffer size), and nh is the number of partitions. If the smaller relation fits entirely in memory, nested-loop, block nested-loop and hash joins all drop to br + bs block transfers.

Worked example from the class notes: CUSTOMER ⋈ ORDERS

CUSTOMER has 10,000 tuples in 400 blocks. ORDERS has 5,000 tuples in 100 blocks. Join them on CName with a nested-loop join.

  • ORDERS as the outer relation: 5,000 × 400 + 100 = 2,000,100 block transfers and 5,000 + 100 = 5,100 seeks.
  • CUSTOMER as the outer relation: 10,000 × 100 + 400 = 1,000,400 block transfers and 10,000 + 400 = 10,400 seeks.
  • Block nested-loop join, ORDERS outer: 100 × 400 + 100 = 40,100 block transfers and 2 × 100 = 200 seeks.
  • ORDERS fits in memory: 400 + 100 = 500 block transfers.

The same join can cost 500 or 2 million block transfers. Choosing well is the job of the optimizer.

Seeing the plan in MySQL

MySQL shows the plan it chose with EXPLAIN. EXPLAIN ANALYZE also runs the query and shows the real time of each step.

SQL (MySQL 8.4) 
EXPLAIN FORMAT=TREE
SELECT name
FROM student
WHERE marks < 50;

EXPLAIN ANALYZE
SELECT name
FROM student
WHERE marks < 50;

In the output, “Table scan” means a linear search, and “Index range scan” means the plan uses an index.

In real life

Like booking a train journey

To travel from Salem to Delhi, there are many routes. You check that the stations exist (parsing), compare routes by time and cost (optimization), then travel on the chosen one (evaluation).

Online shopping search

When you search for “red shoes under ₹1,000”, the shop's database runs a query with a selection and a join. A good plan returns the page in a fraction of a second; a poor plan could take minutes.

Key points

  • Query processing has three steps: parsing and translation, optimization, and evaluation.
  • The parser checks syntax and names, and translates SQL into relational algebra.
  • A query evaluation plan is relational algebra annotated with how to evaluate each operation.
  • Query cost = b × tT + S × tS: block transfers and seeks, because disk access dominates.
  • Linear search costs br transfers + 1 seek; binary search costs ⌈log2(br)⌉ × (tT + tS).
  • External merge sort makes sorted runs that fit in memory, then merges them.
  • Join algorithms: nested-loop, block nested-loop, indexed nested-loop, merge join and hash join; the choice depends on cost.
