Indexing and Hashing

An index lets the DBMS jump straight to the records it needs, instead of reading the whole file. There are two basic kinds: ordered indices and hash indices.

Why we need an index

A library has 50,000 books. To find a book by its title, you do not walk past every shelf. You look in the catalog, which is sorted by title and tells you the shelf number.

A database works the same way. Without help, a query such as WHERE roll_no = 126 may read every block of the STUDENT file. An index is the catalog that tells the DBMS which block to read.

Definition

An index is an extra data structure that helps the DBMS find the records with a given value quickly. It is stored on disk, separate from the data file.

Basic terms

Search key
The attribute or set of attributes used to look up records in a file, for example RollNo or (Dept, Year). A search key is not the same as a primary key or candidate key: any attribute can be a search key.
Index entry (index record)
One entry of the index. It holds a search-key value and one or more pointers to the records with that value. A pointer gives the block and the position of the record inside the block.
Index file
The file that holds the index entries. It is usually much smaller than the data file, because each entry is short.

Two kinds of index

  1. Ordered indices keep the search-key values in sorted order, like the index at the back of a book. Topic 4.5 (ordered indices), topic 4.6 (B+ trees) and topic 4.7 (B trees) describe them.
  2. Hash indices spread the search-key values across buckets. A hash function computes the bucket for each value. Topic 4.8 (static hashing) and topic 4.9 (dynamic hashing) describe them.

A file can have several indices, each on a different search key. For example, STUDENT can have one index on RollNo and another on Name.

How to evaluate an index

No single technique is best for every use. Each indexing or hashing technique is judged on five factors.

The five factors used to evaluate an index
FactorQuestion it answers
Access typesWhich kinds of search does it support well? For example, finding one exact value (RollNo = 126), or a range of values (marks between 60 and 80).
Access timeHow long does it take to find one record or a set of records?
Insertion timeHow long does it take to insert a new record, including finding its place and updating the index?
Deletion timeHow long does it take to delete a record, including updating the index?
Space overheadHow much extra disk space does the index use?
Exam tip

Remember the five factors as “two kinds of access, two kinds of change, one space”: access types and access time, insertion time and deletion time, and space overhead.

Why not index every attribute?

Indices make queries faster, so why not build one on every attribute? Because every index has a cost.

  • Every insert and delete must also update every index on the file. This takes extra CPU time and disk writes.
  • An update of an indexed attribute must also change the index.
  • Each index takes extra disk space.
  • A query with conditions on several attributes is often fast enough when only some of them have an index.

So a good design builds indices only on the attributes that queries search often.

Indexing compared with hashing

Ordered indexing compared with hashing
Ordered indexingHashing
How it finds a recordSearches the sorted search-key values (for example, goes down a B+ tree).Computes a hash function on the value to get the bucket.
Exact value (RollNo = 126)A few disk reads (the height of the tree).About one disk read.
Range (RollNo 110 to 125)Fast: find 110, then read on in order.Slow: the values are scattered over all buckets.
Sorted output (ORDER BY)Free, because the keys are already in order.Needs a separate sort.
GrowthGrows smoothly (B+ tree).Static hashing overflows; dynamic hashing is needed.

Because range queries are common, most databases use ordered indices (B+ trees) by default. Hashing is used when almost every query looks for one exact value.

Common mistake

A hash index cannot answer WHERE marks > 60 quickly. The hash of 61 tells you nothing about where 62 is. Only an ordered index can follow the keys in order.

Indices in MySQL

In MySQL, CREATE INDEX builds an ordered (B+ tree) index by default. The MEMORY storage engine can also build a hash index.

SQL (MySQL 8.4) 
-- An ordered index on name (InnoDB uses a B+ tree).
CREATE INDEX idx_name ON student (name);

-- A hash index, in a table kept in memory.
CREATE TABLE session_cache (
  token   CHAR(32),
  user_id INT,
  INDEX USING HASH (token)
) ENGINE = MEMORY;

-- See the indices of a table.
SHOW INDEX FROM student;

InnoDB tables accept USING HASH in the syntax but still build a B+ tree, so the MEMORY table is used here.

In real life

Mobile recharge

A recharge app looks up a customer by the exact 10-digit mobile number, never by a range of numbers. A hash index on the mobile number can find the record in about one read.

Online shopping filters

When you filter phones by “price from ₹10,000 to ₹15,000”, the shop needs a range query. An ordered index on price finds ₹10,000 and reads on in order.

Key points

  • An index is an extra structure that finds records quickly, like the catalog of a library.
  • A search key is the attribute (or set of attributes) used to look up records. Any attribute can be a search key.
  • An index entry holds a search-key value and pointers to the records with that value.
  • There are two basic kinds: ordered indices (sorted values) and hash indices (values spread over buckets).
  • Indices are evaluated on access types, access time, insertion time, deletion time and space overhead.
  • Every index slows down inserts, deletes and updates, and uses space, so only useful indices are built.
  • Hashing is best for exact-value lookups; ordered indices also handle range queries and sorted output.
