Query Optimization using Heuristics and Cost Estimation

One SQL query can be run in many ways, and some ways are thousands of times faster than others. The optimizer uses rules (heuristics) and cost estimates to pick a fast way.

What is query optimization?

Definition

Query optimization is the process of choosing the most efficient query evaluation plan from the many equivalent plans for a query.

SQL says what data you want. It does not say how to get it. So the system must decide the order of the operations and the algorithm for each one. The user should not have to write the query in the “best” form.

Optimization is needed because equivalent plans can differ in cost a lot. One plan might read a few blocks, and another plan for the same query might read millions of blocks.

There are two main approaches:

  • Heuristic optimization uses fixed rules that usually make a query cheaper.
  • Cost-based optimization estimates the cost of each plan and picks the cheapest.

Most real systems use both: rules first, to cut down the number of choices, and then cost estimates to choose among the rest.

Query trees

Definition

A query tree is a tree that shows a relational algebra expression. The leaves are the relations. The internal nodes are operations such as σ (selection), π (projection), × (Cartesian product) and ⋈ (join). Results flow upward, and the root gives the final answer.

The parser first builds a canonical (initial) query tree straight from the SQL:

  • the FROM clause becomes Cartesian products of the relations;
  • the WHERE clause becomes one selection on top of them;
  • the SELECT clause becomes a projection at the root.

This tree is correct, but it is slow, because it builds every combination of rows before it filters them. Optimization changes the shape of the tree without changing the answer.

Example: the class notes query

Find the names of customers who have an account at a branch in Pune. Two equivalent expressions are:

  1. Πcname(σcity = “Pune”(BRANCH ⋈ ACCOUNT ⋈ CUSTOMER))
  2. Πcname(σcity = “Pune”(BRANCH) ⋈ (ACCOUNT ⋈ CUSTOMER))

Tree (a) joins all the branches with all the accounts and customers, and selects Pune at the end. Tree (b) first selects the Pune branches, so the join works on far fewer tuples. Tree (b) is much faster. Choose “Class notes” in the widget below to see both trees and their sizes.

Equivalence rules

Two expressions are equivalent if they give the same set of tuples on every legal database. An equivalence rule says that one form of an expression can be replaced by another form. The optimizer uses these rules to rewrite a query tree. The main rules are:

Main equivalence rules (E, E1, E2 are expressions; θ is a condition)
No.RuleIn symbols
1Cascade of σ. A selection with AND can be split into a sequence of selections.σθ1 ∧ θ2(E) = σθ1(σθ2(E))
2σ is commutative. Selections can be done in any order.σθ1(σθ2(E)) = σθ2(σθ1(E))
3Cascade of π. Only the last (outer) projection matters.ΠL1(ΠL2(E)) = ΠL1(E), when L1 ⊆ L2
4σ with × is a join.σθ(E1 × E2) = E1 ⋈θ E2
5Joins are commutative.E1 ⋈ E2 = E2 ⋈ E1
6Natural joins are associative.(E1 ⋈ E2) ⋈ E3 = E1 ⋈ (E2 ⋈ E3)
7σ distributes over a join when θ uses only attributes of E1.σθ(E1 ⋈ E2) = σθ(E1) ⋈ E2
8π distributes over a join when the join attributes are kept.ΠL1 ∪ L2(E1 ⋈ E2) = ΠL1(E1) ⋈ ΠL2(E2)

Rules for set operations also exist. For example, ∪ and ∩ are commutative and associative, and σ distributes over ∪, ∩ and −.

Example: pushing a selection down (rule 7)

σdept = “CSE”(STUDENT ⋈ MARKS) = σdept = “CSE”(STUDENT) ⋈ MARKS

dept is an attribute of STUDENT only, so the selection can be done on STUDENT before the join. The join then works on CSE students only.

Heuristic optimization

Definition

A heuristic is a rule that leads to the least cost in most cases. Heuristic optimization changes the query tree using a set of such rules, without computing the cost of each plan.

The heuristic rules

  1. Perform selections as early as possible. This reduces the number of tuples that later operations must handle.
  2. Perform projections as early as possible. This reduces the number of attributes, so each tuple is smaller.
  3. Perform the most restrictive selections and joins first. “Most restrictive” means the one that gives the fewest tuples. Do these before other similar operations.
  4. Avoid Cartesian products. Replace a Cartesian product followed by a selection with a join.

Steps in heuristic optimization

The class notes give three steps:

  1. The scanner and parser build the initial query representation (the canonical query tree).
  2. The representation is improved using the heuristic rules.
  3. The query execution plan is built from the improved tree.

Step 2 is done in this order (Elmasri and Navathe):

  1. Split each selection with AND into a cascade of single selections (rule 1).
  2. Move each selection down the tree as far as it can go (rules 2 and 7).
  3. Rearrange the leaves so that the most restrictive selections and joins are done first (rules 5 and 6).
  4. Combine each Cartesian product and the selection above it into a join (rule 4).
  5. Split projections and move them down the tree, keeping only the attributes that later steps need (rules 3 and 8).
  6. Find the subtrees that can be run as one pipeline.
Worked example: CSE students who take the DBMS course

STUDENT has 5,000 rows, ENROLL has 40,000 rows and COURSE has 200 rows. The query is:

SQL 
SELECT name
FROM student, enroll, course
WHERE student.roll_no = enroll.roll_no
  AND enroll.course_id = course.course_id
  AND course.title = 'DBMS'
  AND student.dept = 'CSE';

Common mistake

Do not move a selection below a join if the condition uses attributes from both sides. For example, S.roll_no = E.roll_no must stay at the join, because it needs a row from each relation.

Cost-based optimization

Definition

Cost-based optimization creates many equivalent evaluation plans, estimates the cost of each plan from statistics about the data, and picks the plan with the least cost.

The class notes describe it in three steps:

  1. The optimizer looks at all the possible ways (scenarios) in which the query can be run.
  2. Each scenario is given a cost, which shows how efficiently the query can be run that way.
  3. The optimizer picks the scenario with the least cost and runs the query using it.

The scope of optimization is usually one query block (one SELECT … FROM … WHERE). Optimizing a query with several blocks together is called global query optimization.

Cost components

  • Access cost to secondary storage: reading and writing disk blocks. This is usually the largest part.
  • Disk storage cost: storing intermediate results on disk.
  • Computation cost: CPU work such as comparing, sorting and merging.
  • Memory usage cost: the number of memory buffers needed.
  • Communication cost: sending data between sites in a distributed database.

As in the query processing topic, we measure cost mainly by the number of block transfers (tT each) and seeks (tS each).

Catalog statistics and size estimation

The optimizer cannot run every plan to see which is fastest. It estimates. The estimates use statistics kept in the DBMS catalog (data dictionary).

Statistics stored for a relation r (Silberschatz notation)
SymbolMeaning
nrNumber of tuples in r
brNumber of blocks that hold the tuples of r
lrSize of one tuple of r, in bytes
frBlocking factor: the number of tuples that fit in one block
V(A, r)Number of distinct values of attribute A in r

The catalog also stores the file organization (heap, sorted or hashed), the indices on each file and the number of levels of each multilevel index. These are all listed in the class notes.

If the tuples of r are stored together, br = ⌈nr / fr⌉.

Selectivity

Definition

The selectivity of a condition is the fraction of tuples that satisfy it. A condition with low selectivity keeps few tuples, so it is very “restrictive”.

Estimating the number of result tuples (assuming values are spread evenly)

Example: estimating sizes

STUDENT has nr = 5,000 and V(dept, STUDENT) = 8. COURSE has 200 tuples with 200 different titles. ENROLL has 40,000 tuples.

  • σdept = 'CSE'(STUDENT): 5,000 / 8 = 625 tuples.
  • σtitle = 'DBMS'(COURSE): 200 / 200 = 1 tuple.
  • That 1 course ⋈ ENROLL: course_id is the key of COURSE, so each course has about 40,000 / 200 = 200 enrollments.
  • Those 200 enrollments ⋈ the 625 CSE students: 200 × 625 / 5,000 = 25 tuples.

These are the numbers the optimizer uses to see that COURSE should be joined first.

Histograms

The formulas above assume that values are spread evenly. Real data is often uneven. So the class notes say that an RDBMS stores histograms for the most important attributes. A histogram divides the values into ranges (buckets) and stores the number of tuples in each range.

Histogram on STUDENT.marks (5,000 students)
Marks0 to 2021 to 4041 to 6061 to 8081 to 100
Students2008001,8001,600600

For σmarks > 80(STUDENT), the even-spread formula gives 5,000 × 20 / 100 = 1,000 tuples. The histogram gives 600, which is much closer to the truth.

Choosing a plan by cost

Cost estimates let the optimizer choose an algorithm for each operation and an order for the joins.

Worked example: is the index worth using?

STUDENT has 5,000 tuples, 50 per block, so br = 100. A secondary B+ tree index on dept has height 2. Take tT = 0.1 ms and tS = 4 ms. The query is σdept = 'CSE'(STUDENT), with 625 matching tuples (estimated above).

Two plans for the same selection
PlanCost formulaEstimated time
Linear search (read every block)br × tT + tS = 100 × 0.1 + 414 ms
Secondary index on dept(h + n) × (tT + tS) = (2 + 625) × 4.1, because each match may be in a different blockabout 2,571 ms

The optimizer picks the linear search. A rule like “always use an index” would pick the slow plan here. For σroll_no = 1234(STUDENT), only one tuple matches, so the index costs (2 + 1) × 4.1 ≈ 12 ms and wins.

Join order

The number of possible join orders grows very fast. For n relations there are (2(n − 1))! / (n − 1)! different join orders.

Number of join orders
Relations35710
Join orders121,680665,280more than 17.6 billion

So optimizers do not try every order. They use dynamic programming: the best plan for each smaller set of relations is found once and reused. Many systems also consider only left-deep join trees, where the right input of every join is a stored relation. Left-deep trees work well with pipelining and indexed nested-loop joins.

Tip

Many systems use heuristics to reduce the number of choices, and then use cost estimates to choose among the plans that are left. Some systems use only heuristics.

Statistics and plans in MySQL

MySQL has a cost-based optimizer. ANALYZE TABLE updates the statistics that it uses, and it can also build a histogram on a column. EXPLAIN shows the chosen plan with its estimated cost and row counts.

SQL (MySQL 8.4) 
-- Refresh the statistics for the table
ANALYZE TABLE student;

-- Build a histogram on marks with 5 buckets
ANALYZE TABLE student UPDATE HISTOGRAM ON marks WITH 5 BUCKETS;

-- See the plan, with estimated cost and rows
EXPLAIN FORMAT=TREE
SELECT name
FROM student
WHERE marks > 80;

In the output, cost= is the optimizer's cost estimate and rows= is its estimate of the number of rows. If these estimates are far from the real numbers, refresh the statistics.

In real life

Maps and route planning

A maps app does not try every possible road. It uses rules (stay on main roads) and estimates (traffic and distance) to choose a fast route. A query optimizer does the same with rules and cost estimates.

Slow reports after a data load

When a college loads a new semester's marks, an old report can suddenly become slow. The statistics still describe the old data, so the optimizer picks a poor plan. Running ANALYZE TABLE often fixes it.

Shopping filters

On a shopping site, “brand = X” may match 50 products while “in stock” matches a million. The optimizer applies the brand filter first, because it is the most restrictive.

Key points

  • Query optimization chooses the most efficient plan from many equivalent plans.
  • A query tree shows relations as leaves and operations as internal nodes; the canonical tree is correct but slow.
  • Equivalence rules (cascade of σ, pushing σ and π through joins, join commutativity and associativity) let the optimizer rewrite a tree safely.
  • Heuristic rules: perform selections early, perform projections early, do the most restrictive operations first, and replace × followed by σ with ⋈.
  • Cost-based optimization estimates the cost of each plan from catalog statistics (nr, br, V(A, r), histograms) and picks the cheapest.
  • Selectivity is the fraction of tuples that satisfy a condition; σA = v(r) is estimated as nr / V(A, r).
  • Heuristics are fast but may miss the best plan; cost-based optimization is slower but usually better.
