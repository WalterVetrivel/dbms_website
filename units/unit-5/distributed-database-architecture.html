Distributed Databases: Architecture

A distributed database keeps its data at several sites joined by a network. Users still see one database. This page shows how the sites work together and how the data is split and copied.

What is a distributed database?

Think of a bank with branches in Salem, Chennai and Coimbatore. Each branch has its own computer. The Salem computer stores the accounts of Salem customers. Still, a customer can check their balance from any branch. The bank's data is spread over many computers, but it works as one database.

Definition

A distributed database is a collection of related data stored at several sites. The sites are connected by a communication network. Each site has its own database system and can work on its own. To the user, all the sites together look like one database.

The software that manages a distributed database is called a distributed database management system (DDBMS).

A site (also called a node) is one computer, or a group of computers, in one place. The sites are loosely coupled: they share no memory or disks. They talk to each other only by sending messages over the network.

Each site handles two kinds of work:

  • A local transaction uses data only at the site where it starts.
  • A global transaction uses data at more than one site. See Transaction Processing.

Architecture

The figure shows the general architecture. Every site has its own local database and local DBMS. The sites are joined by a network.

Parts of the architecture

  • Sites: each site has users, a local DBMS and a local database.
  • Communication network: carries queries, results and control messages between sites.
  • Global schema and catalog: describe all the data of the whole system, and record which site stores which part. The DDBMS uses the catalog to find data.
  • Transaction manager and transaction coordinator: each site has both. They run transactions and keep them atomic across sites (see Transaction Processing).

How a request is answered

  1. A user at site Si asks for some data.
  2. The DBMS at Si first looks in its local database.
  3. If the data is not there, it uses the catalog and sends the request over the network to the site that has it, say Sj.
  4. Site Sj runs the request on its local database.
  5. Sj sends the result back to Si, and Si shows it to the user.

Data storage: replication and fragmentation

There are two ways to store a relation r in a distributed database. They can also be used together.

  • Replication: keep copies of r at several sites.
  • Fragmentation: split r into parts called fragments, and store each fragment at a different site.

Deciding which fragment or copy goes to which site is called allocation.

Replication

Definition

Data replication means storing a copy (a replica) of a relation or a fragment at two or more sites.

  • Full replication: every site has a copy of the whole database.
  • Partial replication: only some fragments are copied, to some sites.
  • No replication: each fragment is stored at exactly one site.

Merits (advantages)

  • Availability: if one site fails, a copy at another site can be used.
  • Parallelism: different sites can answer queries on r at the same time.
  • Less data transfer: r is often available locally, so reads are fast.

Demerits (disadvantages)

  • Costly updates: every copy must be changed when r changes.
  • Complex concurrency control: the copies must not differ when many transactions run together.
  • Copies use more disk space.

Fragmentation

Definition

Data fragmentation divides a relation r into fragments r1, r2, …, rn. The fragments together hold enough information to rebuild r.

1. Horizontal fragmentation (split by rows)

Each tuple (row) of r goes to a fragment. A fragment is defined with a selection (σ). To rebuild r, take the union of the fragments: r = r1 ∪ r2 ∪ … ∪ rn.

Example

Store each student at the site of their city:

  • Salem site: F1 = σCity='Salem'(Student), which holds rows 101 and 104.
  • Chennai site: F2 = σCity='Chennai'(Student), which holds rows 102 and 106.
  • Coimbatore site: F3 = σCity='Coimbatore'(Student), which holds rows 103 and 105.

In SQL, F1 is SELECT * FROM Student WHERE City = 'Salem';. Student = F1 ∪ F2 ∪ F3.

2. Vertical fragmentation (split by columns)

The schema of r is split into groups of attributes. A fragment is defined with a projection (π). Every fragment must keep the primary key (or a tuple id). To rebuild r, take the natural join: r = r1 ⋈ r2 ⋈ … ⋈ rn.

Example
  • College office: F1 = πRollNo, Name, Dept(Student)
  • Exam cell: F2 = πRollNo, City, Marks(Student)

In SQL, F1 is SELECT RollNo, Name, Dept FROM Student;. Student = F1 ⋈ F2, joined on RollNo.

Common mistake

A vertical fragment without the key cannot be joined back. If F2 kept only City and Marks, we could not tell which marks belong to which student.

3. Mixed (hybrid) fragmentation

First split by columns, then split one of the parts again by rows (or the other way round). To rebuild r, use union and join in the reverse order.

Example
  • F1 = πRollNo, Name, Dept(Student)
  • F2 = σCity='Chennai'(πRollNo, City, Marks(Student))
  • F3 = σCity≠'Chennai'(πRollNo, City, Marks(Student))

Student = F1 ⋈ (F2 ∪ F3).

Rules for correct fragmentation

  1. Completeness: every row (or column) of r is in at least one fragment, so no data is lost.
  2. Reconstruction: r can be rebuilt from its fragments with union or join.
  3. Disjointness: a row is in only one horizontal fragment; only the key repeats in vertical fragments.
Exam tip

For a “fragmentation with example” question, draw one small table, show each fragment with its σ or π expression, and write the rebuild formula: ∪ for horizontal, ⋈ for vertical.

Transparency

Transparency means the user does not need to know how the data is spread. The user writes a query on Student as if it were at one site.

  • Fragmentation transparency: the user does not know that Student is split into fragments.
  • Replication transparency: the user does not know how many copies exist or which copy is used.
  • Location transparency: the user does not know at which site the data is stored.
  • Naming transparency: each data item has one unique name, wherever it is stored.

Merits and demerits (advantages and disadvantages)

Merits (advantages)

  • Reliability and availability: when one site fails, the other sites keep working.
  • Faster local access: data is stored near the people who use it most.
  • Parallel processing: several sites can work on one request at the same time.
  • Easy growth: add a new site when the business opens a new branch.
  • Sharing and local control: sites share data, but each site still controls its own data (local autonomy).

Demerits (disadvantages)

  • Complexity: the system is harder to design, manage and control.
  • Security: many sites and the network must all be protected.
  • Harder transactions: commit, concurrency control and deadlock handling must work across sites.
  • Cost: more hardware, software and network links are needed.
  • Lack of standards: sites with different software are hard to join.

In real life

Bank branches

A bank stores each customer's account at their home branch (horizontal fragmentation). The head office keeps a copy of all accounts for reports (replication). A customer can still use any ATM in India.

Railway reservation

Train booking data is copied to servers in several cities. If one data center has a power cut, the booking site keeps working from another copy.

Key points

  • A distributed database stores related data at several sites joined by a network, but looks like one database to users.
  • Each site has its own local DBMS and database; a DDBMS manages the whole system.
  • A request that cannot be answered locally is sent to the site that holds the data.
  • Replication keeps copies at several sites: better availability, but costly updates.
  • Horizontal fragmentation splits rows with σ and is rebuilt with union (∪).
  • Vertical fragmentation splits columns with π, keeps the key in every fragment, and is rebuilt with join (⋈).
  • Mixed fragmentation uses both splits.
  • Transparency hides fragmentation, replication and location from the user.
