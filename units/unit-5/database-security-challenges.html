Challenges in Database Security

Access control, SQL injection defenses and encryption solve many problems, but database security is never finished. This page explains the main challenges that remain, and what organizations do about them.

Why security is never finished

Attackers keep finding new tricks. Data moves to the cloud and to mobile apps. Laws on personal data get stricter. So the tools from topics 5.10 to 5.14 are needed, but they are not enough on their own.

Elmasri and Navathe name three main challenges: data quality, intellectual property rights and database survivability. To these we add privacy and some newer challenges.

Data quality

Users need to know that data is correct, complete and from a trusted source. Wrong data is a security problem too. Bad decisions made on it can harm people.

  • Quality checks: constraints, validation rules and regular audits catch wrong or missing values.
  • Quality labels: data can carry a note about where it came from (its source or provenance) and how reliable it is.
  • Cleaning and matching: duplicate and conflicting records are found and fixed.
Example

A scholarship list is built from two databases. One spells a student “Mohamed Iqbal” and the other “Mohammed Ikbal”. Without matching, the student is either paid twice or left out.

Intellectual property rights

A database can be valuable property, such as a map database, a product catalog or a question bank. Once it is shared or sold, copies can leak. The owner needs a way to prove the data is theirs. They also need a way to find who leaked a copy.

  • Watermarking: hidden, harmless changes are added to the data, such as tiny changes in the last digit of some numbers. The pattern proves ownership, but does not spoil the data.
  • Fingerprinting: each buyer gets a copy with a different watermark. If a copy leaks, its fingerprint shows which buyer it came from.
  • Licenses and contracts: legal terms say how the data may be used.

Database survivability

Definition

Database survivability is the ability of a database to keep doing its main work, perhaps at a lower level, during an attack, and to recover fully afterwards.

A survivable system follows five steps.

  1. Confinement: stop the damage from spreading. Block the attacker's account or cut off the affected part.
  2. Damage assessment: find out which data and functions were harmed.
  3. Reconfiguration: rearrange the system so that its main work goes on, perhaps in a reduced mode.
  4. Repair: restore the damaged data and fix the broken functions.
  5. Fault treatment: find the weakness that was used and fix it so the attack cannot happen again.

The tools from Unit III help here. The log and backups are used to undo bad transactions and bring the data back to a correct state.

Worked example: surviving a ransomware attack

At 2 a.m., ransomware encrypts the main MySQL server of a college. The attackers ask for money. Follow the five steps.

The five survivability steps in a ransomware attack
StepWhat the college does
ConfinementDisconnect the server from the network and disable the stolen admin account, so the replica and backups are not touched.
Damage assessmentFind that the main server's files are encrypted, but the read-only replica in another building and last night's offline backup are safe.
ReconfigurationPoint the results website to the replica in read-only mode. Students can still see results; changes wait.
RepairBuild a clean server, restore last night's backup and replay the binary log up to just before 2 a.m.
Fault treatmentFind that the attacker used a leaked admin password. Turn on two-factor login, change all passwords and patch the server.
Common mistake

A backup that stays connected to the same network can be encrypted too. At least one backup should be offline or unchangeable, and restoring it should be tested often.

Privacy

Privacy is a person's right to decide how data about them is collected and used. Security keeps outsiders away from data. Privacy also limits what the organization itself may do with it.

  • Laws: India's Digital Personal Data Protection Act, 2023 and Europe's GDPR require consent, a clear purpose and safe handling of personal data.
  • Collect less: store only the data the purpose needs. A canteen app does not need a student's Aadhaar number.
  • Anonymize before sharing: remove or blur details that identify a person, before data is used for research or reports.

Removing names is not enough. Other columns together can still point to one person. This is the same danger as the inference attack in topic 5.10.

Worked example: making data anonymous

A hospital shares this table for research. Names were removed.

Your 23-year-old neighbor lives in PIN code 638056. Only one row matches, so you now know the neighbor has diabetes. Age and PIN code together act like a name. Such columns are called quasi-identifiers.

Fix it by generalizing them: ages become ranges, and the last digits of PIN codes are hidden.

Now each combination of age range and PIN code fits at least 2 people. This is called k-anonymity with k = 2. Real data uses a larger k, such as 5 or 10. The cost is that the data becomes less exact, so research results are rougher.

Newer challenges

Cloud databases

Data sits on someone else's servers. A wrong setting, such as a storage bucket left public, can expose millions of records. Security is shared between the provider and the customer.

Insider threats

Staff with real access misuse it or are tricked into sharing passwords. Least privilege, audit logs and separation of duties reduce the risk.

Ransomware

Attackers encrypt the database and ask for money. Offline backups and survivability plans are the main defense.

NoSQL and big data

Some NoSQL systems once shipped with no password by default, and many were found open on the internet. Large, spread-out systems are harder to protect.

Mobile and IoT devices

Phones and sensors hold copies of data and connect from anywhere. Each device is one more door to protect.

AI and data

AI tools trained on or connected to databases can leak private data in their answers. Access rules must cover these tools too.

Through all of this, the balance between security and ease of use remains a challenge. Rules that are too strict make people find unsafe shortcuts.

Exam tip

The 16-mark question pairs encryption and PKI (topic 5.14) with challenges. For the challenges half, explain data quality, intellectual property and the five survivability steps. Then add privacy and two newer challenges.

Key points

  • Database security is never finished, because attacks, systems and laws keep changing.
  • Data quality: users must be able to trust that data is right, complete and from a known source.
  • Intellectual property: hidden marks in the data (watermarks and fingerprints) prove who owns it and trace leaks.
  • Survivability: confinement, damage assessment, reconfiguration, repair and fault treatment.
  • Privacy: removing names is not enough. Blur ages, PIN codes and similar details so each person looks like several others (k-anonymity).
  • Newer challenges include cloud settings, insiders, ransomware, NoSQL defaults, devices and AI.
