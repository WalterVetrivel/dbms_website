NoSQL Databases: Introduction

Relational databases store data in tables with a fixed schema. NoSQL databases store data in other shapes, such as documents and key-value pairs. This page explains why NoSQL is needed and how it differs from a relational database.

What is NoSQL?

Definition

A NoSQL database (“not only SQL”) is a non-relational database. It stores data in shapes other than tables, such as documents, key-value pairs, wide columns or graphs. Most NoSQL databases have a flexible schema and are built to run on many servers.

The name does not mean “no SQL at all”. It means that SQL tables are not the only way to store data. Some NoSQL systems even offer a query language that looks like SQL.

Think of a cupboard. A relational database is like a cupboard with fixed boxes of the same size. Every item must fit a box. A NoSQL database is like a cupboard with bags of any size. You can put in items of different shapes, and you can add more cupboards when you run out of room.

Why NoSQL is needed

Relational databases work well for most business data. But modern web and mobile apps brought new problems. NoSQL databases were built to solve them.

  1. Big data. Apps such as social media store billions of posts, likes and messages. This is too much for one server.
  2. Many kinds of data. Data can be structured (fixed fields, like a mark sheet), semi-structured (fields that change, like JSON from an app) or unstructured (text, images, logs). Tables suit only the first kind well.
  3. High availability. A shopping app must keep working all day, every day, even when some servers fail.
  4. Easy scaling. When users grow, the system should grow by adding cheap servers. This is called scaling out.
  5. Fast changes. App teams add new fields often. Changing a fixed schema in a large table is slow and risky.

Scaling up and scaling out

There are two ways to handle more data and more users.

  • Vertical scaling (scale up): buy a bigger server with more CPU, memory and disk. This has a limit, and big servers cost a lot.
  • Horizontal scaling (scale out): add more ordinary servers and spread the data across them. There is almost no limit.

Scaling out means the data is spread over many sites. So a NoSQL database is a kind of distributed database. The ideas of fragmentation and replication from topic 5.1 apply here too. NoSQL systems call fragmentation sharding.

Features of NoSQL

  1. Non-relational. Data is not kept in tables joined by foreign keys.
  2. Schema-free or flexible schema. You do not have to define every field first. Two records in the same collection can have different fields.
  3. Distributed. Data is split (sharded) and copied (replicated) across many servers.
  4. Horizontal scalability. Add servers to store more data and serve more users.
  5. High availability. Copies of data on other servers keep the system running when one server fails.
  6. Handles all kinds of data. It stores structured, semi-structured and unstructured data.
  7. Cost effective. It runs on many cheap servers, and most NoSQL systems are open source.
  8. Simple access by key. Many queries read or write one item by its key, which is very fast.
  9. Eventual consistency. Many NoSQL systems follow the BASE model, explained below.

Worked example: one student, two models

Let us store a student, her phone numbers and her course marks. First, in a relational database.

SQL (MySQL 8.4) 
CREATE TABLE student (
  roll_no INT PRIMARY KEY,
  name    VARCHAR(50),
  dept    CHAR(4)
);
CREATE TABLE student_phone (
  roll_no INT,
  phone   VARCHAR(15),
  PRIMARY KEY (roll_no, phone)
);
CREATE TABLE marks (
  roll_no INT,
  course  VARCHAR(30),
  marks   INT,
  PRIMARY KEY (roll_no, course)
);

-- Reading one student needs joins over three tables.
SELECT s.name, p.phone, m.course, m.marks
FROM student s
JOIN student_phone p ON p.roll_no = s.roll_no
JOIN marks m ON m.roll_no = s.roll_no
WHERE s.roll_no = 101;

The data is split over three tables, because a cell in a table can hold only one value. Now the same student as one document in a NoSQL database such as MongoDB.

JSON document 
{
  "_id": 101,
  "name": "Anitha",
  "dept": "CSE",
  "phones": ["98940 12345", "94430 67890"],
  "marks": [
    { "course": "DBMS", "marks": 86 },
    { "course": "Operating Systems", "marks": 78 }
  ]
}

Everything about the student is in one place. The app reads it with one lookup by its key, _id, and no joins.

Example: adding a new field

The college now wants to store a hostel room for hostel students only.

  • Relational: run ALTER TABLE student ADD COLUMN hostel_room VARCHAR(10);. Every row gets the new column, and day scholars hold NULL.
  • NoSQL: just add "hostel_room": "B-204" to the documents of hostel students. Other documents stay the same. No schema change is needed.
Common mistake

“Schema-free” does not mean there is no structure. The app still expects fields such as name. The difference is that the database does not check the structure. The app must do it.

ACID and BASE

Relational databases follow the ACID properties (topic 3.2): atomicity, consistency, isolation and durability. ACID keeps data correct at every moment. But across many servers, ACID needs a lot of waiting, as we saw with two-phase commit. Many NoSQL systems relax it and follow BASE instead.

Definition: BASE
  • Basically available (BA): the system always answers, even if some servers are down. The answer may be a little old.
  • Soft state (S): the data on different copies may differ for a short time, even with no new writes.
  • Eventual consistency (E): if writes stop, all copies become the same after some time.
Example

You like a friend's photo. Your phone shows 101 likes at once. Your friend in another city still sees 100 likes for a second or two. Soon, every copy shows 101. This short delay is eventual consistency. It is fine for likes, but not for a bank balance.

Exam tip

For a “differentiate SQL and NoSQL” question, write at least five rows: data model, schema, scaling, transactions (ACID and BASE) and examples. Add the four NoSQL types with one example each for more marks.

NoSQL does not replace relational databases. Many apps use both. For example, a shopping site may keep orders and payments in MySQL and keep the product catalog and the shopping cart in a NoSQL store.

Merits and demerits (advantages and disadvantages)

Merits (advantages)

  • Scales out easily: add cheap servers as data and users grow.
  • Flexible schema: add new fields without changing old records.
  • High availability: replicas keep the system running when a server fails.
  • Fast for simple reads and writes: one lookup by key, with no joins.
  • Handles big and varied data: semi-structured and unstructured data fit well.
  • Low cost: runs on ordinary servers, and many systems are open source.

Demerits (disadvantages)

  • Weaker consistency: with eventual consistency, a read can return old data for a short time.
  • No standard query language: each product has its own way to query data.
  • Limited joins and complex queries: queries across many items are harder than in SQL.
  • Redundant data: denormalized data is copied in many places, so updates must change every copy.
  • Less mature tools: fewer reporting tools and experts than for relational databases.

In real life

Food delivery app

Restaurant menus change often and each restaurant has different items and options. A document store keeps each menu as one document. Payments still go to a relational database with ACID.

Live cricket scores

Millions of fans check the score at the same moment. A key-value cache such as Redis serves the score fast. A delay of one second is fine.

Key points

  • NoSQL means “not only SQL”. It is a non-relational database with a flexible schema.
  • It is needed for big data, varied data, high availability and easy scaling.
  • Relational databases mostly scale up (bigger server). NoSQL databases scale out (more servers).
  • BASE means basically available, soft state and eventual consistency. It trades strict consistency for availability.
  • The four types are document, key-value, column-based and graph databases.
  • Choose a relational database for strict correctness and complex queries. Choose NoSQL for huge, fast-changing data.
