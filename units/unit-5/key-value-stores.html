Key Value Stores

A key-value store is the simplest NoSQL database. It keeps each item as a unique key and a value, like a giant dictionary. This page explains how it works, where it shines, and its two best-known examples, Redis and Amazon DynamoDB.

What is a key-value store?

Definition

A key-value store is a NoSQL database that stores data as pairs of a unique key and a value. The value can be a string, a number, JSON or any binary object. The database finds data only by its key and does not look inside the value.

Think of the lockers at a railway station cloakroom. You give a bag and get a token number. Later you show the token and get the same bag back. The staff never open the bag. The token is the key and the bag is the value.

A few key-value pairs
KeyValue
user:42:name"Karthik"
cart:42{"P1001": 2, "P2050": 1}
session:9f3a1c{"user": 42, "login": "2026-10-07T09:15"}
views:P100118342

The basic operations

A key-value store needs only three basic operations.

  • put(key, value): store the value under the key. If the key exists, replace its value.
  • get(key): return the value stored under the key.
  • delete(key): remove the key and its value.

In Redis, these are SET, GET and DEL.

Redis 
SET user:42:name "Karthik"
GET user:42:name        -- returns "Karthik"
INCR views:P1001        -- adds 1 to the view count
DEL user:42:name

Each operation touches one key, so it can be done in well under a millisecond. There are no joins and no search conditions such as WHERE marks > 80.

Common mistake

“Find all users from Salem” is not a key-value query. The store cannot look inside the values. To answer it, the app must keep an extra key such as city:Salem holding the list of user ids, or use another kind of database.

Designing keys

Because data is found only by key, choosing keys is the main design work. A common pattern is type:id:part, joined by colons.

  • student:101 for the whole student record.
  • student:101:marks for that student's marks only.
  • cart:42 for the cart of user 42.

Good keys are unique, easy to build from what the app already knows (such as the user id), and short.

Worked examples

Example 1: login sessions that expire

When a user logs in, the website makes a random session id and stores the session. The key should disappear after 30 minutes. Redis can set an expiry time (TTL, time to live) in seconds.

Redis 
SET session:9f3a1c "{\"user\": 42}" EX 1800
GET session:9f3a1c      -- the session, while it is valid
TTL session:9f3a1c      -- seconds left before it expires

Every page request reads the session by its key in one fast step. After 1800 seconds, Redis deletes the key by itself.

Example 2: a cache in front of MySQL

A college results page reads the same results again and again. The app first asks Redis for result:101. If the key is there (a cache hit), it uses it. If not (a cache miss), it runs the SQL query on MySQL, stores the answer in Redis for 10 minutes and returns it. MySQL now does far less work.

Example 3: a quiz leaderboard

Redis has a sorted set value type that keeps members in order of a score. It suits a live leaderboard.

Redis 
ZADD quiz:board 86 "Anitha" 72 "Bala" 91 "Divya"
ZREVRANGE quiz:board 0 2 WITHSCORES   -- top three, highest first

Redis values can be strings, lists, hashes, sets and sorted sets. Even so, each command works on the value of one key.

How the data is spread over servers

A big key-value store runs on many servers. It decides where a key lives by hashing the key, the same idea as hashing in Unit IV.

  1. Apply a hash function to the key: h("cart:42") gives a number.
  2. The number decides the server, for example h(key) mod 3 for three servers.
  3. The pair is also copied to one or two more servers, so the data survives a failure.

Any server can find a key by hashing it, without a central index. To add servers without moving most keys, systems such as DynamoDB use consistent hashing. Servers are placed on a ring, and each key goes to the next server along the ring. A new server takes over only the keys next to it.

Exam tip

Many key-value stores are AP systems in the CAP theorem. They stay available and use eventual consistency. DynamoDB also offers strongly consistent reads when you ask for them.

Redis and Amazon DynamoDB

Redis

An open-source store that keeps data in memory, so it is extremely fast. It can also save data to disk. It offers rich value types, expiry times and publish-subscribe messages. It is widely used as a cache, a session store and for leaderboards.

Amazon DynamoDB

A fully managed cloud service from Amazon Web Services. Each item has a partition key (hashed to pick the server) and an optional sort key that orders items with the same partition key. It grows to huge sizes with steady, fast response times.

Other key-value stores include Riak, Memcached and etcd.

Merits and demerits (advantages and disadvantages)

Merits (advantages)

  • Very fast: one lookup by key, often from memory.
  • Simple: only a few operations to learn.
  • Easy to scale: hashing spreads keys evenly over many servers.
  • Flexible values: any data can be stored without a schema.
  • Highly available: copies on other servers keep it running.

Demerits (disadvantages)

  • Search only by key: no search on the contents of the value.
  • No relationships: no joins or foreign keys.
  • Extra work for the app: the app must build keys and keep extra keys for lookups.
  • Memory cost: in-memory stores such as Redis need a lot of RAM for large data.

Key points

  • A key-value store keeps data as a unique key and a value; it finds data only by key.
  • The basic operations are put, get and delete (SET, GET and DEL in Redis).
  • Keys are designed from what the app knows, such as cart:42.
  • Keys are spread over servers by hashing; consistent hashing makes adding servers easy.
  • Uses: caches, login sessions with expiry, shopping carts, counters and leaderboards.
  • Examples: Redis (in memory) and Amazon DynamoDB (managed cloud service).
