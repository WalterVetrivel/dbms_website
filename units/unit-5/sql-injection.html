SQL Injection

SQL injection is one of the oldest and most common attacks on web applications. It happens when a program pastes user input into an SQL query. This page shows how the attack works, its types and impacts, and how prepared statements stop it.

What is SQL injection?

Definition

SQL injection is an attack in which a user types SQL code into an input field, such as a login box or a search box. The application joins this input directly into its SQL query, so the input changes the meaning of the query. The attacker can then read, change or delete data they should not reach.

Think of a form at a bank: “Pay ₹____ to ____.” The clerk copies your words into the gap. If you write “₹100 to Ravi, and also give me all the cash in the safe”, a careless clerk copies all of it and obeys. The problem is not the form. It is the clerk who treats your words as orders.

Any database can be attacked this way: MySQL, Oracle, SQL Server and others. The fault is in the application code, not in the DBMS.

How the attack works

Here is a login check written the unsafe way, in Java. It builds the query by joining strings.

Java (unsafe) 
String user = request.getParameter("username");
String pass = request.getParameter("password");

String sql = "SELECT * FROM users WHERE username = '" + user +
             "' AND password = '" + pass + "'";

ResultSet rs = stmt.executeQuery(sql);
if (rs.next()) {
    // login successful
}

For a normal user, anitha and Anitha@123, the server builds a normal query.

SQL (MySQL 8.4) 
SELECT * FROM users WHERE username = 'anitha' AND password = 'Anitha@123'

But the input goes straight inside the quotes. If the input itself contains a quote ', it closes the string early. Whatever follows is read as SQL code, not as data. That is the whole trick.

Note

Real systems never store plain passwords. They store a salted hash. We use plain text here only to keep the queries short.

Worked examples

Example 1: always true (tautology)

The attacker types anitha as the username and ' OR '1'='1 as the password.

SQL (MySQL 8.4) 
SELECT * FROM users
WHERE username = 'anitha' AND password = '' OR '1'='1'

AND is done before OR, so the condition is (username = 'anitha' AND password = '') OR '1'='1'. The part '1'='1' is true for every row. The query returns all users, and the program logs the attacker in as the first one, often the administrator.

Example 2: cut off the rest (comment)

The attacker types admin' -- (with a space at the end) as the username and anything as the password.

SQL (MySQL 8.4) 
SELECT * FROM users
WHERE username = 'admin' -- ' AND password = 'anything'

In MySQL, -- starts a comment, so everything after it is ignored. The password check is gone. The query finds the admin row, and the attacker is logged in as admin.

Example 3: steal another table (UNION)

A shop's search page runs SELECT name, price FROM products WHERE name LIKE '%input%'. The attacker searches for:

Attacker's input 
%' UNION SELECT username, password FROM users --
SQL (MySQL 8.4) 
SELECT name, price FROM products WHERE name LIKE '%%'
UNION SELECT username, password FROM users -- %'

UNION adds the rows of a second query to the first. Both have two columns, so the page now lists every username and password next to the products.

Common mistake

Hiding the error messages does not fix SQL injection. Attackers can still ask yes-or-no questions and watch how the page changes. Only keeping input out of the SQL code fixes it.

Types of SQL injection

Types of SQL injection
TypeHow the attacker gets dataExample
In-band: tautologyMakes the WHERE clause always true' OR '1'='1
In-band: UNION basedJoins the results of another query onto the page' UNION SELECT username, password FROM users --
In-band: error basedMakes the database show an error that contains dataA bad cast whose error message prints a value
Blind: boolean basedAsks yes-or-no questions and watches if the page changes' AND SUBSTRING(password,1,1) = 'a' --
Blind: time basedMakes the database wait when the answer is yes' AND IF(1=1, SLEEP(5), 0) --
Piggy-backed (stacked)Adds a second statement after a ;'; DROP TABLE users; --
Out-of-bandMakes the server send data to the attacker's machineUsing a function that opens a network link
Second orderStores the input safely now; it runs as SQL later in another queryA username such as admin' -- used later in a password-change query

In in-band attacks, the data comes back on the same page. In blind attacks, nothing is shown, so the attacker learns one bit at a time. Blind attacks are slower, but tools can automate them.

Impacts

  • Login bypass: enter as any user, even the administrator, without a password.
  • Data theft (loss of confidentiality): read passwords, card numbers, marks and personal details.
  • Data change (loss of integrity): change marks or prices, or add fake records.
  • Data loss (loss of availability): delete rows or drop whole tables.
  • Server takeover: with too many privileges, write files or run commands on the server.
  • Legal and money loss: fines under data protection law, lawsuits and loss of trust.

Prevention

  1. Prepared statements (parameterized queries): the main defense. The SQL is sent with ? placeholders, and the values are sent separately. The database never reads a value as code, whatever quotes or dashes it contains.
  2. Stored procedures that use parameters, not joined strings, inside them.
  3. Input validation with allow-lists: accept only what is expected. A roll number must be digits only; a sort column must be one of a fixed list.
  4. Least privilege: the web app's MySQL account gets only the privileges it needs (topic 5.11). A login page does not need DROP.
  5. Hide database errors from users and log them for the developers instead.
  6. Escaping special characters, only when nothing else is possible. It is easy to get wrong.
  7. A web application firewall (WAF) that blocks known attack patterns, as an extra layer.

For the 16-mark question, cover five parts. Define SQL injection and show the unsafe code with the ' OR '1'='1 example. Then list the types in a table and the impacts. End with prevention, showing the prepared statement code.

Worked example: the prepared statement fix

The same login check, written safely with JDBC's PreparedStatement.

Java (safe) 
String sql = "SELECT * FROM users WHERE username = ? AND password = ?";

PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, user);   // value for the 1st ?
ps.setString(2, pass);   // value for the 2nd ?

ResultSet rs = ps.executeQuery();

Now the attacker types ' OR '1'='1 as the password. The database looks for a user whose password is exactly the 11 characters ' OR '1'='1. No such row exists, so the login fails. The query's shape was fixed before the value arrived.

MySQL 8.4 also supports prepared statements directly in SQL.

SQL (MySQL 8.4) 
PREPARE login FROM
  'SELECT * FROM users WHERE username = ? AND password = ?';

SET @u = 'anitha', @p = ''' OR ''1''=''1';
EXECUTE login USING @u, @p;     -- no rows: the attack fails

DEALLOCATE PREPARE login;
Common mistake

A prepared statement helps only if the input goes into a ?. Code such as conn.prepareStatement("... WHERE name = '" + user + "'") is still unsafe, because the input was joined before preparing.

In real life

Big data breaches

SQL injection has caused some of the largest leaks of card numbers and passwords. It is still listed in the OWASP Top 10 risks for web applications, under “Injection”.

Frameworks help

Modern tools such as Spring (Java), Django (Python) and Laravel (PHP) use parameters by default. Injection usually returns when a developer joins strings by hand.

Key points

  • SQL injection happens when user input is joined into an SQL query and changes its meaning.
  • A quote in the input closes the string early; what follows runs as SQL.
  • Classic attacks: ' OR '1'='1 (always true), admin' -- (comment) and UNION SELECT (steal data).
  • Types: in-band (tautology, UNION, error based), blind (boolean, time based), stacked, out-of-band and second order.
  • Impacts: login bypass, data theft, data change or loss, and server takeover.
  • Prevention: prepared statements first, plus allow-list validation, least privilege and hidden errors.
