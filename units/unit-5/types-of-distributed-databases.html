Types of Distributed Databases

Some distributed databases use the same DBMS at every site. Others join different systems that were built separately. This page explains homogeneous, heterogeneous and federated databases.

Two questions that decide the type

Think of a chain of shops. In one chain, every shop uses the same billing app, so the shops can share data with ease. In another group, each shop picked its own app. They can still share data, but someone must first convert it. Distributed databases are the same.

A distributed database has many sites. To find its type, we ask two simple questions about the sites.

  1. Do all sites use the same software? If every site runs the same DBMS with the same schema, the system is homogeneous (“homo” means same). If not, it is heterogeneous (“hetero” means different).
  2. How much does each site control itself? This is called local autonomy. A site with full autonomy makes its own rules. It can change its own tables. It can say no to a request from another site.

Homogeneous systems

Definition

In a homogeneous distributed database, all sites use the same DBMS software and the same schema. The sites know about each other and cooperate to answer user requests.

  • To the user, it looks like one single database.
  • Each site gives up part of its autonomy. For example, a site cannot change the schema or the DBMS software on its own.
  • The system is usually designed as one distributed database from the start (top-down design).
Example

A bank runs MySQL 8.4 at its Salem, Chennai and Coimbatore branches. Every branch has the same Account and Customer tables. A transfer from Salem to Chennai is handled by the two MySQL sites working together.

Merits (advantages)

  • Easy to design, manage and grow.
  • No translation between systems is needed.
  • The sites work as one team, so a query that needs many sites is simple.

Demerits (disadvantages)

  • Every site must use the same product, even if a site needs a different one.
  • Each site has little control of its own.

Heterogeneous systems

Definition

In a heterogeneous distributed database, the sites may use different DBMS software or different schemas. They may even use different data models. For example, one site has tables and another site stores JSON documents.

  • A site may not know about the other sites.
  • Sites help each other only a little. This is called limited cooperation.
  • A program called middleware (or a gateway) sits between the sites. It turns a query for one system into a query the other system can read.
  • Such a system often starts as many separate databases. They are joined later. This is called bottom-up design.

Example

After two banks merge, one bank's branches still run Oracle and the other bank's branches run MySQL. Middleware lets head office run one query over both.

Merits (advantages)

  • Old databases can be joined. We do not need to build them again.
  • Each site can choose the system that suits it best.
  • Each site keeps more control over its own data.

Demerits (disadvantages)

  • Queries and data must be translated, which is complex and slower.
  • A transaction that uses many sites is hard to control.
  • Differences in schema and meaning must be resolved by hand.

Federated systems

Definition

A federated database system (FDBS) is a group of autonomous databases that agree to share some of their data. It is also called a multidatabase system. A layer of software on top gives users one view of the shared data.

Each member database still works for its own local users. It shares only the data it wants to share. So the global view shows only part of the data.

Kinds of autonomy in a federated system

  • Design autonomy: each site chooses its own data model, schema and DBMS.
  • Communication autonomy: each site decides whether to talk to other sites and what to share.
  • Execution autonomy: each site runs its local work in its own way, and can refuse or delay a global request.
  • Association autonomy: each site decides how much of its data and processing to share.
Example

A state health department wants a report on patients from many hospitals. Each hospital keeps its own system and its own rules. Each hospital shares only a few tables, without names, with the department's federated system.

Note

Some books also use the words peer-to-peer and client-server. These words tell us how the sites are set up. They do not tell us if the sites use the same software. See Distributed Databases: Architecture.

In real life

College group

A group of colleges uses one ERP product at every campus with the same tables. This is a homogeneous system, so the group office can run reports across campuses easily.

DigiLocker

DigiLocker shows mark sheets, driving licenses and other documents from many government departments. Each department keeps its own system, and only shares the documents through a common layer, much like a federated system.

Key points

  • The type depends on two things: whether sites use the same software (homogeneity) and how much control each site keeps (autonomy).
  • Homogeneous: same DBMS and schema at all sites; sites know each other and cooperate fully.
  • Heterogeneous: sites may use different DBMS software, schemas or data models; middleware translates between them.
  • Federated (multidatabase): each database keeps its own control and shares only some data through a common layer.
  • There are four kinds of autonomy. They are design, communication, execution and association.
  • A homogeneous system is easy to manage. A heterogeneous system lets old databases work together.
