Access Control Based on Privileges

A database should let each user do only what their job needs. This page explains how privileges are given and taken back with GRANT and REVOKE, and compares this with the stricter, level-based mandatory access control.

Privileges and access control

Definitions
  • A privilege is a right to do one kind of action on one database object, such as SELECT on the marks table.
  • Discretionary access control (DAC) gives and takes back privileges with GRANT and REVOKE. The owner of an object decides, at their own discretion (choice), who else may use it.

Think of your own notebook. You own it, so you decide who may read it. You may even let a friend lend it to others. That is discretionary control. In a hostel, the warden decides the rules for every room, and students cannot change them. That is closer to mandatory control, which we meet later on this page.

Access control follows the principle of least privilege: give each user only the privileges their work needs, and no more.

Two levels of privileges

  1. Account level: privileges an account holds whatever tables exist. Examples: the right to create tables, create views, create users or shut down the server.
  2. Table (relation) level: privileges on one table or view. Examples: SELECT, INSERT, UPDATE, DELETE and REFERENCES (use the table in a foreign key). UPDATE and SELECT can even be limited to some columns.

Every table has an owner, usually the account that created it. The owner holds all privileges on it and can grant them to others.

The access matrix

DAC can be pictured as an access matrix M. Each row is a subject (a user, account or program). Each column is an object (a table, view or column). The cell M(i, j) lists the privileges that subject i holds on object j.

A real system has thousands of users and tables, and most cells are empty. So the DBMS stores the matrix in parts. Each object keeps a list of who may use it. This is an access control list (ACL). In MySQL, the grant tables in the mysql system database play this part.

GRANT and REVOKE

Here is the teacher row of the matrix above, written in MySQL 8.4.

SQL (MySQL 8.4) 
CREATE USER 'ravi'@'localhost' IDENTIFIED BY 'T3ach#2026';

-- Table-level privileges
GRANT SELECT ON college.student TO 'ravi'@'localhost';
GRANT SELECT, INSERT ON college.marks TO 'ravi'@'localhost';

-- Column-level privilege: may change only the marks column
GRANT UPDATE (marks) ON college.marks TO 'ravi'@'localhost';

-- Account-level (global) privilege
GRANT CREATE VIEW ON *.* TO 'ravi'@'localhost';

-- Take one privilege back
REVOKE INSERT ON college.marks FROM 'ravi'@'localhost';

SHOW GRANTS FOR 'ravi'@'localhost';

The pattern is GRANT privileges ON object TO account and REVOKE privileges ON object FROM account.

Example: rows with a view

GRANT works on whole tables or columns, not on chosen rows. To let the CSE head see only CSE students, make a view and grant on the view.

SQL (MySQL 8.4) 
CREATE VIEW college.cse_students AS
  SELECT roll_no, name, cgpa FROM college.student WHERE dept = 'CSE';

GRANT SELECT ON college.cse_students TO 'hod_cse'@'localhost';

The head of department can read the view but not the full student table. The view hides both the other departments' rows and the columns not listed.

Passing privileges on

By default, a user who receives a privilege cannot pass it to others. The grantor can allow this by adding WITH GRANT OPTION.

SQL (MySQL 8.4) 
GRANT SELECT ON college.marks TO 'ravi'@'localhost' WITH GRANT OPTION;

Now Ravi may grant SELECT on marks to other users. This is called propagation of privileges. It is useful, but the owner loses track of who can read the data.

When a privilege is revoked, what happens to the copies that were passed on?

  • In standard SQL, REVOKE ... CASCADE also removes the privileges that the user passed on, unless those users got the same privilege from someone else. REVOKE ... RESTRICT refuses to revoke if this would happen.
  • MySQL does not record who granted what. Revoking from one user does not touch the users they granted to, so the DBA must revoke from each of them too.

Some systems also limit propagation. A horizontal limit caps how many accounts a user may grant to. A vertical limit caps the length of the chain of grants.

Worked example: a chain of grants

The DBA owns the marks table. Follow the grants in standard SQL.

  1. The DBA grants SELECT to A WITH GRANT OPTION.
  2. A grants it to B WITH GRANT OPTION.
  3. B grants it to C (without the option).
  4. The DBA also grants SELECT directly to C.

Now the DBA runs REVOKE SELECT ON marks FROM A CASCADE.

  • A loses the privilege.
  • B got it only from A, so B loses it too.
  • C got it from B, but also directly from the DBA. So C keeps it.

In MySQL, only A would lose it. B and C would keep their privileges until the DBA revoked them.

Common mistake

Revoking a privilege does not always remove every path to the data. Always check with SHOW GRANTS, and remember other routes such as a view or another grantor.

Mandatory access control

Definition

In mandatory access control (MAC), the system gives every object a classification and every user a clearance. Access is decided by comparing the two levels. Users cannot pass their rights to others.

The usual levels, from highest to lowest, are Top Secret (TS) > Secret (S) > Confidential (C) > Unclassified (U). MAC is used by the army, the government and intelligence agencies.

The best-known MAC model is Bell-LaPadula. It has two rules.

  1. Simple security property (no read up): a subject may read an object only if the subject's clearance is at least as high as the object's class.
  2. Star (*) property (no write down): a subject may write an object only if the object's class is at least as high as the subject's clearance.

The second rule stops a Top Secret user from copying secrets into an Unclassified table, even by mistake.

Merits and demerits (advantages and disadvantages)

Discretionary access control

Merits (advantages)

  • Flexible: owners share data as needed.
  • Simple to use with GRANT and REVOKE.
  • Fine control down to columns and views.

Demerits (disadvantages)

  • Grants can spread beyond the owner's control.
  • No control over copies a reader makes.
  • Hard to manage for thousands of users.

Mandatory access control

Merits (advantages)

  • Very strong protection of secret data.
  • Stops leaks to lower levels.
  • Users cannot weaken the rules.

Demerits (disadvantages)

  • Rigid: hard to share data across levels.
  • Every object and user needs a level.
  • Too strict for most businesses.

Key points

  • A privilege is a right to do one action on one object. DAC grants and revokes privileges at the owner's choice.
  • Privileges exist at the account level and at the table (relation) level, even down to columns.
  • The access matrix has subjects as rows, objects as columns and privileges in the cells.
  • GRANT ... ON ... TO gives privileges; REVOKE ... ON ... FROM takes them back. Views limit rows.
  • WITH GRANT OPTION lets privileges spread; REVOKE ... CASCADE removes the spread copies in standard SQL.
  • MAC uses clearance and classification levels. Bell-LaPadula: no read up, no write down.
