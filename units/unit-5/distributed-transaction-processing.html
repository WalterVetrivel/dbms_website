Transaction Processing in Distributed Databases

A transaction in a distributed database may change data at many sites. It must commit at all of them or at none of them. This page shows how the sites agree, and what happens when a site or the network fails.

Local and global transactions

A student pays the college fee from an account in the Salem branch. The college account is in the Chennai branch. The money must leave Salem and reach Chennai. If only one of the two changes happens, money is lost or created. So both changes must happen together, or not at all.

Definitions
  • A local transaction reads and writes data only at the site where it starts.
  • A global transaction (or distributed transaction) reads or writes data at more than one site.

The site where a transaction starts is its coordinating site. The other sites that do part of its work are participating sites.

Example

Transaction T1 starts at site S1 and needs data at sites S2 and S3. S1 is the coordinating site. T1 runs a subtransaction T12 at S2 and another subtransaction T13 at S3. S2 and S3 are the participating sites.

Like any transaction, a global transaction must have the ACID properties. The hard one is atomicity: T1 must commit at every site or abort at every site. It must never commit at S2 and abort at S3.

Transaction manager and coordinator

Each site has two parts that work on transactions.

Transaction manager (TM)

Manages the transactions and subtransactions that use data stored at its own site.

  • Keeps the log for recovery.
  • Takes part in concurrency control (locking) for the transactions running at that site.

Transaction coordinator (TC)

Manages the transactions that start at its site, local or global.

  • Starts the transaction.
  • Splits it into subtransactions and sends them to the right sites.
  • Ends it: makes sure it commits at all sites or aborts at all sites.

Failure modes

A distributed system can fail in ways that a single computer cannot. There are four basic failure modes.

  1. Failure of a site: one computer stops, for example after a power cut.
  2. Loss of messages: a message never reaches the other site. This is the most common failure. Network protocols such as TCP detect lost messages and send them again.
  3. Failure of a communication link: one network link breaks. Messages are then sent along another route, if one exists.
  4. Network partition: the network splits into two or more groups of sites. Sites in one group cannot talk to sites in another group.
Note

A site often cannot tell these failures apart. If site S2 does not reply, S1 does not know whether S2 crashed, the message was lost, or the network is split. So sites use a timeout: if no reply comes within a set time, they assume a failure.

Two-phase commit (2PC)

A commit protocol makes sure that a global transaction commits at all sites or aborts at all sites. Two-phase commit is the most widely used commit protocol.

Let T start at site Si, so its coordinator is Ci. T has finished its work at every site and now wants to commit. Each step writes a record to the log on disk first, so that a site knows what it did even after a crash.

Phase 1: voting (prepare phase)

  1. Ci writes <prepare T> to its log and sends a prepare T message to every participating site.
  2. Each site checks whether it can commit its part of T.
    • If it can, it writes <ready T> to its log and replies ready T.
    • If it cannot, it writes <no T> to its log and replies abort T.

A site that has replied “ready” gives up the right to abort T on its own. It must now wait for the coordinator's decision.

Phase 2: decision (commit phase)

  1. If every site replied ready, Ci writes <commit T> to its log. If any site replied abort, or did not reply in time, Ci writes <abort T>. Once this record is on disk, the decision is final.
  2. Ci sends commit T or abort T to every site.
  3. Each site writes the same record to its log, commits or aborts its part of T, and sends an acknowledgment.
  4. When all acknowledgments arrive, Ci writes <complete T>.

Single-phase commit and two-phase commit

In a single-phase commit, the coordinator simply tells every site to commit. A site has no chance to say that it cannot commit. If one site then fails to commit, T is committed at some sites and not at others, so atomicity is broken. 2PC fixes this with the voting phase, at the cost of more messages and more waiting.

How 2PC handles failures

A participating site fails

If a site fails before it replies ready, the coordinator treats the missing reply as “abort” and aborts T. When the failed site Sk recovers, it reads its log for T:

Recovery of a participating site Sk
Log of Sk containsAction
<commit T>redo(T)
<abort T>undo(T)
<ready T> onlyAsk the coordinator (or other sites) what was decided, then redo or undo
No record for TSk failed before voting, so the coordinator must have aborted T: undo(T)

The coordinator fails

If the coordinator Ci fails while T is in progress, the active participating sites look at their own logs to decide:

  1. If any active site has <commit T>, then T is committed.
  2. If any active site has <abort T>, then T is aborted.
  3. If some active site does not have <ready T>, then Ci cannot have decided to commit. So T can be aborted.
  4. Otherwise every active site has <ready T> and nothing more. The sites cannot know the decision. They must wait for Ci to recover.
The blocking problem

In case 4, T is blocked. The sites keep T's locks while they wait, so other transactions that need the same data must wait too. This can last a long time. Blocking is the main demerit (disadvantage) of 2PC.

Network partition

If the coordinator and all participants are in the same part, the partition does not affect T. If they are split, the sites cut off from the coordinator act as if the coordinator failed. The coordinator acts as if those sites failed.

Three-phase commit (3PC)

Three-phase commit extends 2PC to avoid the blocking problem. It assumes that:

  • there is no network partition;
  • at any time, at least one site is up;
  • at most K sites fail at the same time (K is a chosen number).

The three phases

  1. Phase 1 (voting): the same as phase 1 of 2PC. The coordinator asks every site to prepare, and each site votes.
  2. Phase 2 (pre-commit): if all vote ready, the coordinator makes a pre-commit decision. It writes <precommit T> and sends it to the sites. At least K sites must record it and reply before the coordinator goes on.
  3. Phase 3 (commit): the coordinator writes <commit T> and sends commit T to all sites.

If the coordinator fails, the remaining sites choose a new coordinator. The new coordinator asks the sites for their state. If any site has <precommit T>, everyone voted ready, so it commits T. If no site has it, the old coordinator cannot have committed T, so it aborts T. Either way, the sites do not have to wait for the old coordinator.

Merit (advantage)

It avoids blocking, as long as no more than K sites fail.

Demerits (disadvantages)

An extra round of messages and log writes makes every commit slower. It does not work correctly if the network is partitioned, so it is rarely used in practice.

In real life

Train ticket with payment

Booking a train ticket changes the seat database and the payment system. Both must agree. If the payment succeeds but the seat is not booked, the money is returned automatically. This is the same idea as a commit protocol.

XA transactions in MySQL

MySQL supports two-phase commit across servers through XA transactions. XA PREPARE is the voting phase, and XA COMMIT or XA ROLLBACK is the decision.

Key points

  • A global (distributed) transaction uses data at more than one site; a local transaction uses only one site.
  • The transaction coordinator starts, splits and ends transactions; the transaction manager runs them at its own site and keeps the log.
  • Failure modes: site failure, lost message, link failure and network partition.
  • 2PC phase 1: prepare T, then each site logs <ready T> or <no T> and votes.
  • 2PC phase 2: commit only if all vote ready; the coordinator logs <commit T> or <abort T> and tells every site.
  • A recovering site with no <ready T> aborts T; with <ready T> only, it must ask what was decided.
  • 2PC can block: if the coordinator fails after all sites are ready, they must wait for it.
  • 3PC adds a pre-commit phase so that a new coordinator can decide, avoiding blocking when there is no partition.
