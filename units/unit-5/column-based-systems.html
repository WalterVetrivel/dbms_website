Column Based Systems

A column-based NoSQL database stores rows whose columns are grouped into column families, and each row can have its own columns. This page explains the model with HBase and Cassandra and shows how to design a table for huge amounts of data.

What is a column-based database?

Definition

A column-based (or wide-column) NoSQL database stores data in rows found by a row key. The columns of a row are grouped into column families, and columns of one family are stored together. Each row can have a different set of columns, so the number of columns is not fixed.

It looks like a table, but it behaves like a two-level map. First the row key finds the row. Then the column family and column name find the value.

The idea comes from Google's Bigtable (2006). Apache HBase copies Bigtable's design. Apache Cassandra, first built at Facebook, mixes it with ideas from Amazon's key-value store.

The data model

  • Table: holds rows, like a relational table.
  • Row key: the unique id of a row. Rows are kept sorted by row key, and data is split over servers by ranges of row keys.
  • Column family: a group of related columns, such as info and marks. Families are declared when the table is made.
  • Column (qualifier): a name inside a family, such as marks:DBMS. Columns are not declared; any row can add new ones.
  • Cell: the value at a row, family and column. A cell can keep several versions, each with a timestamp.

A cell marked “(none)” is not stored at all. In a relational table it would be a NULL that still takes space. Rows with only a few of thousands of possible columns are called sparse. Wide-column stores handle sparse data well.

Example: versions of a cell

Anitha's DBMS mark is first entered as 68 at time t1. After revaluation, it is changed to 86 at time t2. HBase keeps both: marks:DBMS = 86 @ t2 and 68 @ t1. A normal read returns the newest version, 86. You can also ask for older versions.

Worked example: HBase

We create the student table with two families and add Anitha's data, using the HBase shell.

HBase shell 
create 'student', 'info', 'marks'

put 'student', '101', 'info:name',  'Anitha'
put 'student', '101', 'info:dept',  'CSE'
put 'student', '101', 'marks:DBMS', '86'
put 'student', '101', 'marks:OS',   '78'

get  'student', '101'                 # the whole row
get  'student', '101', 'marks'        # only the marks family
scan 'student', {STARTROW => '101', STOPROW => '200'}
  1. create names only the table and its families. No columns are declared.
  2. Each put writes one cell, named as family:column.
  3. get reads a row by its row key. scan reads a range of rows in row key order.

Worked example: Cassandra and CQL

Cassandra uses CQL (Cassandra Query Language), which looks like SQL. A smart city has thousands of air sensors. Each sends a reading every minute. The app asks: “Show the readings of sensor S17 for one day, newest first.”

In Cassandra you design the table for that query.

CQL (Cassandra) 
CREATE TABLE readings (
  sensor_id  text,
  day        date,
  read_at    timestamp,
  pm25       float,
  temp       float,
  PRIMARY KEY ((sensor_id, day), read_at)
) WITH CLUSTERING ORDER BY (read_at DESC);

INSERT INTO readings (sensor_id, day, read_at, pm25, temp)
VALUES ('S17', '2026-10-07', '2026-10-07 09:15:00', 42.5, 29.1);

SELECT read_at, pm25 FROM readings
WHERE sensor_id = 'S17' AND day = '2026-10-07';
  • Partition key (sensor_id, day): hashed to choose the servers. All readings of one sensor for one day sit together.
  • Clustering column read_at: sorts the readings inside the partition, newest first.
  • The SELECT reads one partition from one place, in order. That is very fast even with billions of rows.
Common mistake

CQL looks like SQL, but it is not SQL. SELECT * FROM readings WHERE pm25 > 100 is refused by default, because it would have to scan every server. Joins are not supported. You design one table per query, and the same data may be stored in more than one table.

Why writes are fast

HBase and Cassandra never update data in place on disk. A write does three quick steps.

  1. Add the change to the end of a commit log, for recovery after a crash (like the log in Unit III).
  2. Put the change in a sorted table in memory.
  3. When memory fills, write it to disk as a new sorted file. Older files are merged in the background.

Writing to the end of a file is much faster than finding and changing a record. This is why wide-column stores suit apps that write all the time, such as logs and sensor data.

Wide-column and columnar are not the same

Some books also use “column store” for a different idea: a columnar database that stores each column of a table separately on disk. Adding up one column, such as total sales, is then very fast. Examples are Amazon Redshift and ClickHouse, used for data warehouses and reports.

Merits and demerits (advantages and disadvantages)

Merits (advantages)

  • Handles huge data: billions of rows spread over many servers.
  • Very fast writes: writes are appended, not updated in place.
  • Flexible columns: each row can have its own columns, and empty cells cost nothing.
  • High availability: data is copied to several servers; Cassandra has no single master.
  • Versioned cells: old values can be kept with timestamps.

Demerits (disadvantages)

  • Query-first design: new kinds of queries may need new tables.
  • No joins and limited filters: reads should use the row or partition key.
  • Duplicate data: the same data is often kept in several tables.
  • Complex to run: clusters need skilled people to tune and repair.

In real life

Messages and chats

Chat apps store billions of messages, partitioned by chat id and sorted by time. Discord ran its messages on Cassandra for years for this reason.

Sensors and logs

Electricity smart meters and factory machines send readings every few seconds. A wide-column store takes these writes without slowing down.

Key points

  • A column-based (wide-column) database stores rows by row key, with columns grouped into column families.
  • Families are declared; columns are not. Each row can have different columns, and missing cells are not stored.
  • Cells can keep several versions with timestamps.
  • HBase uses put, get and scan; Cassandra uses CQL with a partition key and clustering columns.
  • Tables are designed around the queries; there are no joins.
  • Examples: Apache HBase and Apache Cassandra. Uses: sensor data, logs, messages, time series.
