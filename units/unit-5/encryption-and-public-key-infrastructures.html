Encryption and Public Key Infrastructures

Access control stops people who log in from doing too much. Encryption protects data even when someone gets past it, for example by stealing a disk or listening on the network. This page explains the two kinds of encryption, digital signatures and the public key infrastructure that makes them trustworthy.

Encryption basics

Definitions
  • Plaintext: the readable data, such as Marks: 86.
  • Ciphertext: the scrambled data after encryption, such as 9f3Ac0e1....
  • Encryption: turning plaintext into ciphertext with an algorithm and a key.
  • Decryption: turning ciphertext back into plaintext with the right key.
  • Key: a secret value. The algorithm can be public; only the key must be kept safe.

A simple old example is the Caesar cipher: shift each letter 3 places, so DBMS becomes GEPV. The algorithm is “shift”, and the key is 3. It is far too easy to break today, but it shows the idea of a key.

Databases use encryption in two places:

  • Data in transit: data moving between the app and the database server over the network.
  • Data at rest: data stored on disk, in backups and in log files.

Symmetric encryption

Definition

In symmetric (secret key) encryption, the same key is used to encrypt and to decrypt.

It is like a lockbox with one key copied for two people. Both can lock and unlock it. The standard today is AES (Advanced Encryption Standard), with 128-bit or 256-bit keys. The older DES used 56-bit keys and is no longer safe.

Symmetric encryption is fast, so it is used for large amounts of data, such as whole disks and tables. Its problem is key distribution: how do two people share the secret key safely in the first place? If the key is sent openly, anyone who sees it can read everything.

Asymmetric (public key) encryption

Definition

In asymmetric (public key) encryption, each user has a pair of keys. The public key is shared with everyone. The private key is kept secret. Data encrypted with the public key can be decrypted only with the matching private key.

Think of a post box with a slot. Anyone can drop a letter in (the public key). Only the owner, who has the key to open the box, can take letters out (the private key).

The best-known method is RSA (Rivest, Shamir and Adleman, 1977). Its safety comes from a hard problem: multiplying two large primes is easy, but splitting the result back into those primes is extremely slow.

Public key encryption solves key distribution, because the public key need not be secret. But it is much slower than AES. So real systems use both together, called hybrid encryption: public key encryption is used only to share a fresh AES key, and AES then encrypts the data. TLS, the lock in your browser, works this way.

Worked example: RSA with small numbers

Real RSA uses numbers with hundreds of digits. Small numbers show the same steps.

  1. Pick two primes: p = 3 and q = 11.
  2. Compute n = p × q = 33. This is part of both keys.
  3. Compute φ(n) = (p − 1)(q − 1) = 2 × 10 = 20.
  4. Pick e with no common factor with 20, such as e = 3. The public key is (e, n) = (3, 33).
  5. Find d so that (d × e) mod 20 = 1. Since 7 × 3 = 21 and 21 mod 20 = 1, d = 7. The private key is (d, n) = (7, 33).

Encrypt the message m = 4 with the public key: c = me mod n = 43 mod 33 = 64 mod 33 = 31.

Decrypt with the private key: m = cd mod n = 317 mod 33. Work it in small steps:

  • 312 = 961, and 961 mod 33 = 4.
  • 314 = (312)2, so it is 42 = 16 (mod 33).
  • 317 = 314 × 312 × 31, so it is 16 × 4 × 31 = 1984 (mod 33).
  • 1984 mod 33 = 1984 − 60 × 33 = 1984 − 1980 = 4. We get the message back.
Exam tip

Remember the order: choose p and q, then n and φ(n), then e and d. Encrypt with c = me mod n and decrypt with m = cd mod n.

Hashing passwords

Passwords should not be encrypted, because anyone with the key could decrypt them all. They are hashed instead.

  • A hash function, such as SHA-256, turns any input into a fixed-size value. It cannot be reversed.
  • To log in, the server hashes the typed password and compares the two hashes.
  • A random salt is added to each password before hashing, so two users with the same password get different hashes.

MySQL 8.4 stores account passwords this way. Its default method, caching_sha2_password, uses salted SHA-256.

Common mistake

Hashing is not encryption. Encryption can be undone with the key; a hash cannot be undone at all. Use encryption for data you must read back, and hashing for passwords you only need to check.

Digital signatures

A digital signature proves who sent a message and that it was not changed. It uses the key pair the other way round.

  1. The sender hashes the message.
  2. The sender encrypts the hash with their private key. This is the signature, sent with the message.
  3. The receiver decrypts the signature with the sender's public key and also hashes the message.
  4. If the two hashes match, the message is genuine and unchanged.

Only the owner has the private key, so only they could have made the signature. The sender also cannot later deny sending it. This is called non-repudiation.

Certificates and PKI

Public keys raise one more question: how do you know a public key really belongs to your bank, and not to an attacker pretending to be the bank? The answer is a certificate.

Definitions
  • A digital certificate is an electronic document that links a public key to its owner. It holds the owner's name, the public key, the dates it is valid and the signature of a certificate authority. The common format is X.509.
  • A certificate authority (CA) is a trusted organization that checks identities and signs certificates.
  • Public key infrastructure (PKI) is the whole set of CAs, policies, software and procedures used to create, share, store, check and cancel digital certificates.

The parts of a PKI are:

  • Certificate authority (CA): issues and signs certificates. A root CA signs intermediate CAs, which sign server certificates. This is a chain of trust.
  • Registration authority (RA): checks the identity of whoever asks for a certificate, before the CA signs it.
  • Certificate repository: where certificates are published so others can fetch them.
  • Revocation: a certificate revocation list (CRL) or an online check (OCSP) marks certificates that were cancelled, for example after a private key was stolen.
  • Key management: rules for making, storing, renewing and destroying keys.
Example: connecting to a database server

A college app connects to its MySQL server over TLS. The server sends its certificate. The app checks that a CA it trusts signed it, that the name matches the server and that the dates are valid. Only then does it share a session key and send the password. An attacker in the middle cannot show a valid certificate for that name.

In India, the Controller of Certifying Authorities (CCA) licenses the CAs that issue the certificates used for e-filing taxes and e-signing documents.

Worked example: encryption in MySQL 8.4

1. Encrypt connections (data in transit). MySQL 8.4 sets up TLS certificates when it is installed. The DBA can force every connection to use TLS, or require it for one account.

SQL (MySQL 8.4) 
SET PERSIST require_secure_transport = ON;

CREATE USER 'results_app'@'%' IDENTIFIED BY 'App#Key2026'
  REQUIRE SSL;            -- this account must use TLS

SHOW STATUS LIKE 'Ssl_cipher';   -- shows the cipher in use

2. Encrypt stored tables (data at rest). With a keyring component set up, InnoDB can encrypt a table's file on disk. A thief who copies the file sees only ciphertext.

SQL (MySQL 8.4) 
CREATE TABLE fees (
  roll_no INT PRIMARY KEY,
  amount  DECIMAL(10,2),
  paid_on DATE
) ENCRYPTION = 'Y';

3. Encrypt one column. The functions AES_ENCRYPT and AES_DECRYPT encrypt single values. The app must keep the key safe, outside the database.

SQL (MySQL 8.4) 
SET @k = 'a-long-secret-key-kept-by-the-app';

INSERT INTO student_private (roll_no, aadhaar_enc)
VALUES (101, AES_ENCRYPT('1234 5678 9012', @k));

SELECT roll_no, CAST(AES_DECRYPT(aadhaar_enc, @k) AS CHAR) AS aadhaar
FROM student_private;

A user who can read the table but does not have the key sees only binary data in aadhaar_enc.

Merits and demerits (advantages and disadvantages)

Merits (advantages)

  • Protects stolen data: a stolen disk, backup or network capture is useless without the key.
  • Trust over the internet: certificates prove the server is genuine.
  • Integrity and non-repudiation: signatures show a message is unchanged and who sent it.
  • Meets the law: data protection rules expect personal data to be protected.

Demerits (disadvantages)

  • Slower: encrypting and decrypting take CPU time, and encrypted columns are hard to search or index.
  • Key management is hard: if the key is lost, the data is lost; if it is stolen, the protection is gone.
  • PKI costs effort: certificates must be bought or issued, renewed before they expire and revoked when needed.
  • Not a full answer: encryption does not stop an authorized user, or SQL injection through the app, from reading data.

Key points

  • Encryption turns plaintext into ciphertext with a key; decryption reverses it.
  • Symmetric (AES): one shared key, fast, but the key is hard to share.
  • Asymmetric (RSA): public key to encrypt, private key to decrypt; slower; solves key sharing.
  • Passwords are hashed with a salt, not encrypted.
  • A digital signature is a hash encrypted with the sender's private key and checked with their public key.
  • PKI is the system of certificate authorities, certificates, policies and revocation that makes public keys trustworthy. MySQL uses it for TLS connections.
