CAP Theorem

A distributed database keeps copies of data on many servers. When the network between them breaks, it must make a hard choice. The CAP theorem explains that choice.

The setting: copies on many servers

Big NoSQL systems keep copies (replicas) of each item on several servers, often in different cities. This is replication from topic 5.1. Copies make the system fast and keep it running when one server fails.

But copies bring a problem. When a user changes one copy, the change must travel over the network to the other copies. What if the network breaks at that moment? The CAP theorem answers this question.

The three guarantees

Definitions
  • Consistency (C): every read gets the most recent write, or an error. All users see the same data at the same time, whichever server they use.
  • Availability (A): every request to a working server gets a response (not an error). The response may not hold the latest data.
  • Partition tolerance (P): the system keeps working even when the network splits the servers into groups that cannot talk to each other.

A network partition is a break in the network between servers. A cable is cut, a router fails or a data center loses its link. Each group of servers still works, but the groups cannot share changes.

Common mistake

The C in CAP is not the C in ACID. In ACID, consistency means the data obeys the rules (constraints). In CAP, consistency means every copy shows the same, latest value.

The CAP theorem

CAP theorem (Brewer's theorem)

A distributed system with replicated data cannot guarantee all three of consistency, availability and partition tolerance at the same time. It can guarantee at most two.

Eric Brewer stated the idea in the year 2000. Seth Gilbert and Nancy Lynch proved it in 2002. That is why it is also called Brewer's theorem.

Why only two? A worked example

Two servers, S1 in Chennai and S2 in Delhi, keep copies of a bank balance. The balance is ₹5,000 on both.

  1. The network between Chennai and Delhi breaks. This is a partition.
  2. A user in Chennai withdraws ₹4,000 at S1. S1 now shows ₹1,000. It cannot tell S2.
  3. A user in Delhi asks S2 for the balance. What should S2 do?
S2's two choices during the partition
S2 does thisKeepsLoses
Answers with its own copy: ₹5,000Availability (it answered)Consistency (the answer is old)
Refuses: “Please try again later”Consistency (no wrong data)Availability (no answer)

There is no third choice. S2 cannot know about the withdrawal, because the network is broken. So during a partition the system must give up either C or A.

Note

In a system spread over many servers, partitions will happen sooner or later. So P is not really optional. The real choice is: when a partition happens, keep C or keep A? When there is no partition, a good system gives both C and A.

CP, AP and CA systems

The three pairs of the CAP theorem
TypeDuring a partitionExamplesGood for
CP (consistency + partition tolerance)Some servers refuse or wait, so no one sees old dataHBase, MongoDB (default settings), Redis ClusterBanking, ticket booking, stock levels
AP (availability + partition tolerance)All servers keep answering; some answers may be old; copies sync laterApache Cassandra, CouchDB, Amazon DynamoDBSocial media feeds, likes, shopping carts
CA (consistency + availability)Cannot handle a partition; works only on one siteMySQL or PostgreSQL on a single serverSmall systems on one server

Many NoSQL systems let you tune the choice. For example, Cassandra can wait for a majority of copies to agree before it answers. That moves it closer to CP for that query.

Worked examples: choosing CP or AP

To choose, ask one question: “Is an old answer worse than no answer?” If yes, choose CP. If no, choose AP.

Example 1: train ticket booking

Two people must never get the same seat. An old seat count could sell one seat twice. No answer (“try again”) is better than a wrong answer. Choose CP.

Example 2: likes on a video

If a user sees 1,203 likes when the true count is 1,205, no harm is done. But an error page would annoy millions of users. Choose AP.

Example 3: shopping cart

A user must always be able to add items to the cart, even during a network problem. If two copies of the cart differ, the system merges them later. Amazon built DynamoDB this way. Choose AP.

CAP, ACID and BASE

In topic 5.4 we met BASE: basically available, soft state, eventual consistency. BASE is the AP choice of the CAP theorem. The system stays available, and the copies become consistent later.

CP systems behave more like ACID databases. They may need protocols such as two-phase commit or a majority vote. These make users wait during a failure.

Merits and demerits (advantages and disadvantages)

Each choice has its own merits and demerits.

CP systems

Merits (advantages)

  • Users never see old or wrong data.
  • Easy for app developers to reason about.

Demerits (disadvantages)

  • Some requests fail or wait during a partition.
  • Slower, because copies must agree first.

AP systems

Merits (advantages)

  • Always answers, even during a partition.
  • Fast, because each server answers on its own.

Demerits (disadvantages)

  • Users may see old data for a while.
  • Conflicting changes must be merged later.

Key points

  • C: every read sees the latest write. A: every request gets an answer. P: the system works when the network splits.
  • The CAP theorem says a distributed system can guarantee at most two of C, A and P at the same time.
  • Partitions cannot be avoided across many servers, so the real choice during a partition is C or A.
  • CP systems refuse or wait (HBase, MongoDB). AP systems answer with possibly old data (Cassandra, CouchDB, DynamoDB).
  • CA is possible only on a single site, such as MySQL on one server.
  • BASE and eventual consistency are the AP choice. The C in CAP is not the C in ACID.
