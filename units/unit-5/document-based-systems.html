What is a document database?

Definition

A document database (document store) is a NoSQL database that stores data as documents. A document is a set of field and value pairs, usually written in JSON (or XML). Similar documents are grouped into collections. Each document has a unique key, and the database can search on any field inside it.

Think of a student file in the college office. Everything about one student is in one folder: personal details, marks and certificates. You do not need to open three cabinets to see one student. A document works the same way.

A document store is like a key-value store in which the database can look inside the value. That is why it is the most popular NoSQL type.

Documents and collections

Here is one document for a product in an online shop.

JSON document 
{
  "_id": "P1001",
  "name": "Wireless Mouse",
  "price": 599,
  "tags": ["computer", "wireless"],
  "seller": { "name": "Sri Ram Traders", "city": "Erode" },
  "reviews": [
    { "user": "Kavin", "stars": 5 },
    { "user": "Meena", "stars": 4 }
  ]
}
  • Field: a name and its value, such as "price": 599. A value can be a number, string, true or false, a date, an array (list) or another document.
  • Embedded document: a document inside a document, such as seller.
  • Array: a list of values, such as tags or reviews.
  • _id: the unique key of the document, like a primary key.
  • Collection: a group of documents, such as products. It is like a table, but the documents in it need not have the same fields.

Example: different fields in one collection

A products collection can hold a mouse with a "dpi" field and a T-shirt with "size" and "color" fields. In a relational table, you would need a column for every possible field, and most cells would be NULL.

MongoDB stores documents in BSON (binary JSON). BSON is faster to read and supports more types, such as dates.

Embedding and referencing

When two things are related, such as an order and its items, there are two ways to store them.

  • Embedding: put the related data inside the document. One read gets everything.
  • Referencing: keep the related data in another document and store its _id. This is like a foreign key.
Worked example: blog posts and comments

A college blog has posts. Each post has a few comments, and each post has one author who writes many posts.

  • Comments: they belong to one post and are always shown with it. Embed them in the post.
  • Author: one author has many posts, and the author's details can change. Refer to the author by author_id, so the details are stored once.
JSON document 
{
  "_id": 501,
  "title": "Our trip to Yercaud",
  "author_id": 12,
  "comments": [
    { "by": "Priya", "text": "Great photos!" },
    { "by": "Arun",  "text": "Next time, Ooty." }
  ]
}
Rule of thumb

Embed when the data is read together and belongs to one parent. Refer when the data is shared by many documents, changes often or can grow without limit.

Worked example: MongoDB and SQL side by side

We store students in a collection named students. Each command is shown next to the SQL that does the same job on a students table.

Basic operations in SQL (MySQL 8.4) and in MongoDB (mongosh)
TaskSQLMongoDB
InsertINSERT INTO students (roll_no, name, dept) VALUES (101, 'Anitha', 'CSE');db.students.insertOne({ _id: 101, name: "Anitha", dept: "CSE" })
Find all CSE studentsSELECT * FROM students WHERE dept = 'CSE';db.students.find({ dept: "CSE" })
Marks above 80SELECT name FROM students WHERE marks > 80;db.students.find({ marks: { $gt: 80 } }, { name: 1 })
UpdateUPDATE students SET dept = 'IT' WHERE roll_no = 101;db.students.updateOne({ _id: 101 }, { $set: { dept: "IT" } })
DeleteDELETE FROM students WHERE roll_no = 101;db.students.deleteOne({ _id: 101 })
IndexCREATE INDEX idx_dept ON students (dept);db.students.createIndex({ dept: 1 })

Notice three things.

  1. There is no CREATE TABLE. The collection is made when the first document is inserted.
  2. A query is itself a document, such as { dept: "CSE" }.
  3. Operators start with $, such as $gt (greater than) and $set.

You can also search inside arrays and embedded documents. This finds products sold by a seller in Erode.

MongoDB 
db.products.find({ "seller.city": "Erode" })
Common mistake

A typing mistake in a field name, such as dpet for dept, is not an error in MongoDB. The document is saved with the wrong field, and later queries silently miss it. The app must check its data, or you can add a schema validation rule to the collection.

MongoDB and CouchDB

MongoDB

The most used document database. It stores BSON documents in collections and is queried with the mongosh shell or drivers for Java, Python and other languages. It spreads data over servers by sharding and keeps copies in replica sets. By default it is a CP system.

Apache CouchDB

Stores JSON documents and is used through a web (HTTP) interface. It is built for copying data between servers and devices, even ones that go offline. It is an AP system with eventual consistency.

Other document databases include Amazon DocumentDB and Couchbase. Even MySQL 8.4 has a JSON column type and a document store mode.

Merits and demerits (advantages and disadvantages)

Merits (advantages)

  • Natural for apps: a document looks like the objects in the program, so less conversion is needed.
  • Flexible schema: new fields can be added at any time.
  • Fast reads: related data is in one document, so no joins are needed.
  • Rich queries: you can search and index any field, even inside arrays.
  • Scales out: collections can be sharded across many servers.

Demerits (disadvantages)

  • Duplicate data: embedded data may be copied in many documents and must be updated in each.
  • Weak joins: combining data from many collections is slower and harder than SQL joins.
  • No schema check by default: wrong or missing fields are not caught by the database.
  • Large documents: a document that keeps growing (such as endless comments) becomes slow; MongoDB limits a document to 16 MB.

In real life

Online shop catalog

Phones, shoes and books have very different details. Each product is one document with its own fields, so the shop can add a new category without changing a schema.

Mobile app data

A college app stores each user's profile, settings and saved items as one document. The app reads it in one request when the user logs in.

Key points

  • A document database stores data as JSON-like documents grouped into collections.
  • A document has fields; values can be arrays or embedded documents. _id is the unique key.
  • Documents in one collection can have different fields (flexible schema).
  • Embed data that is read together; refer to data that is shared or grows without limit.
  • MongoDB uses commands such as insertOne, find, updateOne and deleteOne.
  • MongoDB and CouchDB are the two best-known document databases.
