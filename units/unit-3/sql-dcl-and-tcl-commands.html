SQL DCL and TCL Commands

DCL decides who may do what to the data. TCL decides when a group of changes becomes permanent or is undone. Together they keep a shared database safe from wrong users and half-done work.

SQL command groups

Groups of SQL commands
GroupFull namePurposeCommands
DDLData definition languageDefine and change the structure of tablesCREATE, ALTER, DROP, TRUNCATE, RENAME
DMLData manipulation languageRead and change the data in tablesSELECT, INSERT, UPDATE, DELETE
DCLData control languageGive and take away access rightsGRANT, REVOKE
TCLTransaction control languageManage transactionsCOMMIT, ROLLBACK, SAVEPOINT

Some books list SELECT on its own as DQL (data query language). TCL is sometimes counted with DML, since it controls DML changes.

DCL: GRANT

GRANT gives privileges on a database object to users or roles. The DCL commands are used to enforce database security when many users share one database.

SQL 
GRANT privilege_name [, privilege_name ...]
ON object_name
TO {user_name | PUBLIC | role_name}
[WITH GRANT OPTION];
  • privilege_name: the right being given, such as SELECT, INSERT, UPDATE, DELETE, EXECUTE, or ALL PRIVILEGES.
  • object_name: a database object such as a table, view or stored procedure.
  • user_name: the user who receives the privilege. In MySQL, a user is written as 'name'@'host'.
  • PUBLIC: every user (standard SQL; MySQL does not support it).
  • role_name: a named set of privileges.
  • WITH GRANT OPTION: lets the user pass the same privilege on to other users.
SQL 
-- read-only access to one table
GRANT SELECT ON Employee_Info TO user1;

-- several privileges at once, and the right to pass them on
GRANT SELECT, INSERT, UPDATE ON college.marks TO 'hod'@'localhost' WITH GRANT OPTION;

-- privilege on chosen columns only
GRANT UPDATE (PhoneNumber, Address) ON Employee_Info TO 'clerk'@'localhost';

-- every privilege on every table of a database
GRANT ALL PRIVILEGES ON college.* TO 'admin'@'localhost';

A grant chain and what happens when it is broken are explained in Access Control Based on Privileges.

DCL: REVOKE

REVOKE withdraws privileges that were given with GRANT.

SQL 
REVOKE privilege_name [, privilege_name ...]
ON object_name
FROM {user_name | PUBLIC | role_name};
SQL 
REVOKE SELECT ON Employee_Info FROM user1;
REVOKE GRANT OPTION ON college.marks FROM 'hod'@'localhost';   -- keeps the privileges, removes the right to pass them on
REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'admin'@'localhost';
Common mistake

GRANT uses TO; REVOKE uses FROM. REVOKE SELECT ON Employee_Info TO user1; is a syntax error.

In standard SQL, REVOKE ... CASCADE also takes the privilege away from everyone who received it through this user, and RESTRICT refuses to revoke if anyone did. SHOW GRANTS FOR 'name'@'host'; lists a MySQL user's privileges.

Roles and the lab example

A role groups privileges, so they can be given to many users at once. When a job changes, you change the role instead of every user. See Role-Based Access Control for more.

SQL 
CREATE ROLE 'store_staff';
GRANT SELECT, INSERT, UPDATE ON GameStore.* TO 'store_staff';
GRANT 'store_staff' TO 'ravi'@'localhost', 'meena'@'localhost';
SET DEFAULT ROLE 'store_staff' TO 'ravi'@'localhost', 'meena'@'localhost';

In the lab, a new customer user may only browse the games, not change them:

SQL 
CREATE USER 'customer'@'localhost' IDENTIFIED BY '';
GRANT SELECT ON Games TO 'customer'@'localhost';
REVOKE INSERT, UPDATE, DELETE ON Games FROM 'customer'@'localhost';
SHOW GRANTS FOR 'customer'@'localhost';

Logged in as customer, SELECT * FROM Games; works, but UPDATE Games SET CurrentPrice = 0; fails with “UPDATE command denied to user”.

TCL: COMMIT, ROLLBACK and SAVEPOINT

TCL commands
CommandWhat it does
COMMIT;Saves all changes made in the current transaction permanently. They can no longer be rolled back.
ROLLBACK;Undoes all changes not yet committed, returning the database to its last committed state.
SAVEPOINT name;Sets a point inside the transaction to which you can roll back without undoing everything.
ROLLBACK TO name;Undoes only the changes made after that savepoint.

START TRANSACTION (BEGIN TRANSACTION in SQL Server) and SET TRANSACTION also control transactions; see SQL Facilities for Concurrency and Recovery.

COMMIT 
START TRANSACTION;
UPDATE Shippings SET status = 'Shipped'
  WHERE shipping_id = 1;
COMMIT;
ROLLBACK 
START TRANSACTION;
DELETE FROM Orders WHERE order_id = 5;
-- after some checks, cancel
ROLLBACK;   -- order 5 is back
SAVEPOINT 
START TRANSACTION;
UPDATE Customers SET age = 32
  WHERE customer_id = 1;
SAVEPOINT SP1;
UPDATE Customers SET country = 'Canada'
  WHERE customer_id = 2;
ROLLBACK TO SP1;  -- only customer 2's change is undone
COMMIT;           -- customer 1's change is saved

Savepoints are covered in detail on Save Points.

Steps for commit and rollback

The game purchase from the lab, written as a transaction that either commits or rolls back:

  1. Start the transaction: START TRANSACTION;. From here on, changes are not permanent.
  2. Record the purchase: INSERT INTO Transactions(TransactionDate, UserID) VALUES (NOW(), 1); and save the new ID with SELECT LAST_INSERT_ID() INTO @T_ID;
  3. Copy the cart: insert each game in the user's cart into PurchaseHistory with its current price.
  4. Empty the cart: DELETE FROM Cart WHERE UserID = 1;
  5. Check: if any statement failed (for example, a game was removed from the store), go to step 6. Otherwise go to step 7.
  6. Roll back: ROLLBACK; undoes steps 2 to 4. The cart is still full and no purchase is recorded.
  7. Commit: COMMIT; makes steps 2 to 4 permanent together. Other users now see the purchase.
  8. Verify: SELECT from Transactions, PurchaseHistory and Cart to see the result.

In a stored procedure, step 5 is done by an error handler:

SQL 
DELIMITER //
CREATE PROCEDURE checkout(IN p_user INT)
BEGIN
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    ROLLBACK;                      -- any error: undo everything
  END;
  START TRANSACTION;
  INSERT INTO Transactions(TransactionDate, UserID) VALUES (NOW(), p_user);
  INSERT INTO PurchaseHistory(TransactionID, GameID, SalePrice)
    SELECT LAST_INSERT_ID(), Cart.GameID, Games.CurrentPrice
    FROM Cart INNER JOIN Games ON Cart.GameID = Games.GameID
    WHERE Cart.UserID = p_user;
  DELETE FROM Cart WHERE UserID = p_user;
  COMMIT;                          -- no error: save everything
END //
DELIMITER ;

In real life

College ERP

Students get SELECT on their own marks through a view, staff get UPDATE on the marks of their own subjects, and only the exam cell can GRANT. Each marks entry is a transaction: if saving one subject fails, the whole entry is rolled back.

Online shop

The website connects as a user with only SELECT, INSERT and UPDATE on the order tables. Even if an attacker finds a bug, they cannot DROP a table, because that privilege was never granted.

Key points

  • DCL: GRANT gives privileges, REVOKE takes them away. GRANT ... TO; REVOKE ... FROM.
  • WITH GRANT OPTION lets the receiver pass the privilege on.
  • Roles group privileges so they can be given to many users at once.
  • TCL: COMMIT saves, ROLLBACK undoes, SAVEPOINT marks a point for a partial rollback.
  • A transaction runs from START TRANSACTION to COMMIT or ROLLBACK.
  • DCL is about security; TCL is about atomicity and durability.
