Transaction Concepts

Moving money between two bank accounts takes several steps, but it must behave like one step. This page explains what a transaction is, how it reads and writes data, and the states it passes through.

What is a transaction?

A student pays ₹50 to a friend using a banking app. The bank must take ₹50 out of the student's account A and add ₹50 to the friend's account B. These are two separate changes. If only the first one happens, ₹50 simply disappears. So the bank treats the two changes as one unit of work.

Definition

A transaction is a collection of operations that forms a single logical unit of work. It reads and possibly updates data items. A transaction must run completely or not at all.

A transaction is usually started by a program written in a language such as Java or Python, which sends SQL to the database (for example through JDBC or ODBC). In the textbook, a transaction is written between the statements begin transaction and end transaction. In SQL, it starts with START TRANSACTION and ends with COMMIT or ROLLBACK.

Example: the funds-transfer transaction

Ti transfers ₹50 from account A to account B.

Ti: read(A);
    A := A − 50;
    write(A);
    read(B);
    B := B + 50;
    write(B).

This example is used all through Unit III, so it is worth remembering.

Read and write operations

A transaction does its work in main memory. Each transaction has its own buffer (work area) in main memory. Data moves between the database and this buffer with two operations.

read(X)

Copies the data item X from the database into a variable, also called X, in the transaction's buffer.

write(X)

Copies the value of the variable X from the buffer back to the data item X in the database.

Calculations such as A := A − 50 change only the copy in the buffer. The database changes only when write(A) runs.

Note

Even after write(X), the new value may sit in a buffer block in main memory for a while before it reaches the disk. This is why the database also keeps a log on disk. Recovery from failures (topic 3.9) depends on this log.

Commit and abort

Every transaction ends in one of two ways.

The two ways a transaction can end
EndMeaningSQL statement
CommitThe transaction finished successfully. Its changes become permanent.COMMIT
AbortThe transaction did not finish. All its changes are undone (rolled back), as if it never ran.ROLLBACK

Once a transaction has committed, it cannot be undone by aborting it. If its effect was wrong, another transaction must be run to reverse it. This is called a compensating transaction, for example a refund.

Transaction states

A transaction is always in one of five states.

The five transaction states
StateThe transaction is in this state when
ActiveIt is running. This is the first state.
Partially committedIts last statement has run, but its changes may still be only in main memory.
FailedIt finds that normal execution can no longer go on, because of an error or a system failure.
AbortedIt has been rolled back, and the database is back to its state before the transaction started.
CommittedIt has completed successfully. Enough information is on disk to rebuild its changes after a failure.

What happens after an abort

After a transaction is aborted, the system has two choices.

  • Restart the transaction, if it failed because of a hardware or software problem that was not caused by its own logic. A restarted transaction is a new transaction.
  • Kill the transaction, if it failed because of an error in its own logic (for example, bad input or a missing record). The program must be fixed first.
Common mistake

Partially committed is not the same as committed. A partially committed transaction can still fail, for example if the power goes off before its changes reach the disk. Draw the arrow from partially committed to failed in your answer.

Why transactions need care

Two things can go wrong with transactions. The rest of Unit III deals with them.

Failures

The system can crash in the middle of a transaction. Then some of its writes are done and some are not. The recovery system must undo or redo work so that each transaction happens completely or not at all. See Transaction Recovery.

Concurrent execution

Many transactions run at the same time to keep the CPU and disks busy. Their steps can mix in harmful ways. The concurrency-control system stops this. See Concurrency Control.

The rules that a transaction must follow are called the ACID properties, the next topic.

In real life

UPI payment

When a UPI payment fails halfway, the app shows “money will be refunded”. The debit already happened, so the bank runs a reverse entry, which is a compensating transaction.

Train ticket booking

Booking a seat must mark the seat as taken and record the passenger in one transaction. If the booking fails, the seat is released, as if the booking never started.

Key points

  • A transaction is a single logical unit of work that runs completely or not at all.
  • read(X) copies X from the database to the transaction's buffer; write(X) copies it back.
  • A transaction ends with commit (changes kept) or abort (changes rolled back).
  • The five states are active, partially committed, failed, aborted and committed.
  • Partially committed means the last statement ran; the transaction can still fail.
  • After an abort, the system can restart or kill the transaction.
  • A committed transaction can only be reversed by a compensating transaction.
