Concurrency Control and Need for Concurrency

Running many transactions at once makes a database fast, but their steps can interfere. This page shows the classic problems that appear without control, and the main ways a DBMS prevents them.

Need for concurrency

A railway booking site gets thousands of requests every minute. If the database ran them one at a time (a serial schedule), each user would wait for everyone in front of them. So databases run many transactions concurrently, with their steps interleaved.

Better throughput and resource use

A transaction spends much of its time waiting for the disk. While one waits, another can use the CPU. More transactions finish per second, and the CPU and disks stay busy.

Shorter waiting time

A short transaction need not wait behind a long one. This lowers the average response time, so users get answers faster.

What is concurrency control?

Definition

Concurrency control is the part of the DBMS that controls the interaction among concurrent transactions, so that the database stays consistent. It allows only serializable schedules, and preferably recoverable and cascadeless ones.

Without concurrency control, the interleaved steps of transactions can break isolation and leave the database wrong. The next sections show the classic problems. Each uses the account balance A = ₹1000.

Lost update problem

Two transactions read the same item and both update it. The second write overwrites the first, so one update is lost.

Lost update: T1 withdraws ₹50, T2 deposits ₹100
T1T2A in database
read(A) → 10001000
read(A) → 10001000
A := A − 50
write(A)		950
A := A + 100
write(A)		1100

The correct final balance is 1000 − 50 + 100 = ₹1050. The database shows ₹1100, so T1's withdrawal is lost. This is also called a write-write conflict.

Dirty read problem

A transaction reads a value written by another transaction that has not committed. If that transaction then aborts, the value read was never valid. Elmasri calls this the temporary update problem.

Dirty read: T1 aborts after T2 reads its value
T1T2A in database
read(A)
A := A − 50
write(A)		950 (uncommitted)
read(A) → 950950
abort1000 (rolled back)
commit (used 950)1000

T2 worked with ₹950, a value that never existed in any committed state. This is a write-read conflict. It also causes the cascading rollback problem.

Unrepeatable read problem

A transaction reads the same item twice and gets different values, because another transaction changed and committed it in between. It is also called the non-repeatable read or inconsistent retrieval problem.

Unrepeatable read
T1T2A in database
read(A) → 10001000
read(A)
A := A − 50
write(A)
commit		950
read(A) → 950950

T1 might check that the balance is enough, then read it again to print a receipt, and get a different number. This is a read-write conflict.

Incorrect summary problem

One transaction computes a total (an aggregate, such as SUM) while another transaction is updating some of the items. The total uses some old and some new values, so it is wrong.

Incorrect summary: T1 moves ₹50 from A to B while T2 adds A + B
T1T2
sum := 0
read(A) → 1000; sum := 1000
read(A); A := A − 50; write(A)
read(B); B := B + 50; write(B)
read(B) → 2050; sum := 3050

With A = ₹1000 and B = ₹2000, the true total is always ₹3000. T2 reads A before the transfer and B after it, so it reports ₹3050.

Phantom problem

A transaction runs a query over a range of rows (a condition) twice. In between, another transaction inserts (or deletes) a row that matches the condition and commits. The second query sees a row that was not there before, a phantom.

Phantom
T1T2
SELECT COUNT(*) FROM student WHERE dept = 'CSE'; → 3
INSERT INTO student VALUES (104, 'Divya', 'CSE');
COMMIT;
SELECT COUNT(*) FROM student WHERE dept = 'CSE'; → 4

The difference from an unrepeatable read: here no existing row changed. A new row appeared. Locking only the rows that T1 read does not stop it, because the new row did not exist when T1 read.

Concurrency control protocols

A concurrency control protocol (or scheme) is a set of rules that every transaction follows so that only safe schedules happen. The main kinds are:

Kinds of concurrency control protocols
ProtocolIdeaExample
Lock-basedA transaction must lock an item before using it. Conflicting requests wait.Two phase locking
Timestamp-basedEach transaction gets a timestamp when it starts. Conflicting operations must run in timestamp order, or the late transaction is rolled back.Timestamp ordering protocol
Validation-based (optimistic)Transactions run freely on private copies. Before commit, the system checks for conflicts and rolls back if there are any.Optimistic concurrency control
MultiversionEach write makes a new version of the item. Readers read an older, committed version and never wait for writers.Snapshot isolation in MySQL InnoDB, Oracle and PostgreSQL

Lost updateWrite-writeExclusive locks held until commit
Dirty readWrite-readReading only committed data (strict 2PL)
Unrepeatable readRead-writeShared locks held until commit
Incorrect summaryRead-writeShared locks on every item summed
PhantomInsert or delete in a rangeIndex (range) locks, or the SERIALIZABLE isolation level
Exam tip

For “discuss the need for concurrency control”, start with the two merits of concurrency, then give each problem as a two-column table with values, then list the protocols. The SQL isolation levels are defined by which of these problems they allow.

In real life

Tatkal booking

At 10 a.m. many users try to book the last few berths at the same moment. Without concurrency control, two users could both see “1 seat left” and both be given the same berth (a lost update).

Joint bank account

Two people use the same account at two ATMs at once. The bank's database locks the balance, so one withdrawal waits for the other to finish.

Key points

  • Concurrency gives better throughput, better resource use and shorter waiting time.
  • Concurrency control keeps concurrent schedules serializable and recoverable.
  • Lost update: a later write overwrites an earlier one (write-write).
  • Dirty read: reading uncommitted data that may be rolled back (write-read).
  • Unrepeatable read: the same item gives two values in one transaction (read-write).
  • Incorrect summary: an aggregate mixes old and new values.
  • Phantom: a repeated range query sees newly inserted rows.
  • Protocols: lock-based, timestamp-based, validation-based and multiversion.
