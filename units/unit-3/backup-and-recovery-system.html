Backup and Recovery System

Logs and crash recovery protect a database when memory is lost. They cannot help when the disk itself is destroyed, or when someone deletes a table by mistake. For that, a DBMS needs backups and a plan to restore them.

Backup and recovery

Definition

A backup is a copy of the database, taken at a point in time and kept in a safe, separate place. Recovery is restoring the database to a correct, consistent state after a failure, using the backups and the logs.

Data can be lost in many ways:

  • Media failure: a disk or SSD breaks. RAID survives one failed disk, but not a fire, a theft or a failed controller.
  • Human error: someone runs DROP TABLE or an UPDATE without a WHERE clause. The DBMS carries out the mistake and copies it to every replica at once.
  • Software bugs and attacks: a faulty program or ransomware corrupts or encrypts the data.
  • Disasters: flood, fire or power failure destroys a whole data centre.

Crash recovery from Transaction Recovery handles only the loss of main memory. Every failure above needs a backup.

Two numbers describe how good a backup plan is:

  • Recovery point objective (RPO): how much recent data you can afford to lose, for example “at most 15 minutes”.
  • Recovery time objective (RTO): how long the restore may take, for example “back online within 1 hour”.

Full, incremental and differential backups

  • A full backup copies the whole database.
  • An incremental backup copies only what changed since the last backup of any kind, full or incremental.
  • A differential backup copies everything that changed since the last full backup.

Worked example: a weekly plan

A college database takes a full backup every Sunday night and a smaller backup every other night. The disk fails on Thursday morning.

Which backups are needed to restore on Thursday morning?
PlanSunMonTueWedBackups to restore
Full + incrementalFullChanges of MonChanges of TueChanges of WedSun full, then Mon, Tue and Wed incremental backups (4 backups)
Full + differentialFullChanges of MonChanges of Mon–TueChanges of Mon–WedSun full, then Wed differential (2 backups)

Either way, the changes made on Thursday morning before the failure are not in any backup. To get them back, apply the log, as in point-in-time recovery below.

Exam tip

Remember the difference by what each backup is compared with. Incremental: since the last backup. Differential: since the last full backup. A short table with the restore steps earns the marks.

Other ways to classify backups

Backup classifications
KindMeaningExample
LogicalThe data as SQL statements or text that can recreate itmysqldump output: CREATE TABLE and INSERT statements
PhysicalAn exact copy of the database files on diskCopying the data directory; MySQL Enterprise Backup
Hot (online)Taken while the database runs and accepts updatesmysqldump --single-transaction on InnoDB tables
Cold (offline)Taken after the database is shut downStop the server, copy the files, start it again

Logical backups are portable between versions and machines but slow to restore for big databases. Physical backups are fast to restore but tied to the same product and version.

Loss of non-volatile storage: the archival dump

The textbook method for surviving a disk failure is to dump the entire database to stable storage, such as tape or another site, from time to time. To take a dump, the system:

  1. Writes all log records in main memory to stable storage.
  2. Writes all changed buffer blocks to disk.
  3. Copies the contents of the database to stable storage.
  4. Writes a <dump> record to the log on stable storage.

After a disk failure, the system restores the database from the latest dump, then uses the log to redo every transaction that committed after the <dump> record. No undo is needed. This is the same idea as a full backup followed by the binary log.

A simple dump stops all transactions while it runs. A fuzzy dump lets transactions continue during the dump, and uses the log to fix up the changes made while copying.

Binary log and point-in-time recovery

MySQL writes every committed change to the binary log, a series of files on disk. It is separate from the InnoDB redo log. The redo log is for crash recovery and is reused in a circle; binary log files are kept as long as you need them. The binary log is turned on by default in MySQL 8.

Point-in-time recovery brings the database back to its state at any chosen moment:

  1. Restore the latest full backup taken before that moment.
  2. Replay the binary log from the point where the backup was taken, up to the chosen moment.

Example. The full backup was taken on Sunday at 23:00. On Wednesday at 11:00, someone runs DROP TABLE marks; by mistake. Restore the Sunday backup, then replay the binary log from Sunday 23:00 up to Wednesday 10:59:59, stopping just before the bad statement. Every other change up to that moment is kept.

Shell 
mysql -u root -p college < sunday_full.sql
mysqlbinlog --stop-datetime="2025-03-12 10:59:59" binlog.000041 binlog.000042 | mysql -u root -p

The same log, sent to another server, keeps a replica up to date. That is how MySQL replication works.

Backup and restore in MySQL

Shell 
# Logical full backup of one database, without locking InnoDB tables
mysqldump -u root -p --single-transaction --routines --triggers college > college_full.sql

# Backup of every database
mysqldump -u root -p --single-transaction --all-databases > all_full.sql

# Restore
mysql -u root -p college < college_full.sql
  • --single-transaction starts a REPEATABLE READ transaction and dumps from its snapshot, so the backup is consistent and other users can keep working.
  • --routines and --triggers also save stored procedures, functions and triggers.
  • For incremental backups in MySQL, save the binary log files written since the last full backup. Physical tools such as MySQL Enterprise Backup can also take incremental backups of the data files.

Remote backup systems

For high availability, the whole database is kept at a second site, the remote backup, far from the primary site. The primary sends its log records to the backup, which applies them to stay up to date. If the primary is destroyed, the backup takes over.

  • Detection of failure: the backup must know when the primary has failed, using several independent communication links so that a broken link is not mistaken for a failed site.
  • Transfer of control: the backup becomes the new primary. When the old primary recovers, it can become the backup.
  • Time to recover: the backup takes checkpoints of its own, so it has little log to process at takeover. A hot-spare backup applies log records as they arrive, so it can take over almost at once.

When is a transaction committed? There is a trade-off between speed and safety:

Commit durability levels
LevelCommits when the commit record is…Risk
One-safeWritten to stable storage at the primaryFastest; recent commits can be lost if the primary is destroyed
Two-very-safeWritten at both primary and backupNo loss, but no transaction can commit while either site is down
Two-safeWritten at both sites when both are up; at the primary alone when the backup is downGood balance; used most often

A good backup plan

  • 3-2-1 rule: keep at least 3 copies of the data, on 2 different kinds of storage, with 1 copy at another site.
  • Automate backups on a schedule, and keep the binary logs between them.
  • Test restores regularly. A backup that has never been restored may not work when it is needed.
  • Protect backups with encryption and limited access, since they hold all the data.
  • Remember: RAID and replication are not backups. They copy mistakes and deletions at once.

In real life

Banks

Banks keep a disaster recovery site in another city. Log records flow to it all the time, so if the main data centre is lost, the other site can take over with little or no data lost.

Your phone

A phone backs up to the cloud every night, but only the photos and chats that changed. That is an incremental backup. Restoring on a new phone downloads the full set plus every change since.

Key points

  • Backup: a copy of the database in a safe place. Recovery: restoring a correct state after failure.
  • Full copies everything; incremental copies changes since the last backup; differential copies changes since the last full backup.
  • Restore with incremental: full plus every incremental. With differential: full plus the latest differential.
  • Logical backups are SQL text; physical backups are file copies. Hot backups run while the database is in use.
  • Point-in-time recovery: restore the last full backup, then replay the binary log up to the chosen moment.
  • A remote backup site applies the primary's log and takes over if the primary fails.
  • RAID and replication are not backups.
