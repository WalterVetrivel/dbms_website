Locking Protocols

The most common way to control concurrent transactions is to make them lock data before using it. This page explains the two lock modes, when a lock can be granted, and why the timing of unlocks matters.

What is a lock?

Definition

A lock is a mechanism that controls concurrent access to a data item. A transaction may access a data item only if it holds a lock on that item. While one transaction holds a lock, a lock may be denied to other transactions to prevent wrong results.

To keep a schedule serializable, data items should be accessed in a mutually exclusive way: while one transaction is changing an item, no other transaction may change it. Locking is the most widely used way to do this.

Shared and exclusive locks

Shared lock (S)

If Ti holds a shared-mode lock on Q, Ti can read Q but cannot write it. Many transactions can hold S locks on Q at the same time. Requested with lock-S(Q).

Exclusive lock (X)

If Ti holds an exclusive-mode lock on Q, Ti can both read and write Q. No other transaction can hold any lock on Q. Requested with lock-X(Q).

A transaction releases a lock with unlock(Q). It asks for the mode it needs: S if it only reads Q, X if it will write Q. The request goes to the concurrency-control manager, and the transaction can go on only after the lock is granted.

The compatibility matrix

Suppose Ti asks for a lock of mode A on Q, while another transaction Tj already holds a lock of mode B on Q. If Ti can be granted the lock at once, mode A is compatible with mode B. This is shown in a matrix, comp(A, B).

Only shared with shared is compatible. So many readers can work together, but a writer must be alone. If the lock is not compatible, the requesting transaction waits until all incompatible locks held by others are released.

Example: unlocking too early

Accounts A = ₹100 and B = ₹200. T1 moves ₹50 from B to A. T2 displays A + B, which should be ₹300.

Transaction 
T1: lock-X(B);
    read(B);
    B := B − 50;
    write(B);
    unlock(B);
    lock-X(A);
    read(A);
    A := A + 50;
    write(A);
    unlock(A).
Transaction 
T2: lock-S(A);
    read(A);
    unlock(A);
    lock-S(B);
    read(B);
    unlock(B);
    display(A + B).

Run serially, T2 always shows ₹300. But this concurrent schedule is possible:

Schedule 1: T2 displays ₹250

read(B); B := B − 50; write(B)
unlock(B)		B = 150 on disk
lock-S(A)grant-S(A, T2)
read(A) → 100
unlock(A)
lock-S(B)grant-S(B, T2)
read(B) → 150
unlock(B)
display(A + B) → 250
lock-X(A)grant-X(A, T1)
read(A); A := A + 50; write(A)
unlock(A)		A = 150 on disk

T2 shows ₹250, which is wrong. Every access was locked, yet the result is wrong. The reason: T1 unlocked B too early, so T2 saw the database halfway through T1's transfer.

Common mistake

“Using locks” is not enough for serializability. When locks are released matters. A rule about lock and unlock timing, such as two phase locking, is needed.

If instead T1 and T2 delay their unlocks to the end, the wrong total cannot happen. But then a deadlock becomes possible: T1 holds X on B and waits for A, while T2 holds S on A and waits for B. See Deadlock.

What is a locking protocol?

Definition

A locking protocol is a set of rules, followed by every transaction, that says when a transaction may lock and unlock each data item. A locking protocol restricts the set of possible schedules, so that only conflict serializable ones can happen.

A schedule S is legal under a protocol if it can be produced by transactions that follow the protocol's rules. A protocol ensures conflict serializability if all its legal schedules are conflict serializable.

Examples of locking protocols:

  • Two phase locking (2PL) and its strict and rigorous forms (next topic).
  • Graph-based protocols, such as the tree protocol, where items must be locked in a fixed order.
  • Multiple granularity locking, where a transaction can lock a whole table, a page or a single row, using intention locks (IS, IX, SIX).

The lock manager

The lock manager is the part of the DBMS that grants and releases locks. Transactions send it lock and unlock requests as messages, and it replies with grant messages (or asks the transaction to roll back, if there is a deadlock).

It keeps a lock table in main memory. The lock table is usually a hash table on the name of the data item. For each item it stores a linked list of requests, in the order they arrived. Each request records the transaction, the lock mode and whether it has been granted.

  • Lock request: the request is added to the end of the item's list. It is granted if it is compatible with all earlier requests, and all earlier requests have been granted.
  • Unlock: the request is removed, and the next waiting requests are checked to see whether they can now be granted.
  • Abort: all requests of the aborted transaction are removed.

Starvation

Suppose T2 holds an S lock on Q, and T1 asks for an X lock on Q, so T1 waits. Then T3 asks for an S lock on Q. S is compatible with S, so T3 is granted at once. Then T4 comes for S, and so on. Each time one reader leaves, another has arrived. T1 may never get its X lock.

Definition

Starvation is a situation where a transaction waits indefinitely for a lock and never makes progress, although the system as a whole keeps working.

How to avoid it: grant a lock on Q only if no earlier request for Q is still waiting. Then T3's S request waits behind T1's X request, and requests are served in the order they arrived (first come, first served).

In real life

Library reference book

Many students may read a reference book in the library at once (shared). But to correct its pages, the librarian takes it away from everyone (exclusive).

MySQL row locks

InnoDB uses shared and exclusive row locks. SELECT ... FOR SHARE takes S locks and SELECT ... FOR UPDATE takes X locks. See SQL Facilities.

Key points

  • A transaction must hold a lock on an item before it accesses it.
  • Shared (S): read only, many holders. Exclusive (X): read and write, one holder.
  • Compatibility: only S with S is true; any pair with X is false.
  • An incompatible request waits until the conflicting locks are released.
  • Unlocking too early can still give wrong results (T2 displays 250 instead of 300).
  • A locking protocol is a set of rules for when to lock and unlock, to ensure serializability.
  • The lock manager keeps a lock table: a hash table of items with lists of requests.
  • Starvation: a transaction waits forever; avoided by serving requests in arrival order.
