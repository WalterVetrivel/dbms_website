Serializability

A concurrent schedule is safe if it has the same effect as some serial schedule. This page shows two ways to define “the same effect”, conflict and view serializability, and the precedence graph test used in exams.

What is serializability?

Definition

A concurrent schedule is serializable if it is equivalent to a serial schedule of the same transactions.

A serial schedule always keeps the database consistent (see Schedules). So a serializable schedule does too, while still letting transactions run at the same time.

There are two kinds of equivalence, which give two kinds of serializability:

  1. Conflict serializability, based on the order of conflicting instructions.
  2. View serializability, based on what each read sees and who writes last.

We look only at read and write instructions. Calculations such as A := A − 50 happen in the transaction's own buffer, so they do not affect other transactions.

Conflicting instructions

Definition

Instructions Ii and Ij of different transactions Ti and Tj conflict if they access the same data item Q and at least one of them is a write.

The four cases for two instructions on the same item Q
IiIjConflict?Why
read(Q)read(Q)NoBoth read the same value, whatever the order.
read(Q)write(Q)YesWhether Ii sees the old or new value depends on the order.
write(Q)read(Q)YesWhether Ij sees Ii's value depends on the order.
write(Q)write(Q)YesThe final value of Q depends on which write is last.

If two consecutive instructions of different transactions do not conflict, we can swap them. The result of the schedule does not change. Instructions on different items never conflict.

Conflict serializability

Definitions
  • Schedules S and S′ are conflict equivalent if S can be turned into S′ by a series of swaps of non-conflicting instructions.
  • A schedule is conflict serializable if it is conflict equivalent to a serial schedule.

Example: schedule 7 is not conflict serializable

Schedule 7

Every pair here conflicts, so no swap is possible. The schedule is neither ⟨T3, T4⟩ nor ⟨T4, T3⟩. It is not conflict serializable.

View serializability

Definition

Schedules S and S′ with the same transactions are view equivalent if, for every data item Q, these three conditions hold:

  1. Initial read: if Ti reads the initial value of Q in S, then Ti also reads the initial value of Q in S′.
  2. Reads-from: if Ti reads a value of Q written by Tj in S, then Ti also reads the value of Q written by Tj in S′.
  3. Final write: the transaction that does the final write(Q) in S also does the final write(Q) in S′.

A schedule is view serializable if it is view equivalent to a serial schedule.

Conditions 1 and 2 make sure every transaction reads the same values, so it computes the same results. Condition 3 makes sure the database ends in the same state.

Example: view serializable but not conflict serializable

Schedule 8
T3T4T6
read(Q)
write(Q)
write(Q)
write(Q)

Compare with the serial schedule ⟨T3, T4, T6⟩:

  • T3 reads the initial value of Q in both.
  • No transaction reads a value written by another.
  • T6 does the final write of Q in both.

So schedule 8 is view serializable. But it contains schedule 7's pattern, so it is not conflict serializable.

T4 and T6 write Q without reading it first. These are called blind writes. A view serializable schedule that is not conflict serializable always has blind writes.

Note

Every conflict serializable schedule is also view serializable, but not the other way round. Testing for view serializability is hard (it is NP-complete), so real systems use conflict serializability.

Testing with a precedence graph

Swapping by hand is slow. The quick test draws a precedence graph (also called a serialization graph).

  1. Vertices: draw one node for each transaction in the schedule.
  2. Edges: draw an edge Ti → Tj if, on the same item Q, one of these happens:
    • Ti does write(Q) before Tj does read(Q);
    • Ti does read(Q) before Tj does write(Q);
    • Ti does write(Q) before Tj does write(Q).
  3. Check for a cycle. If the graph has a cycle, the schedule is not conflict serializable. If it has no cycle, the schedule is conflict serializable.
  4. Find the serial order by topological sorting: repeatedly take a node with no incoming edges.

An edge Ti → Tj means “in any equivalent serial schedule, Ti must come before Tj”. A cycle asks for Ti before Tj and Tj before Ti, which is impossible.

Schedules 1 and 3

One edge T1 → T2 (on A and B). No cycle, so conflict serializable, equivalent to ⟨T1, T2⟩.

Schedule 2

One edge T2 → T1. No cycle, equivalent to ⟨T2, T1⟩.

Schedule 4

read(A) of T1 before write(A) of T2 gives T1 → T2. write(A) of T2 before write(A) of T1 gives T2 → T1. A cycle, so not conflict serializable.

Worked example

Question: Is this schedule conflict serializable? If yes, give an equivalent serial schedule.

The schedule
#T1T2T3
1read(A)
2read(B)
3write(A)
4read(A)
5write(B)
6write(A)
7read(B)
8write(B)

Solution. List the conflicting pairs (same item, different transactions, at least one write):

Conflicting pairs and edges
ItemConflicting pair (earlier, later)Edge
Aread(A) of T1 (1), write(A) of T3 (6)T1 → T3
Awrite(A) of T1 (3), read(A) of T3 (4)T1 → T3
Awrite(A) of T1 (3), write(A) of T3 (6)T1 → T3
Bread(B) of T2 (2), write(B) of T3 (8)T2 → T3
Bwrite(B) of T2 (5), read(B) of T3 (7)T2 → T3
Bwrite(B) of T2 (5), write(B) of T3 (8)T2 → T3

There is no cycle, so the schedule is conflict serializable. T1 and T2 have no incoming edges, and T3 must come after both. So both ⟨T1, T2, T3⟩ and ⟨T2, T1, T3⟩ are equivalent serial schedules.

Exam tip

Number the rows of the schedule first. Then go item by item, and for each item list the pairs in time order. This avoids missing an edge. Draw each edge only once, and label it with the item.

In real life

Locking gives serializability

Databases do not draw precedence graphs while running. Instead, they use rules such as two phase locking, which guarantee that every schedule produced is conflict serializable.

SERIALIZABLE isolation

In SQL, SET TRANSACTION ISOLATION LEVEL SERIALIZABLE asks the database to give serializable schedules. Lower levels allow some non-serializable schedules for speed. See Isolation Levels.

Key points

  • A schedule is serializable if it is equivalent to some serial schedule.
  • Two instructions conflict if they are from different transactions, use the same item, and at least one is a write.
  • Conflict serializable: can be turned into a serial schedule by swapping non-conflicting instructions.
  • View equivalence: same initial reads, same reads-from, same final writes.
  • Every conflict serializable schedule is view serializable; the extra view serializable ones have blind writes.
  • Precedence graph: edge Ti → Tj for each conflicting pair where Ti acts first.
  • No cycle means conflict serializable; topological sort gives the serial order.
