Schedules

When many transactions run at the same time, their steps are mixed together. A schedule records the order in which those steps run. This page shows the kinds of schedules and which ones are safe.

What is a schedule?

Definition

A schedule is a sequence of instructions that shows the chronological order (time order) in which the instructions of concurrent transactions are executed.

A schedule must contain all the instructions of the transactions in it, and it must keep the order of instructions inside each transaction. Only the mixing between transactions can change.

In the textbook, a schedule is drawn with one column per transaction. Time runs from top to bottom. A short form writes the same schedule on one line: r1(A) means T1 reads A, w2(B) means T2 writes B, and c1 means T1 commits.

The two transactions used on this page

A = ₹1000 and B = ₹2000 at the start.

T1: transfer ₹50 from A to B.

read(A); A := A − 50; write(A);
read(B); B := B + 50; write(B).

T2: transfer 10% of A to B.

read(A); temp := A * 0.1;
A := A − temp; write(A);
read(B); B := B + temp; write(B).

Serial schedules

Definition

In a serial schedule, the instructions of each transaction run one after the other, with no break. One transaction finishes completely before the next one starts.

read(B)

write(B)

A := A − temp
write(A)

Schedule 1 ends with A = ₹855 and B = ₹2145. Schedule 2 ends with A = ₹850 and B = ₹2150. The results differ, but both are correct, because A + B = ₹3000 in each. A serial schedule always keeps the database consistent, since each transaction alone is consistent.

With n transactions there are n! (n factorial) different serial schedules. Two transactions give 2 serial schedules; three give 6.

Concurrent schedules

Definition

In a concurrent (non-serial) schedule, the instructions of different transactions are interleaved. The CPU switches between transactions, so one starts before another has finished.

Some concurrent schedules are correct and some are not.

T1T2

A := A − 50
write(A)
read(A)
temp := A * 0.1
A := A − temp
write(A)
read(B)
B := B + 50
write(B)
read(B)

Schedule 1 (serial T1, T2)85521453000Yes

In schedule 4, T1 reads A = 1000 before T2 writes A. T1 then writes A = 950 over T2's value of 900, so T2's update to A is lost. The bank has ₹50 that came from nowhere.

Schedule 3 is safe because it gives the same result as a serial schedule. Such a schedule is called serializable. The next topic, Serializability, shows how to test for it.

Why run transactions concurrently?

Serial schedules are always correct, so why allow concurrency at all? There are two good reasons.

  • Better throughput and resource use: one transaction can use the CPU while another waits for the disk. More transactions finish per second, and the CPU and disks are less idle.
  • Less waiting time: a short transaction does not have to wait behind a long one. The average response time drops.

The job of the concurrency-control system is to allow only those concurrent schedules that are as good as some serial schedule.

Recoverable schedules

So far we assumed no transaction fails. Now suppose a transaction aborts. Its changes must be undone, and so must the work of any transaction that used its data.

Definition

A schedule is recoverable if, for every pair of transactions Ti and Tj where Tj reads a data item written by Ti, Ti commits before Tj commits.

Schedule 9: not recoverable
T8T9
read(A)
write(A)
read(A)
commit
read(B)
abort

T9 reads the value of A written by T8 and commits at once. Then T8 aborts. T8's write must be undone, so T9 read a value that never existed. But T9 has already committed and cannot be rolled back. The database cannot be recovered.

To make it recoverable, T9 must delay its commit until after T8 commits.

Cascadeless and strict schedules

Cascading rollback

Schedule 10: cascading rollback
T10T11T12
read(A)
read(B)
write(A)
read(A)
write(A)
read(A)
abort

T11 reads A from T10, and T12 reads A from T11. None of them has committed, so the schedule is recoverable. But when T10 aborts, T11 must roll back because it used T10's data, and then T12 must roll back because it used T11's data.

One failure causes a chain of rollbacks. This is a cascading rollback. It can undo a lot of work.

Definitions
  • A cascadeless schedule is one where, whenever Tj reads a data item written by Ti, Ti commits before Tj reads it. No transaction reads uncommitted data (no dirty reads), so cascading rollback cannot happen.
  • A strict schedule is one where a data item written by Ti cannot be read or written by another transaction until Ti commits or aborts.

Every cascadeless schedule is also recoverable, and every strict schedule is also cascadeless. Strict schedules make recovery easiest: to undo Ti, the system just puts back the old values from the log. Most database systems produce strict schedules by using strict two phase locking.

In real life

Exam result portal

On result day, thousands of students check marks while staff update a few records. The database interleaves all these transactions. A serial schedule would make every student wait in one long queue.

Online shopping cart

Your order should never be confirmed using stock that another order has reserved but not yet confirmed. Databases avoid this by giving strict schedules, so no one reads uncommitted data.

Key points

  • A schedule is the time order of the instructions of concurrent transactions; it keeps each transaction's own order.
  • Serial: no interleaving, always consistent; n transactions have n! serial schedules.
  • Concurrent schedules improve throughput and waiting time, but some give wrong results (schedule 4 creates ₹50).
  • A serializable schedule has the same effect as some serial schedule.
  • Recoverable: if Tj reads from Ti, Ti commits before Tj commits.
  • Cascading rollback: one abort forces other transactions that read its data to roll back.
  • Cascadeless: read only committed data. Strict: no read or write of an item until its writer ends.
  • Strict ⊂ cascadeless ⊂ recoverable.
