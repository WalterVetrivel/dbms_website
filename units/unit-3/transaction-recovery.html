Transaction Recovery

Transactions fail, systems crash and disks break. The recovery system makes sure that, after any of these, the database keeps the work of committed transactions and none of the work of unfinished ones. This page shows how it uses a log to do that.

Why recovery is needed

Transaction Ti moves ₹50 from account A to account B. It writes A, then B. Suppose the system crashes after A has been written to disk but before B has. A has lost ₹50 and B has not gained it, so the database is inconsistent.

When the system restarts, it cannot simply run Ti again (A would lose another ₹50), and it cannot leave things as they are. It must either undo the change to A or finish the change to B. To do either, it needs a record of what Ti was doing. That record is the log.

Definition

The recovery system is the part of the DBMS that restores the database to a consistent state after a failure. It makes sure that the atomicity and durability properties hold: a committed transaction's changes survive, and an unfinished transaction leaves no trace.

Failure classification

  1. Transaction failure.
    • Logical error: the transaction cannot go on because of something inside it, such as bad input, data not found, or overflow.
    • System error: the system must stop an active transaction, for example because of a deadlock. The transaction can be run again later.
  2. System crash. A hardware fault, a power cut, or a bug in the DBMS or operating system stops the system. The contents of main memory are lost, but the disk is not harmed. This is the fail-stop assumption.
  3. Disk failure. A head crash or similar fault destroys all or part of a disk. Recovery needs copies on other disks or on backup media, such as tapes or cloud storage. See Backup and Recovery System.

Storage types

Storage types and what survives
TypeExamplesSurvives a crash?
Volatile storageMain memory, cacheNo. Contents are lost when power goes off.
Non-volatile storageHard disk, SSD, magnetic tapeSurvives a system crash, but can still be lost in a disk failure.
Stable storageCopies on several disks, often at different sitesIn theory, never lost. Built by keeping several copies of each block on independent non-volatile media.

The log must be on stable storage, because recovery depends on it. A block is written to stable storage carefully: write the first copy; when that has finished, write the second copy; only then is the output complete. If a failure happens during the writes, the two copies are compared on restart and made the same.

Data moves between disk and memory in blocks. A transaction reads a block into the buffer in main memory and changes it there. The changed block is written back to disk later, at a time the buffer manager chooses. So after a crash, some changes may be on disk and others may have been lost with the buffer.

The log and write-ahead logging

The log is a sequence of records, one for each update and for each important event in a transaction. It is the most widely used structure for recording database changes.

Log records
RecordMeaning
<Ti start>Ti has started.
<Ti, Xj, V1, V2>Ti wrote data item Xj. V1 is the old value and V2 the new value.
<Ti commit>Ti has committed.
<Ti abort>Ti has aborted.

With the log, the system can do two things for any transaction:

  • undo(Ti) sets every item Ti wrote back to its old value, going backward through the log.
  • redo(Ti) sets every item Ti wrote to its new value, going forward through the log.

Both operations are idempotent: doing them twice has the same effect as doing them once. This matters because the system may crash again during recovery.

Write-ahead logging (WAL) rule
  1. The log record for an update must reach stable storage before the changed data block is written to disk.
  2. All log records of a transaction, including <Ti commit>, must reach stable storage before the transaction is said to have committed.

A transaction has committed when its commit record is on stable storage, even if none of its data blocks have reached the disk yet.

Deferred database modification

In the deferred modification technique, a transaction does not change the database until it has committed. Its writes are only recorded in the log. When it commits, the log records are used to apply the writes.

  • Log records need only the new value: <Ti, X, V2>.
  • After a crash, Ti is redone if the log has both <Ti start> and <Ti commit>.
  • A transaction without a commit record is simply ignored. It never changed the database, so no undo is needed. This is also called the NO-UNDO/REDO method.

Example: A = 1000, B = 2000, C = 700. T0 moves ₹50 from A to B; T1 withdraws ₹100 from C.

Immediate database modification

In the immediate modification technique, a transaction may change the database while it is still active, as long as the log record is written first (the WAL rule).

  • Log records need the old and new value: <Ti, X, V1, V2>.
  • Ti is undone if the log has <Ti start> but neither <Ti commit> nor <Ti abort>.
  • Ti is redone if the log has <Ti start> and <Ti commit> (or <Ti abort>, since the undo it did is logged too).
  • Both undo and redo may be needed. This is the UNDO/REDO method.
Log 
<T0 start>
<T0, A, 1000, 950>
<T0, B, 2000, 2050>
<T0 commit>
<T1 start>
<T1, C, 700, 600>
<T1 commit>

Exam tip

The results are the same for both techniques; only the work differs. Deferred: redo committed, ignore the rest. Immediate: undo unfinished, redo committed. When asked to recover from a log, first list which transactions have a commit record, then apply the rule.

Checkpoints

Without help, recovery must read the whole log, and it redoes many transactions whose changes are already on disk. The log keeps growing, so recovery gets slower and slower. Checkpoints fix this.

To take a checkpoint, the system:

  1. Writes all log records now in main memory to stable storage.
  2. Writes all changed buffer blocks to disk.
  3. Writes the record <checkpoint L> to stable storage, where L is the list of transactions active at that moment.

No transaction may update the database while a checkpoint is being taken. After a crash, every change made before the checkpoint is already on disk. So the system only needs to look at the transactions in L and those that started after the checkpoint. Everything earlier in the log can be skipped, and old log records can even be deleted.

The recovery algorithm

Modern systems use immediate modification and recover in two passes.

  1. Redo pass. Find the last <checkpoint L> record and set the undo-list to L. Scan forward from there to the end of the log.
    • For each update record, redo it: write the new value. This “repeats history”, including the writes of transactions that will be undone.
    • For <Ti start>, add Ti to the undo-list.
    • For <Ti commit> or <Ti abort>, remove Ti from the undo-list.
  2. Undo pass. Scan the log backward from the end.
    • For each update record of a transaction in the undo-list, restore the old value, and write a redo-only record <Ti, X, V1> to the log.
    • When <Ti start> is reached for a transaction in the undo-list, write <Ti abort> and remove it from the list.
    • Stop when the undo-list is empty.

After recovery, normal transaction processing starts again.

When a single transaction is rolled back during normal running, the same undo steps are used, scanning backward only over that transaction's records. In a distributed database, each site also needs a commit protocol so that all sites agree to commit or abort. See two-phase commit in Unit V.

Shadow paging

Shadow paging recovers without a log. The database is split into fixed-size pages, and a page table says where each page is on disk.

  • When a transaction starts, the current page table is copied. The copy is the shadow page table. It is saved on disk and never changed while the transaction runs.
  • When the transaction writes a page for the first time, the page is copied to a new free block on disk, and the change is made to the copy. The current page table is changed to point to the copy. The old page, still pointed to by the shadow table, is not touched.
  • Commit: write all changed pages and the current page table to disk, then change the single pointer to the database root so that it points to the current page table. That one-block write is atomic, so the switch happens all at once.
  • Abort or crash: just keep the shadow page table and throw away the current one. The shadow table still points to the old pages, so no undo is needed.

Merits: no log is needed for undo or redo, and recovery after a crash is almost instant.

Demerits:

  • Commit overhead: every changed page and the whole page table must be written at each commit.
  • Data fragmentation: changed pages move to new places, so related pages are no longer close together on disk.
  • Garbage collection: after commit, the old pages are no longer used and must be found and freed.
  • Hard to use with concurrent transactions: some logging is still needed when many transactions run at once.

Try it yourself

Things to try
  • Turn off the checkpoint. Where does the redo pass start now, and how many records does it read?
  • Switch to deferred update. Why is there no undo pass? What happens to T2's writes?
  • Crash right after the checkpoint record. Which transaction is undone, and why must the undo pass go back past the checkpoint?

In real life

MySQL InnoDB

InnoDB uses immediate modification. It writes changes to a redo log before the data pages, and keeps old row versions in undo logs. After a crash, it replays the redo log from the last checkpoint, then rolls back the transactions that had not committed, just like the algorithm above.

UPI payment

If your phone's bank app shows “processing” and the bank's server crashes, money is not lost. On restart, the bank's database redoes the committed debit and credit, or undoes a half-done one and refunds it. The log is what makes this possible.

Key points

  • Failures: transaction failure (logical or system error), system crash, disk failure.
  • Storage: volatile (lost on crash), non-volatile (lost on disk failure), stable (never lost).
  • Log records: start, update (item, old value, new value), commit, abort.
  • WAL: the log record reaches stable storage before the data block it describes.
  • Deferred: log new values, change the database after commit; redo only.
  • Immediate: log old and new values; undo unfinished, redo committed.
  • Checkpoint: flush the log and changed blocks, log <checkpoint L>; recovery starts there.
  • Shadow paging: copy-on-write pages; commit switches one pointer; no undo or redo.
