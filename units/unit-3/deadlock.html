Deadlock

Locking keeps schedules correct, but it lets transactions wait for each other. When they wait in a circle, none can ever go on. This page shows how a DBMS prevents such deadlocks, or finds and breaks them.

What is a deadlock?

Definition

A deadlock is a state in which two or more transactions are each waiting for another to release a lock, in a circular chain. Every transaction in the set waits for some other transaction in the set, so none of them can ever go on.

A deadlock can form only when all four of these conditions hold at the same time:

  1. Mutual exclusion: at least one lock cannot be shared. An exclusive (X) lock is held by one transaction only.
  2. Hold and wait: a transaction holds some locks while it waits for another.
  3. No preemption: a lock cannot be taken away from a transaction. It is released only by its holder.
  4. Circular wait: T0 waits for T1, T1 waits for T2, and so on, and the last waits for T0.

Breaking any one condition prevents deadlock. Deadlocks are hard to avoid in general, so every DBMS that uses locks needs a plan for them.

How a deadlock occurs

Take T3 and T4 from Two Phase Locking. T3 moves ₹50 from account B to account A. T4 reads A and B to display their total. Both follow two phase locking, but they lock the items in opposite order.

T3 and T4 in deadlock
StepT3T4What happens
1lock-X(B)Granted
2read(B); B := B − 50; write(B)
3lock-S(A)Granted
4read(A)
5lock-S(B)T3 holds X on B, so T4 waits for T3
6lock-X(A)T4 holds S on A, so T3 waits for T4

After step 6, T3 waits for T4 and T4 waits for T3. Neither can continue, and neither will ever release its lock. This is a deadlock. The system must roll back one of them; the other then gets its lock and finishes.

Note

Deadlock is the price of locking. If T3 had unlocked B before asking for A, there would be no deadlock, but T4 might see an inconsistent total. Rolling back a transaction from time to time is better than letting it see wrong data.

Ways to handle deadlock

There are two main approaches:

  1. Deadlock prevention: make sure the system never enters a deadlock. The DBMS inspects the operations a transaction is about to run. If an operation could create a deadlock, it is not allowed to wait; instead some transaction is rolled back at once. This works well when the chance of deadlock is high.
  2. Deadlock detection and recovery: let deadlocks happen, check for them from time to time, and break any that form. This works well when deadlocks are rare.

Both approaches may roll back transactions. Prevention often rolls back a transaction even when no deadlock would have happened. Detection costs time to keep and check the wait-for graph.

Note on the word “avoidance”

Some notes call checking the wait-for graph “deadlock avoidance”, since the system watches every new wait. In textbooks, avoidance means deciding, before granting a request, whether it could ever lead to a deadlock. Wait-die and wound-wait are often called avoidance schemes for this reason. In an exam answer on prevention, avoidance and detection, use these three headings and explain each scheme under one of them.

Deadlock prevention

Prevention schemes break one of the four conditions.

  • Lock everything at the start (conservative 2PL). Each transaction locks all the items it needs before it begins, all or nothing. This removes hold and wait. It is hard to know all items in advance, and items stay locked for a long time.
  • Lock items in a fixed order. Number all data items, and let each transaction lock items only in increasing order. A circular wait can then never form. In the example above, if both T3 and T4 had to lock A before B, there would be no deadlock.
  • Preemption with timestamps. When a transaction must wait, compare timestamps and roll back one of the two transactions instead of letting a cycle form. This is wait-die and wound-wait, below.
  • Timeout. Let a transaction wait only for a fixed time, then roll it back.

Wait-die and wound-wait

Each transaction gets a unique timestamp TS when it enters the system. A smaller timestamp means an older transaction. Suppose Ti asks for a lock on an item that Tj holds in a conflicting mode.

Wait-die scheme (non-preemptive)

  • If TS(Ti) < TS(Tj), that is Ti is older, Ti is allowed to wait.
  • If TS(Ti) > TS(Tj), that is Ti is younger, Ti dies: it is rolled back and restarted later with the same timestamp.

An older transaction may wait for a younger one, but a younger one never waits for an older one.

Wound-wait scheme (preemptive)

  • If TS(Ti) < TS(Tj), that is Ti is older, Ti wounds Tj: Tj is rolled back and restarted later with the same timestamp, and Ti gets the lock.
  • If TS(Ti) > TS(Tj), that is Ti is younger, Ti waits.

A younger transaction may wait for an older one, but an older one never waits for a younger one.

What happens when Ti asks for a lock held by Tj
Requester Ti isWait-dieWound-wait
Older than TjTi waitsTj is rolled back (wounded)
Younger than TjTi is rolled back (dies)Ti waits

Why no deadlock? In wait-die, every wait goes from an older to a younger transaction; in wound-wait, every wait goes from a younger to an older one. Timestamps only increase along any chain of waits, so the chain can never loop back to its start.

Why no starvation? In both schemes, it is always the younger transaction that is rolled back, and it keeps its old timestamp when it restarts. In time it becomes the oldest transaction in the system and is never rolled back again.

Exam tip

Read the names as what the older transaction does when it meets a younger one. Wait-die: the old one waits, the young one dies. Wound-wait: the old one wounds, the young one waits. In wait-die a young transaction may die many times before it gets its lock; wound-wait usually causes fewer rollbacks.

Applied to T3 and T4. T3 entered first, so TS(T3) = 1 and TS(T4) = 2.

  • Wait-die: at step 5, T4 (younger) asks for B, held by T3. T4 dies and releases A. T3 then gets A and finishes.
  • Wound-wait: at step 5, T4 (younger) waits. At step 6, T3 (older) asks for A, held by T4. T3 wounds T4, which is rolled back, and T3 gets A.

Timeout

In the lock timeout scheme, a transaction that has waited for a lock longer than a fixed time is rolled back and restarted. If there was a deadlock, the rollback breaks it.

  • Merits: very simple; no graph or timestamps to keep.
  • Demerits: it is hard to choose the time. Too long, and a deadlock blocks work for that long. Too short, and transactions that were only waiting behind a slow transaction are rolled back for nothing. Starvation is also possible.

Detection with a wait-for graph

The system keeps a directed wait-for graph:

  • There is one node for each active transaction.
  • When Ti asks for a lock on an item that Tj holds, an edge Ti → Tj is added. It means “Ti waits for Tj”.
  • When Tj releases the item and Ti gets the lock, the edge is removed.
Rule

The system is in a deadlock if and only if the wait-for graph contains a cycle. Every transaction on the cycle is deadlocked.

When to run the check? The detection algorithm can run each time a transaction must wait, or every few seconds. If deadlocks are frequent, it should run often; otherwise transactions stay blocked longer and the cycle may grow to include more transactions.

Recovery from deadlock

When a cycle is found, the system breaks it by rolling back one or more transactions in the cycle. Three steps are needed.

  1. Select a victim. Choose the transaction whose rollback costs least. The cost depends on how long it has run and how much is left. It also depends on how many data items it has used, how many more it needs, and how many other transactions would be rolled back with it. The chosen transaction is called the victim, and this step is called victim selection.
  2. Roll back. A total rollback aborts the victim and restarts it from the beginning. A partial rollback undoes the victim only as far as needed to release the lock that breaks the cycle, and resumes from there. Partial rollback needs more information about the order of lock requests.
  3. Avoid starvation. If the same transaction is picked as the victim every time, it never finishes. The usual fix is to include the number of rollbacks in the cost, so a transaction can be picked only a few times.
Note

It is not always right to roll back the younger transaction. It may be more important than the older one, or it may have done more work. The cost formula decides.

Starvation and livelock

Starvation happens when a transaction waits for a lock forever, or is rolled back over and over, while others keep making progress. For example, a transaction waiting for an X lock may be passed over again and again while new transactions keep getting S locks on the same item.

Livelock is a special case of starvation. It is like a deadlock, except that the transactions involved keep changing state: they are not blocked, yet none of them makes progress. Examples:

  • The system keeps selecting the same transaction as the deadlock victim, so it restarts, deadlocks again and is rolled back again, forever.
  • Two transactions keep running into each other, both back off, both retry at the same moment, and collide again.
Deadlock, livelock and starvation

Wait-die and wound-wait restart a transaction after a random delay and with its old timestamp. This prevents both livelock and starvation.

In real life

MySQL InnoDB

InnoDB detects deadlocks automatically and rolls back the smaller transaction, the one that has changed fewer rows. The application gets error 1213, “Deadlock found when trying to get lock; try restarting transaction”, and should retry. A lock wait that is not a deadlock ends after innodb_lock_wait_timeout, 50 seconds by default.

A narrow lane

Two cars enter a one-car lane from opposite ends and meet in the middle. Each waits for the other to back out, so neither moves: a deadlock. One driver must reverse (roll back). If both keep reversing and entering at the same moment, it is a livelock.

Key points

  • Deadlock: a set of transactions each waiting for another in the set, in a circle.
  • Four conditions: mutual exclusion, hold and wait, no preemption, circular wait.
  • Prevention: lock all at start, lock in a fixed order, wait-die, wound-wait, timeout.
  • Wait-die: older waits, younger dies. Wound-wait: older wounds, younger waits.
  • The rolled back transaction keeps its old timestamp, so it does not starve.
  • Wait-for graph: edge Ti → Tj when Ti waits for Tj. A cycle means deadlock.
  • Recovery: select a victim, roll it back (total or partial), and avoid starvation.
  • Livelock: transactions keep changing state but never progress.
