Overview

SQL gives four groups of facilities:

  1. Transaction boundaries: mark where a transaction starts and ends (START TRANSACTION, COMMIT, ROLLBACK, autocommit).
  2. Isolation: choose how much a transaction is protected from others (SET TRANSACTION).
  3. Explicit locking: lock rows or tables yourself when the isolation level is not enough (SELECT ... FOR UPDATE, FOR SHARE, LOCK TABLES).
  4. Recovery: undo work and survive failures (ROLLBACK, SAVEPOINT, automatic crash recovery, backups).

The examples use MySQL with the InnoDB storage engine, as in the lab.

Starting and ending a transaction

  • START TRANSACTION; (or BEGIN;) starts a transaction.
  • COMMIT; ends it and makes all its changes permanent.
  • ROLLBACK; ends it and undoes all its changes.

MySQL runs with autocommit on by default: each statement is its own transaction and commits as soon as it finishes. START TRANSACTION turns autocommit off until the next COMMIT or ROLLBACK. To turn it off for the whole session, use SET autocommit = 0;. Then every statement is part of a transaction that lasts until you commit or roll back.

The game purchase from the lab moves the user's cart into the purchase history. All the steps must happen together or not at all:

SQL 
START TRANSACTION;
SET @UserID = 1;
INSERT INTO Transactions(TransactionDate, UserID) VALUES (NOW(), @UserID);
SELECT LAST_INSERT_ID() INTO @T_ID;
INSERT INTO PurchaseHistory(TransactionID, GameID, SalePrice)
  SELECT @T_ID, Cart.GameID, Games.CurrentPrice
  FROM Cart INNER JOIN Games ON Cart.GameID = Games.GameID
  WHERE Cart.UserID = @UserID;
DELETE FROM Cart WHERE UserID = @UserID;
COMMIT;

If any statement fails before the COMMIT, the program issues ROLLBACK and the database goes back to its state before START TRANSACTION. The cart is never emptied without the purchase being recorded.

Two useful options when starting:

  • START TRANSACTION READ ONLY; promises that the transaction will not change data, which lets the DBMS run it more cheaply. READ WRITE is the default.
  • START TRANSACTION WITH CONSISTENT SNAPSHOT; takes the read snapshot at once, instead of at the first read.
Common mistake

Some statements cause an implicit commit: most DDL statements (CREATE, ALTER, DROP, TRUNCATE), LOCK TABLES, and START TRANSACTION itself. A ROLLBACK after them cannot undo what came before. Keep DDL out of transactions that you may want to roll back.

SET TRANSACTION

SET TRANSACTION sets the characteristics of the next transaction: its isolation level and its access mode.

SQL 
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE, READ WRITE;
START TRANSACTION;
-- statements run at SERIALIZABLE
COMMIT;

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- every later transaction in this session

The four levels are READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ (the InnoDB default) and SERIALIZABLE.

Locking reads: FOR UPDATE and FOR SHARE

At the default level, a plain SELECT in InnoDB reads a snapshot and takes no locks. That is a problem when you read a value and then write based on it: another transaction may change the value in between, causing a lost update. A locking read solves this.

Locking reads
StatementLock taken on each row readOthers can
SELECT ... FOR SHAREShared (S) lockRead the rows, and also lock them FOR SHARE, but not change them
SELECT ... FOR UPDATEExclusive (X) lockOnly read snapshots; any locking read or change must wait

The locks are held until the transaction commits or rolls back. These are the shared and exclusive locks of the locking protocols, under strict two phase locking. Older MySQL versions write FOR SHARE as LOCK IN SHARE MODE.

Example: booking the last seat. Two users try to book seat 12A at the same time.

SQL 
START TRANSACTION;
SELECT status FROM seats WHERE seat_no = '12A' FOR UPDATE;   -- locks the row
-- if status is 'free':
UPDATE seats SET status = 'booked', user_id = 42 WHERE seat_no = '12A';
COMMIT;                                                       -- releases the lock
Two sessions booking the same seat
StepSession ASession B
1SELECT ... FOR UPDATE → free (row locked)
2SELECT ... FOR UPDATE → waits for A
3UPDATE ... booked; COMMIT
4Gets the lock; reads booked; does not book

Without FOR UPDATE, both sessions could read “free” and both could book the seat.

MySQL 8 adds two options for when waiting is not wanted:

  • FOR UPDATE NOWAIT returns an error at once if a row is locked.
  • FOR UPDATE SKIP LOCKED skips locked rows and returns the rest. This suits job queues, where each worker takes any free job.

LOCK TABLES

LOCK TABLES locks whole tables for the current session.

SQL 
LOCK TABLES Games READ, Cart WRITE;
-- this session may read Games, and read and write Cart
UNLOCK TABLES;
  • READ lock: this session and others can read the table; nobody can write it.
  • WRITE lock: only this session can read or write the table; others wait.
  • While it holds table locks, a session can use only the tables it has locked.
  • LOCK TABLES commits any active transaction first, and UNLOCK TABLES releases all table locks.

For InnoDB tables, row locks from transactions are usually better, because they lock less and let more transactions run at once. LOCK TABLES is used for maintenance tasks and for storage engines without transactions, such as MyISAM.

Lock waits and deadlocks

  • A transaction that waits for a lock longer than innodb_lock_wait_timeout (50 seconds by default) gets an error: “Lock wait timeout exceeded; try restarting transaction”.
  • InnoDB detects deadlocks automatically and rolls back one transaction, which gets error 1213: “Deadlock found when trying to get lock; try restarting transaction”.
  • The application should catch these errors and run the whole transaction again.
  • SHOW ENGINE INNODB STATUS; shows the latest deadlock, and the performance_schema.data_locks table lists the locks held now.
Exam tip

To reduce deadlocks, keep transactions short, access tables and rows in the same order in every program, and use the lowest isolation level that is safe.

Facilities for recovery

  • COMMIT and durability. When COMMIT returns, the change is safe. InnoDB first writes the change to its redo log and flushes the log to disk at commit (the write-ahead logging rule from Transaction Recovery). The setting innodb_flush_log_at_trx_commit = 1, the default, makes this flush happen at every commit.
  • ROLLBACK. InnoDB keeps the old version of each changed row in its undo log. ROLLBACK uses it to put the old values back.
  • SAVEPOINT. Savepoints allow a partial rollback inside a transaction.
  • Automatic crash recovery. After a crash, InnoDB replays the redo log from the last checkpoint and rolls back transactions that had not committed, as soon as the server restarts. No command is needed.
  • Backups and the binary log. For disk failures and human mistakes, use backups and the binary log. See Backup and Recovery System.

Try it in MySQL

Open two MySQL command-line windows on the same database. Call them A and B.

  1. In A: CREATE TABLE seats (seat_no CHAR(3) PRIMARY KEY, status VARCHAR(10)); and INSERT INTO seats VALUES ('12A', 'free');
  2. In A: START TRANSACTION; then SELECT * FROM seats WHERE seat_no = '12A' FOR UPDATE;
  3. In B: START TRANSACTION; then the same SELECT ... FOR UPDATE. B waits.
  4. In A: UPDATE seats SET status = 'booked' WHERE seat_no = '12A'; COMMIT;. B's SELECT now returns, showing “booked”.
  5. In B: ROLLBACK;. Now repeat the steps with a plain SELECT (no FOR UPDATE) in B. Does B still wait?

In real life

Food delivery app

When two delivery partners tap “accept” on the same order, the server runs SELECT ... FOR UPDATE on the order row. The first one gets the order; the second one sees that it is already taken.

Job queues

Many workers take jobs from one table with SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1. Each worker gets a different job, and nobody waits.

Key points

  • START TRANSACTION, COMMIT and ROLLBACK mark a transaction; autocommit makes each statement its own transaction.
  • SET TRANSACTION chooses the isolation level and access mode.
  • FOR SHARE takes shared row locks; FOR UPDATE takes exclusive row locks; both last until commit.
  • LOCK TABLES locks whole tables, and commits any open transaction first.
  • Lock wait timeouts and deadlock errors should be handled by retrying the transaction.
  • Recovery: redo log for COMMIT, undo log for ROLLBACK, automatic crash recovery, backups for disk failure.
