Isolation Levels

Full serializability is safe but slow. SQL lets each transaction choose how much isolation it needs. This page explains the four isolation levels and the problems each one allows.

What is an isolation level?

Definition

An isolation level decides how far one transaction is protected from the changes made by other transactions running at the same time. It is defined by which phenomena (read problems) are allowed to occur.

The I in ACID asks that concurrent transactions behave as if they ran one after another. Guaranteeing that fully needs more locking and more waiting. Many applications can accept a little less isolation in return for more concurrency. So the SQL standard offers four levels, from weakest to strongest.

Lower isolation means more concurrency but less consistency. Higher isolation means more consistency but less concurrency.

The three phenomena

These are the read problems from Concurrency Control. Each returns different results inside one transaction because of what another transaction did.

Dirty read

A transaction reads data written by another transaction that has not committed yet. If that other transaction rolls back, the first one has used a value that never really existed.

T1 sets A from 1000 to 950 but has not committed. T2 reads 950. T1 aborts, so A is 1000 again, but T2 has already used 950.

Non-repeatable read

A transaction reads the same row twice and gets different values, because another transaction modified and committed that row between the two reads. It is also called an unrepeatable read.

T1 reads A = 1000. T2 sets A to 950 and commits. T1 reads A again and gets 950.

Phantom

A transaction runs the same range query twice and gets a different set of rows. Between the two queries, another transaction inserted (or deleted) rows in that range and committed. The new rows are the “phantoms”.

T1 counts students with dept = 'CSE' and gets 3. T2 inserts a new CSE student and commits. T1 counts again and gets 4.

Note

A non-repeatable read is about a change to a row you already read. A phantom is about a new row that now matches your condition. Locking the rows you read stops the first but not the second.

Each level allows fewer phenomena than the one above it. All four levels forbid a dirty write, where a transaction overwrites data that another uncommitted transaction has written.

Each level explained

A lock-based DBMS can build each level from the shared and exclusive locks you already know. Every level holds exclusive (write) locks until the transaction ends. The levels differ in how long they hold shared (read) locks.

  1. READ UNCOMMITTED is the lowest level. Reads take no shared locks, so a transaction may read changes that others have not yet committed. Dirty reads are possible, and transactions are hardly isolated from each other. It suits rough statistics where an exact answer is not needed.
  2. READ COMMITTED guarantees that any data read was committed at the moment it was read, so there are no dirty reads. A shared lock is taken for each read and released straight after it. A row read twice may have changed in between, so non-repeatable reads are possible.
  3. REPEATABLE READ holds shared locks on every row it reads, and exclusive locks on every row it inserts, updates or deletes, until the transaction ends. Other transactions cannot change those rows, so reads are repeatable. But new rows can still be inserted into a range, so phantoms are possible.
  4. SERIALIZABLE is the highest level. It guarantees that concurrent transactions give the same result as some serial order. Besides holding all locks to the end (strict two phase locking), it locks the range of each query, often using index locks, so no phantom can appear.
Note

SERIALIZABLE is the most restrictive level. REPEATABLE READ is the most restrictive level that still allows a phenomenon (phantoms).

Setting the level in SQL

The SQL standard command is SET TRANSACTION. It is given before the transaction begins.

SQL 
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT balance FROM account WHERE acc_no = 'A-101';
-- ... more statements ...
COMMIT;

In MySQL, the level can be set for the next transaction, for the whole session, or for all new sessions:

MySQL 
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;            -- next transaction only
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;   -- this session
SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;   -- new sessions
SELECT @@transaction_isolation;                           -- show the current level

More SQL commands for transactions and locking are on SQL Facilities for Concurrency and Recovery.

Isolation in MySQL InnoDB

The default level differs between products. MySQL InnoDB uses REPEATABLE READ by default. Oracle, PostgreSQL and SQL Server use READ COMMITTED.

InnoDB does not use shared locks for ordinary SELECT statements. Instead it uses multiversion concurrency control: each transaction reads from a snapshot of the committed data.

  • At READ COMMITTED, each SELECT gets a fresh snapshot, so it sees the latest committed data.
  • At REPEATABLE READ, the snapshot is taken at the first read and reused for the whole transaction. Every plain SELECT sees the same data, so even phantoms do not show up in these reads.
  • For locking reads (SELECT ... FOR UPDATE), UPDATE and DELETE, InnoDB locks the rows found and the gaps between them (next-key locks), so other transactions cannot insert into the range.
  • At SERIALIZABLE, InnoDB turns plain SELECT statements into locking reads when autocommit is off.

Two sessions show the difference between READ COMMITTED and REPEATABLE READ:

Session A reads twice while session B updates
StepSession ASession B
1START TRANSACTION;
SELECT balance FROM account WHERE acc_no = 'A-101'; → 1000
2UPDATE account SET balance = 950 WHERE acc_no = 'A-101';
COMMIT;
3SELECT balance FROM account WHERE acc_no = 'A-101';

At READ COMMITTED, step 3 returns 950: a non-repeatable read. At REPEATABLE READ, step 3 returns 1000, from the same snapshot as step 1.

Caution

Snapshot reads do not make everything safe. Two transactions can each read a snapshot, make decisions on it and write different rows, giving a result no serial order would give. This is called write skew. Use SERIALIZABLE, or lock the rows you depend on with SELECT ... FOR UPDATE, when that matters.

Choosing a level

Isolation levels compared
LevelConsistencyConcurrencySuits
READ UNCOMMITTEDLowestHighestApproximate counts and reports where small errors do not matter
READ COMMITTEDLowHighMost web pages and short updates; the default in many systems
REPEATABLE READHighMediumReports that read the same rows more than once
SERIALIZABLEHighestLowestMoney transfers, seat booking, anything that must never be wrong

Higher levels cause more waiting, more deadlocks and more rollbacks, so an application should use the lowest level that keeps its own data correct.

In real life

Exam results portal

A page that shows a student's marks can run at READ COMMITTED. It must never show marks that are later rolled back, but it does not matter if marks change a second later. The batch job that computes ranks across all students needs the same data throughout, so it should use REPEATABLE READ or SERIALIZABLE.

Live cricket score

A dashboard counting page views can use READ UNCOMMITTED. If a count is briefly off by one, nobody minds, and the reads never wait for writers.

Key points

  • An isolation level is defined by which phenomena it allows.
  • Phenomena: dirty read, non-repeatable read, phantom.
  • READ UNCOMMITTED allows all three; READ COMMITTED stops dirty reads.
  • REPEATABLE READ also stops non-repeatable reads; SERIALIZABLE stops all three.
  • Higher level: more consistency, less concurrency.
  • SET TRANSACTION ISOLATION LEVEL ... chooses the level.
  • MySQL InnoDB defaults to REPEATABLE READ and uses snapshots for plain reads.
