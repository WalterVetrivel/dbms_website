Dependency Preservation

When we split a table, every functional dependency is still a rule the data must follow. If each rule can be checked inside one of the new tables, the split is dependency preserving. If not, the database must join tables just to check a rule. This page shows how to tell the difference.

Why preserve dependencies

Every FD is a rule. For example, “each department has one head”: Dept → HOD. The database must check the rule on every insert and update.

  • If all the attributes of an FD are in one table, the check is cheap. A primary key or a UNIQUE constraint does it.
  • If the attributes are spread over several tables, the database must join them on every change. That is slow, and most systems will not do it for you.

A decomposition is dependency preserving when no rule ends up spread like this. Together with a lossless join (see Non-loss Decomposition), it is one of the two properties of a good decomposition.

The FDs that hold on each part

Definition

Let R be split into R1, R2, ..., Rn. The restriction of F to Ri, written Fi, is the set of FDs in F+ that use only attributes of Ri.

Fi is taken from F+, not just from F. An FD that is not written in F can still hold on a part.

Example: R(A, B, C) with F = {A → B, B → C}. Take the part R1(A, C). Neither FD of F fits inside R1. But A → C is in F+ by transitivity, so F1 = {A → C}.

How to find Fi

  1. For each subset X of the attributes of Ri, find X+ under F.
  2. Keep the attributes of X+ that are in Ri and not in X. Call them Y.
  3. If Y is not empty, X → Y is in Fi.
  4. Drop the FDs that follow from the others, so Fi stays short.

Definition

Definition

A decomposition of R into R1, ..., Rn is dependency preserving if

(F1 ∪ F2 ∪ ... ∪ Fn)+ = F+

In words: every FD of F can be derived from FDs that each sit inside one table.

Since F1 ∪ ... ∪ Fn only holds FDs from F+, one direction is always true. So in practice we check the other: every FD in F must follow from F1 ∪ ... ∪ Fn.

Common mistake

Some notes write the condition as F1 ∪ ... ∪ Fn = F, without the closures. The two sets of FDs need not be equal. Only their closures must be equal. In the example below, F1 ∪ F2 ∪ F3 contains C → B, which is not in F, and the decomposition is still dependency preserving.

Testing with closures

  1. Find F1, F2, ..., Fn, the FDs that hold on each part.
  2. Let G = F1 ∪ F2 ∪ ... ∪ Fn.
  3. For each FD X → Y in F, find X+ under G.
  4. If Y is in X+ for every FD, the decomposition is dependency preserving. If any FD fails, that FD is lost.
Quick check

If every FD of F fits inside one part, the decomposition is dependency preserving. You only need closures for the FDs that do not fit.

A test without computing F+

Finding every Fi can take a long time, because a part with k attributes has 2k subsets. This shorter test checks one FD X → Y at a time:

Algorithm 
result = X
repeat
  for each part Ri:
    t = (result ∩ Ri)+ ∩ Ri      -- closure under F
    result = result ∪ t
until result does not change
X → Y is preserved if Y ⊆ result

Each step only uses facts that one table can check on its own. So if the result reaches Y, the FD can be enforced without a join.

Example: a lost dependency

R(A, B, C) with F = {A → B, B → C} is split into R1(A, C) and R2(B, C).

  1. F1 on (A, C): A+ = {A, B, C}, so A → C. C+ = {C}, so nothing more. F1 = {A → C}.
  2. F2 on (B, C): B+ = {B, C}, so B → C. F2 = {B → C}.
  3. G = {A → C, B → C}. Under G, A+ = {A, C}. B is not in it, so A → B is lost.

The algorithm agrees. Start with result = {A}. R1 adds C. R2 sees only C, and C+ = {C}, so it adds nothing. B is never reached.

With real names: Student(RollNo, Dept, HOD) with RollNo → Dept and Dept → HOD. Splitting it into (RollNo, HOD) and (Dept, HOD) loses RollNo → Dept. Nothing stops us storing a student in two departments. This split is also lossy, because the common attribute HOD is not a key of either part.

The better split

Split into R1(A, B) and R2(B, C) instead. Both FDs now fit inside one part, so the split is dependency preserving. It is also lossless, because B is the key of R2. With names: Student(RollNo, Dept) and Department(Dept, HOD).

Example: a preserved dependency

R(A, B, C, D) with F = {A → B, B → C, C → D, D → B} is split into R1(A, B), R2(B, C) and R3(B, D).

First find the closures under F: B+ = C+ = D+ = {B, C, D}, and A+ = {A, B, C, D}.

The FDs that hold on each part
PartFDs that hold on it
R1(A, B)F1 = {A → B}
R2(B, C)F2 = {B → C, C → B}
R3(B, D)F3 = {B → D, D → B}

A → B, B → C and D → B each fit inside one part. Only C → D does not fit. Under G = F1 ∪ F2 ∪ F3, C → B (from F2) and B → D (from F3) give C → D. So every FD of F follows from G, and the decomposition is dependency preserving.

The algorithm for C → D: start with {C}. R2 adds B. R3 then sees B and adds D. D is reached, so C → D is preserved.

This split is also lossless. Use the checker below to step through the tableau test.

The two properties are independent. A split can have either one without the other:

  • R(A, B, C) with F = {A → B, B → C} is split into (A, B) and (A, C). It is lossless, because A is a key of both. But B → C is lost.
  • R(A, B, C, D) with F = {A → B, C → D} is split into (A, B) and (C, D). Every FD fits in one part. But the parts share no attribute, so the split is lossy.

The classic BCNF case is Enrollment(sid, course, teacher) with (sid, course) → teacher and teacher → course. Every BCNF split loses (sid, course) → teacher. This is why designers sometimes stop at 3NF. Boyce-Codd Normal Form covers it in detail.

What a lost FD costs in SQL

Enrollment(sid, course, teacher) is split into Takes(sid, teacher) and Teaches(teacher, course). The rule (sid, course) → teacher says a student has one teacher for each course. Its attributes are now in two tables, so no key can enforce it:

SQL 
CREATE TABLE Teaches (
  teacher VARCHAR(20) PRIMARY KEY,
  course  VARCHAR(20) NOT NULL
);

CREATE TABLE Takes (
  sid     INT,
  teacher VARCHAR(20),
  PRIMARY KEY (sid, teacher),
  FOREIGN KEY (teacher) REFERENCES Teaches (teacher)
);

INSERT INTO Teaches VALUES ('Ankita', 'C'), ('Archana', 'C'), ('Pooja', 'Java');
INSERT INTO Takes VALUES (1, 'Ankita'), (1, 'Pooja'), (2, 'Archana');

-- Accepted, but student 1 now has two teachers for course C.
INSERT INTO Takes VALUES (1, 'Archana');

-- Finding the broken FD needs a join.
SELECT t.sid, c.course, COUNT(*) AS teachers
FROM Takes t
JOIN Teaches c ON c.teacher = t.teacher
GROUP BY t.sid, c.course
HAVING COUNT(*) > 1;
Output 
+-----+--------+----------+
| sid | course | teachers |
+-----+--------+----------+
|   1 | C      |        2 |
+-----+--------+----------+

The bad row got in because each table on its own looked fine. To block it, we would need a trigger that runs this join on every insert. A preserved FD needs only a key or a UNIQUE constraint.

In real life

Train reservations

The rule “one passenger per seat, per train, per date” is checked on every booking. Keeping train, date, coach and seat in one table lets a UNIQUE constraint do it at once.

Hostel allotment

“Each room has one warden” is easy to enforce if Room and Warden sit in the same table. If the design splits them apart, the office must run a report to catch mistakes.

Exam timetable

“A hall holds one exam per slot” must be checked as the timetable is made. A design that preserves this FD rejects clashes at once.

Key points

  • Fi, the restriction of F to Ri, holds the FDs of F+ that use only attributes of Ri.
  • Dependency preserving: (F1 ∪ ... ∪ Fn)+ = F+.
  • Test: every FD X → Y of F must have Y in X+ computed under F1 ∪ ... ∪ Fn.
  • An FD that fits inside one part is always preserved.
  • A lost FD can only be checked with a join, for example in a trigger.
  • Lossless join is required; dependency preservation is desirable. 3NF can always have both; BCNF sometimes cannot.
