Non-loss Decomposition

A table that stores everything in one place repeats data, and repeated data causes mistakes. We fix this by splitting the table, but a careless split loses information. This page shows the problems, the safe way to split, and the tests that prove a split is safe.

Redundancy and anomalies

A company keeps employees and departments in one table:

Emp_Dept (one table for everything)
EmpIDENameSalaryDeptIDDeptNameDeptLoc
1Arun40000101SalesPune
2Banu45000101SalesPune
3Chitra50000101SalesPune
4Dinesh42000102AccountsMumbai
Definition

Redundancy means the same fact is stored in more than one place. Here “department 101 is Sales in Pune” is stored three times.

Redundancy causes four problems:

  1. Redundant storage: the same department details fill many rows and waste space.
  2. Update anomaly: Sales moves to Chennai. If we change only one of the three rows, the table says Sales is in two cities. The data becomes inconsistent.
  3. Insertion anomaly: a new department 103 is created but has no employees yet. We cannot add it without inventing an employee, because EmpID, the key, cannot be NULL.
  4. Deletion anomaly: Dinesh leaves, so we delete row 4. We also lose the only record that department 102, Accounts, is in Mumbai.

The cause is that the table stores facts about two things, employees and departments, in one place. The cure is to split it.

Decomposition

Definition

A decomposition of a relation schema R replaces R by two or more schemas R1, R2, ..., Rn. Each Ri has a subset of the attributes of R, and together they contain all the attributes: R1 ∪ R2 ∪ ... ∪ Rn = R. Each new table stores a projection of the old one.

Split Emp_Dept into two tables:

Schema 
Employee(EmpID, EName, Salary, DeptID)
Department(DeptID, DeptName, DeptLoc)

Now each department is stored once. Moving Sales to Chennai changes one row. A new department can be added with no employees. Deleting Dinesh keeps department 102. All four problems are gone.

A good decomposition has two properties

  1. Non-loss (lossless) join: joining the parts gives back exactly the original table. This one is required.
  2. Dependency preservation: every FD can still be checked inside one table. This one is desirable. See Dependency Preservation.

Costs of decomposing

  • Some queries need a join, which makes them slower.
  • A careless split can lose information, as the next sections show.
  • Checking some FDs may need a join, if dependencies are not preserved.

Non-loss decomposition

Definition

Take any legal instance r of R. Split it into R1 and R2, then join the two parts back. The decomposition is non-loss (lossless-join) if the join always gives back r exactly: πR1(r) ⋈ πR2(r) = r.

  • The join always gives back at least the original rows. A bad split adds extra rows, called spurious tuples.
  • Extra rows are a loss of information: we can no longer tell which rows are true. That is why a split with extra rows is called lossy.
  • Elmasri and Navathe call this the nonadditive join property, because no tuples are added.

The two students named Anitha are mixed up. We cannot tell which Anitha is in CSE, so information is lost. The problem is that the common attribute, Name, does not identify a row in either part.

Testing a split into two

Test

A decomposition of R into R1 and R2 is lossless if all three conditions hold:

  1. R1 ∪ R2 = R: every attribute of R is in R1 or R2.
  2. R1 ∩ R2 ≠ ∅: the parts have at least one common attribute.
  3. R1 ∩ R2 → R1 or R1 ∩ R2 → R2: the common attributes form a superkey of at least one part.

Worked example

R(A, B, C, D) with F = {A → BC} is split into R1(A, B, C) and R2(A, D).

  1. R1 ∪ R2 = {A, B, C, D} = R. ✓
  2. R1 ∩ R2 = {A}, which is not empty. ✓
  3. A+ = {A, B, C}, which contains all of R1. So A → R1, and A is a superkey of R1. ✓

All three hold, so the decomposition is lossless.

For Student above, R1 ∩ R2 = {Name}, and Name+ = {Name}. Name is a superkey of neither part, so that split is lossy.

Exam tip

A quick check: split on a key of one of the parts. Employee and Department share DeptID, and DeptID is the key of Department. So that split is lossless.

Testing a split into three or more

For three or more parts we use the tableau (chase) test:

  1. Make a table with one column for each attribute of R and one row for each part Ri.
  2. In row i, write a in the columns of the attributes of Ri, and a different b in the other columns.
  3. For each FD X → Y: wherever two rows agree on X, make them agree on Y. If one of them has a, both get a.
  4. Repeat until nothing changes. If some row becomes all a's, the decomposition is lossless. Otherwise it is lossy.

Worked example

Take R(A, B, C, D, E, F) with F = {A → BC, C → A, D → E, F → A, E → D}. It is split into R1(A, C, D), R2(B, C, D) and R3(D, E, F).

  • R1 and R2 agree on C, so by C → A, row 2 gets a in column A. Then by A → BC, row 1 gets a in column B.
  • All three rows agree on D, so by D → E, rows 1 and 2 get a in column E.
  • Now no FD changes anything. Column F has a only in row 3, and row 3 has b in A, B and C. No row is all a's, so the decomposition is lossy.

The reason: nothing determines F except F itself, and F is only in R3. The common attribute D of R3 and the rest is not a superkey of either side. Try this example in the checker below and step through every change.

In real life

EB bill

If every monthly bill row repeated the consumer's name and address, a change of address would need hundreds of updates. The board keeps Consumer and Bill in separate tables, joined on the service number.

College admissions

Splitting Applicant(AppNo, Name, Course, CourseFee) into (AppNo, Name, Course) and (Course, CourseFee) is lossless: Course is the key of the fee table.

Online shopping

Joining orders and products on a product name instead of a product ID would mix up two products with the same name: a lossy design.

Key points

  • Redundancy causes the update, insertion and deletion anomalies.
  • Decomposition splits R into R1, ..., Rn whose union is R.
  • Non-loss (lossless-join): R1 ⋈ R2 ⋈ ... ⋈ Rn = R, with no spurious tuples.
  • Two parts: lossless if R1 ∩ R2 → R1 or R1 ∩ R2 → R2 (the common attributes are a superkey of one part).
  • Three or more parts: use the tableau test; lossless if some row becomes all a's.
  • Lossless join is required; dependency preservation is desirable.
