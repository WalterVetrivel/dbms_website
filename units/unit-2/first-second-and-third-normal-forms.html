First, Second and Third Normal Forms

Normalization is a set of rules that tell us when a table stores too much in one place. Each rule is a normal form. This page walks through the first three, shows the dependency that breaks each one, and splits the tables until they pass.

What normalization is

Definition

Normalization is the process of splitting tables, using their functional dependencies, so that each fact is stored in one place. A normal form is a rule a table must pass. A table that passes a higher normal form also passes all the lower ones.

Normalization has two goals:

  1. No redundancy: each fact is stored only once.
  2. Sensible grouping: attributes that belong together stay together.

Why we need it

  • It removes repeated data, so the database uses less space.
  • It removes the update, insertion and deletion anomalies (see Non-loss Decomposition).
  • A fact changes in one place only, so the data stays consistent.
  • Smaller tables are easier to understand and to change.

Every split must be lossless. Joining the new tables must give back exactly the old table.

The normal forms at a glance

Normal formRuleWhat it removes

First normal form (1NF)

Definition

A relation is in first normal form if the domain of every attribute holds only atomic (single, indivisible) values. No cell may hold a list, a set or a repeating group.

A table in 1NF follows four rules:

  1. Each column holds single (atomic) values.
  2. All values in a column come from the same domain.
  3. Every column has a unique name.
  4. The order in which rows are stored does not matter.

Example

This Student table stores two phone numbers for students 1 and 3 in one cell, so it is not in 1NF:

Student (not in 1NF)
sidsnamephone
1Ajay98400 11111, 97100 22222
2Bindu99620 33333
3Chitra94440 44444, 90030 55555

To bring it to 1NF, give each phone number its own row. The key becomes {sid, phone}.

Prime and non-prime attributes

2NF and 3NF are defined using keys. Recall from Functional Dependencies:

  • A superkey is a set of attributes that identifies every row.
  • A candidate key is a minimal superkey. Remove any attribute and it stops being a superkey.
  • A prime attribute is part of some candidate key.
  • A non-prime attribute is not part of any candidate key.

Example

In Student(RegID, RollNo, Sname), both RegID and RollNo identify a student. The superkeys include {RegID}, {RollNo}, {RegID, RollNo} and {RegID, Sname}. The candidate keys are {RegID} and {RollNo}. So RegID and RollNo are prime, and Sname is non-prime.

In R(A, B, C, D) with key AB, the prime attributes are A and B. C and D are non-prime.

Second normal form (2NF)

Definition

A partial dependency is an FD X → A where A is non-prime and X is a proper part of a candidate key.

A relation is in second normal form if it is in 1NF and has no partial dependency. Every non-prime attribute depends on the whole of every candidate key.

For example, take R(A, B, C, D) with F = {AB → CD, A → C}. (AB)+ = {A, B, C, D}, so AB is the key. In A → C, the non-prime C depends on A, which is only part of the key. So A → C is a partial dependency and R is not in 2NF.

Shortcut

If every candidate key has only one attribute, there can be no partial dependency. Such a 1NF table is always in 2NF.

Example: Student_Course

Student_Course (in 1NF, not in 2NF)
sidsnamecidcname
1AjayC1Java
1AjayC2Python
2BinduC3C++
3ChitraC1Java
  1. The FDs are sid → sname and cid → cname. The key is {sid, cid}, because a student takes many courses and a course has many students.
  2. sid → sname and cid → cname are both partial: sname and cname depend on only one part of the key.
  3. The result is redundancy. “C1 is Java” is stored twice. Deleting student 2 also deletes the only record that C3 is C++ (a deletion anomaly).
  4. For each partial dependency X → Y, move X and Y into a new table. Keep X in the old table so the tables can be joined.
2NF tables 
Student(sid, sname)
Course(cid, cname)
Student_Course(sid, cid)

Each split shares a key (sid or cid) with the new table, so the decomposition is lossless.

Third normal form (3NF)

Definition

A transitive dependency is a chain X → Y and Y → Z, where X is a key and Y is not a superkey. Z depends on the key only through Y.

A relation is in third normal form if it is in 2NF and no non-prime attribute is transitively dependent on a key.

A shorter test that does not need 2NF first: R is in 3NF if, for every non-trivial FD X → A, at least one of these holds:

  1. X is a superkey of R, or
  2. A is a prime attribute.

Example: Student_details

Student_details (in 2NF, not in 3NF)
sidsnamezipcodecitynamestate
1Ajay600001ChennaiTamil Nadu
2Bindu560001BengaluruKarnataka
3Chitra600001ChennaiTamil Nadu
4Dev600020ChennaiTamil Nadu
  • FDs: sid → sname, sid → zipcode, zipcode → cityname, cityname → state.
  • The only candidate key is {sid}. It has one attribute, so the table is in 2NF.
  • The non-prime attributes are sname, zipcode, cityname and state.
  • sid → zipcode → cityname → state is a chain. cityname and state depend on sid only through zipcode. zipcode is not a key, so the table is not in 3NF.

Split on zipcode → cityname. Then the zip table still has cityname → state, which is another transitive dependency, so split again:

3NF tables 
Student(sid, sname, zipcode)
Zip(zipcode, cityname)
City(cityname, state)
Common mistake

Some notes split Student_details into only two tables, Student and Zip(zipcode, cityname, state). But they also list cityname → state. With that FD, Zip still has a transitive dependency (zipcode → cityname → state), so it is not in 3NF. It needs the third table City(cityname, state).

Worked example: R(A to J)

Take R(A, B, C, D, E, F, G, H, I, J) with F = {AB → C, A → DE, B → F, F → GH, D → IJ}. Find the key, then decompose R into 2NF and 3NF.

Step 1: find the key

  • A → DE, and D → IJ, so A+ = {A, D, E, I, J}.
  • B → F, and F → GH, so B+ = {B, F, G, H}.
  • AB → C. So (AB)+ = {A, B, C, D, E, F, G, H, I, J}, which is all of R.
  • A and B never appear on a right side, so both must be in every key. AB is the only candidate key.

Prime attributes: A and B. Every other attribute is non-prime.

Step 2: 2NF

A → DE and B → F are partial dependencies. Move each part of the key with everything it determines:

2NF 
R1(A, B, C)
R2(A, D, E, I, J)
R3(B, F, G, H)

Step 3: 3NF

R2 has D → IJ, and R3 has F → GH. D and F are not keys of their tables, so these are transitive dependencies. Split them out:

3NF 
R1(A, B, C)
R2(A, D, E)
R4(D, I, J)
R3(B, F)
R5(F, G, H)
Common mistake

Some notes give the 3NF tables as (A, B, C), (A, D, E), (D, I, J), (B, E) and (E, G, H). The last two are wrong: they should be (B, F) and (F, G, H), because the FDs are B → F and F → GH. E is already in (A, D, E). They also label three of the tables R1.

Question bank example

Normalize R(StudentID, StudentName, CourseID, CourseName, Instructor) into 2NF and 3NF. The question gives no FDs, so we state the business rules first:

  • Each student has one name: StudentID → StudentName.
  • Each course has one name and one instructor: CourseID → CourseName, Instructor.
  • A student takes many courses, so the key is {StudentID, CourseID}.

Partial dependencies

StudentID → StudentName and CourseID → CourseName, Instructor. Each non-prime attribute depends on only one part of the key. So R is in 1NF but not in 2NF.

2NF 
Student(StudentID, StudentName)
Course(CourseID, CourseName, Instructor)
Enrollment(StudentID, CourseID)

Transitive dependencies

With these rules there are none. In Course, both CourseName and Instructor depend directly on CourseID. So the 2NF tables are already in 3NF, and in BCNF too.

A transitive dependency would appear if the table also stored, say, the instructor's room: CourseID → Instructor → Room. Then Room would move to Instructor(Instructor, Room).

A different rule changes the answer

Suppose instead that a course has several instructors, and each instructor teaches only one course. Then {StudentID, CourseID} → Instructor and Instructor → CourseID. The 3NF tables still allow redundancy, and the fix is BCNF. Choose the second example in the animator to see it. Boyce-Codd Normal Form explains this case.

A popular way to remember 2NF and 3NF: every non-key attribute must depend on “the key, the whole key, and nothing but the key”.

The 3NF tables in SQL

Here are the Student_details tables in 3NF. Each table's key is its primary key, and the shared attributes become foreign keys.

SQL 
CREATE TABLE City (
  cityname VARCHAR(40) PRIMARY KEY,
  state    VARCHAR(40) NOT NULL
);

CREATE TABLE Zip (
  zipcode  CHAR(6) PRIMARY KEY,
  cityname VARCHAR(40) NOT NULL,
  FOREIGN KEY (cityname) REFERENCES City (cityname)
);

CREATE TABLE Student (
  sid     INT PRIMARY KEY,
  sname   VARCHAR(40) NOT NULL,
  zipcode CHAR(6),
  FOREIGN KEY (zipcode) REFERENCES Zip (zipcode)
);

INSERT INTO City VALUES ('Chennai', 'Tamil Nadu'), ('Bengaluru', 'Karnataka');
INSERT INTO Zip VALUES ('600001', 'Chennai'), ('600020', 'Chennai'), ('560001', 'Bengaluru');
INSERT INTO Student VALUES (1, 'Ajay', '600001'), (2, 'Bindu', '560001'),
                           (3, 'Chitra', '600001'), (4, 'Dev', '600020');

-- Join the tables to get the original table back.
SELECT s.sid, s.sname, s.zipcode, z.cityname, c.state
FROM Student s
JOIN Zip z ON z.zipcode = s.zipcode
JOIN City c ON c.cityname = z.cityname
ORDER BY s.sid;
Output 
+-----+--------+---------+-----------+------------+
| sid | sname  | zipcode | cityname  | state      |
+-----+--------+---------+-----------+------------+
|   1 | Ajay   | 600001  | Chennai   | Tamil Nadu |
|   2 | Bindu  | 560001  | Bengaluru | Karnataka  |
|   3 | Chitra | 600001  | Chennai   | Tamil Nadu |
|   4 | Dev    | 600020  | Chennai   | Tamil Nadu |
+-----+--------+---------+-----------+------------+

The join gives back exactly the four original rows. Now “Chennai is in Tamil Nadu” is stored once, in City.

In real life

Exam results

A result sheet with RegNo, CourseCode, CourseTitle and Grade repeats each course title for every student. Moving CourseTitle into a Course table is a 2NF step.

Courier addresses

A PIN code fixes the post office and district. Storing the district in every customer row is a transitive dependency. A PIN code table fixes it, as in 3NF.

Reports

Reporting databases sometimes keep repeated data on purpose to avoid joins. This is called denormalization, and it is done only after a normalized design exists.

Key points

  • Normalization splits tables using FDs so that each fact is stored once. Every split must be lossless.
  • 1NF: every cell holds one atomic value.
  • A prime attribute is part of some candidate key; a non-prime attribute is not.
  • 2NF: 1NF and no partial dependency (no non-prime attribute depends on part of a key).
  • 3NF: 2NF and no transitive dependency. Test: for every FD X → A, X is a superkey or A is prime.
  • To fix a violation X → Y, move X and Y to a new table and keep X in the old one.
  • A table whose keys all have one attribute is in 2NF as soon as it is in 1NF.
