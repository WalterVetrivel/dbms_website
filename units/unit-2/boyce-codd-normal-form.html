Boyce-Codd Normal Form

3NF still allows one kind of redundancy: an attribute that is part of a key can depend on something that is not a superkey. Boyce-Codd Normal Form closes this gap with one simple rule. This page shows the rule, the split it needs, and the price it sometimes costs.

Definition

Definition

A relation R is in Boyce-Codd Normal Form (BCNF) if, for every non-trivial FD X → Y that holds on R, X is a superkey of R.

  • A trivial FD has Y ⊆ X, such as AB → A. Trivial FDs always hold, so they are ignored.
  • In short: in BCNF, every determinant is a superkey. Only a key may decide the value of another attribute.
  • BCNF is stronger than 3NF. Every BCNF relation is in 3NF, but not every 3NF relation is in BCNF.

It is named after Raymond Boyce and Edgar Codd, who defined it in 1974. It is sometimes called 3.5NF.

What 3NF misses

Put the two rules side by side. For every non-trivial FD X → A:

The 3NF and BCNF conditions
3NF allows X → A ifBCNF allows X → A if
X is a superkey, or A is a prime attributeX is a superkey

The only difference is the escape clause “or A is prime”. So a relation can be in 3NF but not in BCNF only when some FD X → A has X not a superkey and A prime. That happens when the relation has two or more candidate keys that overlap (share an attribute).

Useful facts
  • A 3NF relation with only one candidate key is always in BCNF.
  • A 3NF relation whose candidate keys do not overlap is always in BCNF.
  • Any relation with only two attributes is in BCNF.
Common mistake

Some notes define BCNF as “a 3NF table with no overlapping candidate keys”. That is a quick test, not the definition. A 3NF table with overlapping keys can still be in BCNF. The definition is always: every determinant is a superkey.

Some notes also say “if Y is a prime attribute, X cannot be non-prime”. This is not the rule. BCNF does not care whether X or Y is prime. It only asks whether X is a superkey.

Example: Enrollment

Enrollment (in 3NF, not in BCNF)
sidcourseteacher
1CAnkita
1JavaPooja
2CArchana
3CAnkita
4JavaPooja

The rules:

  • A student can take many courses, and has one teacher for each course: (sid, course) → teacher.
  • A course can have several teachers (C has Ankita and Archana), but each teacher teaches one course: teacher → course.
  1. Keys: (sid, course)+ = {sid, course, teacher}. (sid, teacher)+ = {sid, teacher, course}. So both {sid, course} and {sid, teacher} are candidate keys. They overlap on sid.
  2. Prime attributes: sid, course and teacher are all prime. There is no non-prime attribute, so there can be no partial or transitive dependency. The relation is in 3NF.
  3. BCNF test: in teacher → course, teacher is not a superkey. So the relation is not in BCNF.

The redundancy is real: “Ankita teaches C” and “Pooja teaches Java” are each stored twice. If Ankita moves to Python, every one of her rows must change.

Common mistake

Some notes say teacher is a non-prime attribute here. It is prime, because it is part of the candidate key {sid, teacher}. That is exactly why 3NF allows teacher → course and BCNF does not.

The BCNF split puts the violating FD in its own table:

BCNF tables 
Teacher(teacher, course)
Student(sid, teacher)

The common attribute teacher is the key of Teacher, so the split is lossless. But (sid, course) → teacher is now lost: sid and course are in different tables. See Dependency Preservation for what that costs.

Finding the normal form of a relation

A common exam question gives R and F and asks for the highest normal form. Work like this:

  1. Find all candidate keys. List the prime and non-prime attributes.
  2. BCNF: is the left side of every FD a superkey? If yes, stop: R is in BCNF.
  3. 3NF: for every FD X → A, is X a superkey or A prime? If yes, R is in 3NF.
  4. 2NF: is there an FD X → A with A non-prime and X a proper part of a key? If not, R is in 2NF. Otherwise R is only in 1NF.

Example: R(A, B, C, D), F = {AB → C, AB → D, C → A, B → D}

  1. Keys: B never appears on a right side, so it is in every key. B+ = {B, D}, not enough. (AB)+ = {A, B, C, D} and (BC)+ = {B, C, A, D}. D appears only on right sides, so it is in no key. The candidate keys are AB and BC. Prime: A, B, C. Non-prime: D.
  2. BCNF? C → A: C is not a superkey. B → D: B is not a superkey. So R is not in BCNF.
  3. 3NF? C → A is allowed, because A is prime. But B → D fails: B is not a superkey, and D is not prime. So R is not in 3NF.
  4. 2NF? B → D: D is non-prime and B is a proper part of the key AB. That is a partial dependency, so R is not in 2NF.

R is in 1NF only.

Common mistake

Some notes show this example failing BCNF because of “C → D”. There is no such FD in F. The FDs that break BCNF are C → A and B → D.

More examples

R(A, B, C) with F = {A → B, B → C, C → A}

A+ = B+ = C+ = {A, B, C}, so A, B and C are each a candidate key. The left side of every FD is a key, so R is in BCNF.

Any relation with two attributes is in BCNF

Take R(A, B). The only possible non-trivial FDs are A → B and B → A.

  • If A → B holds, A is a key, because A+ = {A, B}.
  • If B → A holds, B is a key in the same way.
  • If neither holds, there is no non-trivial FD to break the rule. The key is {A, B}.

In every case, every determinant is a superkey, so R is in BCNF.

Question bank example

R(StudentID, StudentName, CourseID, CourseName, Instructor), where each instructor teaches only one course. The 2NF split gives Student, Course and Enrollment(StudentID, CourseID, Instructor). Enrollment is in 3NF but has Instructor → CourseID, so it is not in BCNF. It splits into Teaches(Instructor, CourseID) and Enrollment(StudentID, Instructor). Decomposing into BCNF

  1. Start with result = {R}.
  2. Find a table Ri in result with an FD X → Y that breaks BCNF (X is not a superkey of Ri).
  3. Replace Ri by two tables: the attributes of X+ that are in Ri, and Ri minus (X+ − X). X stays in both.
  4. Repeat until every table is in BCNF.
  • Every split is lossless, because X is a key of the first new table.
  • The result may not be dependency preserving. An FD whose attributes end up in different tables is lost.
  • The result can depend on the order in which violations are fixed.

Worked example

Continue with R(A, B, C, D), F = {AB → C, AB → D, C → A, B → D}.

  1. B → D breaks BCNF. B+ = {B, D}. Split into R1(B, D) and R2(A, B, C).
  2. R1(B, D) has two attributes, so it is in BCNF.
  3. R2(A, B, C) has AB → C and C → A, with keys AB and BC. C → A breaks BCNF. Split into R3(C, A) and R4(B, C).
  4. Result: R1(B, D), R3(C, A), R4(B, C).

The join is lossless. But AB → C is lost: no single table has A, B and C. After step 1, R1 and R2 were already in 3NF and kept every FD. That is the choice BCNF forces.

BCNF in SQL

In the 3NF table, the primary key enforces (sid, course) → teacher, but nothing enforces teacher → course:

SQL 
CREATE TABLE Enrollment (
  sid     INT,
  course  VARCHAR(20),
  teacher VARCHAR(20) NOT NULL,
  PRIMARY KEY (sid, course)
);

INSERT INTO Enrollment VALUES
  (1, 'C', 'Ankita'), (1, 'Java', 'Pooja'), (2, 'C', 'Archana'),
  (3, 'C', 'Ankita'), (4, 'Java', 'Pooja');

-- Accepted, but now Ankita seems to teach two courses.
INSERT INTO Enrollment VALUES (5, 'Java', 'Ankita');

SELECT teacher, COUNT(DISTINCT course) AS courses
FROM Enrollment
GROUP BY teacher
HAVING COUNT(DISTINCT course) > 1;
Output 
+---------+---------+
| teacher | courses |
+---------+---------+
| Ankita  |       2 |
+---------+---------+

In the BCNF tables, teacher is the primary key of Teacher, so teacher → course is enforced:

SQL 
CREATE TABLE Teacher (
  teacher VARCHAR(20) PRIMARY KEY,
  course  VARCHAR(20) NOT NULL
);

CREATE TABLE Student_Teacher (
  sid     INT,
  teacher VARCHAR(20),
  PRIMARY KEY (sid, teacher),
  FOREIGN KEY (teacher) REFERENCES Teacher (teacher)
);

INSERT INTO Teacher VALUES ('Ankita', 'C'), ('Archana', 'C'), ('Pooja', 'Java');
INSERT INTO Student_Teacher VALUES (1, 'Ankita'), (1, 'Pooja'), (2, 'Archana'),
                                   (3, 'Ankita'), (4, 'Pooja');

-- The join gives back the original rows.
SELECT s.sid, t.course, s.teacher
FROM Student_Teacher s
JOIN Teacher t ON t.teacher = s.teacher
ORDER BY s.sid, t.course;

-- Fails with a duplicate-key error: Ankita already has a course.
INSERT INTO Teacher VALUES ('Ankita', 'Java');
Output 
+-----+--------+---------+
| sid | course | teacher |
+-----+--------+---------+
|   1 | C      | Ankita  |
|   1 | Java   | Pooja   |
|   2 | C      | Archana |
|   3 | C      | Ankita  |
|   4 | Java   | Pooja   |
+-----+--------+---------+

The price: nothing now stops student 1 from taking both Ankita and Archana, two teachers for course C.

In real life

Lab batches

Each lab assistant handles one lab, and each student has one assistant per lab. Storing (Student, Lab, Assistant) together repeats “assistant handles lab” for every student: the Enrollment pattern.

Hospital shifts

Each nurse works in one ward, and each patient has one nurse per ward. A BCNF design keeps Nurse(nurse, ward) as its own table.

Design choice

Many real designs stop at 3NF when BCNF would lose an FD, and accept a little redundancy so that every rule stays a simple key.

Key points

  • BCNF: for every non-trivial FD X → Y, X is a superkey.
  • 3NF also allows X → A when A is prime. BCNF removes that exception.
  • 3NF and BCNF differ only when candidate keys overlap.
  • To decompose, split on a violating X → Y into (X ∪ Y) and (R − (Y − X)), and repeat.
  • BCNF decomposition is always lossless but may lose an FD; 3NF can always keep both.
  • Every relation with two attributes is in BCNF.
