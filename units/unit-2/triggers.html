Triggers

A trigger is SQL code that the database runs by itself when a row is inserted, updated or deleted. Triggers can fill in values, reject bad data and keep a history of changes, without any program having to remember to do it. This page shows how triggers work in MySQL, step by step.

What is a trigger

Definition

A trigger is a named block of SQL statements that the DBMS runs automatically when a given event happens on a given table. The events are INSERT, UPDATE and DELETE.

The name comes from a gun: pull the trigger and the shot follows by itself. In the same way, an INSERT on the table “pulls” the trigger, and its code runs. Nobody calls a trigger directly.

Suppose an HR manager must send a welcome message to every new employee. With thousands of new staff, doing it by hand is not possible. An AFTER INSERT trigger on the employee table can add a row to a message queue each time a new employee is added.

Triggers are used to:

  • fill in or compute values, such as a total or a timestamp;
  • check data and reject rows that break a business rule;
  • keep an audit log of who changed what;
  • keep summary or copy tables in step with the main table.

Event, condition, action

Textbooks describe a trigger with the event-condition-action (ECA) model:

The three parts of a trigger
PartMeaningExample
EventThe change that starts the triggerAn UPDATE on account
ConditionA test that decides if the action should runThe new balance is below 0
ActionThe SQL that runsRaise an error, or write a log row

In MySQL, the condition is written inside the action with IF ... THEN ... END IF.

Trigger syntax in MySQL

Syntax 
CREATE TRIGGER trigger_name
{BEFORE | AFTER} {INSERT | UPDATE | DELETE}
ON table_name
FOR EACH ROW
[{FOLLOWS | PRECEDES} other_trigger]
trigger_body;
  • BEFORE or AFTER says when the trigger runs: before or after the row is changed.
  • INSERT, UPDATE or DELETE is the event.
  • FOR EACH ROW makes it a row-level trigger. It runs once for every row the statement changes. MySQL supports only row-level triggers.
  • The body is one statement, or many statements between BEGIN and END.
Common mistake

Some notes give the syntax as [FOR EACH ROW | FOR EACH COLUMN] AS .... Both parts are wrong for MySQL.

  • There is no FOR EACH COLUMN in any SQL product. The SQL standard has FOR EACH ROW (row-level) and FOR EACH STATEMENT (statement-level, run once per statement). MySQL has only FOR EACH ROW.
  • The keyword AS before the body is SQL Server syntax. MySQL has no AS there.

The six kinds of trigger

Two timings times three events gives six kinds:

Trigger timing and event
TriggerRunsTypical use
BEFORE INSERTBefore a new row is savedFill in or check values
AFTER INSERTAfter a new row is savedLog the new row, update a summary
BEFORE UPDATEBefore a row is changedCheck or adjust the new values
AFTER UPDATEAfter a row is changedLog the old and new values
BEFORE DELETEBefore a row is removedStop the delete if a rule says so
AFTER DELETEAfter a row is removedCopy the row to an archive table

Use BEFORE when you want to change or stop the row. Use AFTER when you want to react to a change that has already happened.

For each row, MySQL runs the BEFORE trigger, then makes the change, then runs the AFTER trigger. Then it moves to the next row.

NEW and OLD

Inside a trigger, two names refer to the row being changed:

  • NEW.column is the value the row will have (or now has) after the change.
  • OLD.column is the value the row had before the change.
Which values each event has
EventOLDNEW
INSERTNo (there was no row before)Yes
UPDATEYesYes
DELETEYesNo (there is no row after)
  • OLD is always read-only.
  • NEW can be changed with SET NEW.column = ..., but only in a BEFORE trigger. In an AFTER trigger the row is already saved.

MySQL checks these rules when you create the trigger:

Output 
ERROR 1363 (HY000): There is no OLD row in on INSERT trigger
ERROR 1363 (HY000): There is no NEW row in on DELETE trigger
ERROR 1362 (HY000): Updating of NEW row is not allowed in after trigger

Example: computing values

This is the example from the notes, corrected so that it runs. A BEFORE INSERT trigger fills in the total and the percentage, so nobody has to type them.

SQL 
CREATE TABLE Student_Trigger (
  Student_RollNo         INT NOT NULL PRIMARY KEY,
  Student_FirstName      VARCHAR(100),
  Student_EnglishMarks   INT,
  Student_PhysicsMarks   INT,
  Student_ChemistryMarks INT,
  Student_MathsMarks     INT,
  Student_TotalMarks     INT,
  Student_Percentage     INT
);

CREATE TRIGGER Student_Table_Marks
BEFORE INSERT ON Student_Trigger
FOR EACH ROW
SET NEW.Student_TotalMarks = NEW.Student_EnglishMarks + NEW.Student_PhysicsMarks
                           + NEW.Student_ChemistryMarks + NEW.Student_MathsMarks,
    NEW.Student_Percentage = (NEW.Student_TotalMarks / 400) * 100;

INSERT INTO Student_Trigger VALUES (201, 'Sorya', 88, 75, 69, 92, 0, 0);

SELECT Student_RollNo, Student_FirstName, Student_TotalMarks, Student_Percentage
FROM Student_Trigger;
Output 
+----------------+-------------------+--------------------+--------------------+
| Student_RollNo | Student_FirstName | Student_TotalMarks | Student_Percentage |
+----------------+-------------------+--------------------+--------------------+
|            201 | Sorya             |                324 |                 81 |
+----------------+-------------------+--------------------+--------------------+

The INSERT gave 0 for the total and the percentage. The trigger replaced them with 324 and 81 before the row was saved. The second SET line can use the new total, because the first line has already set it.

Common mistake

The notes' version does not run, for two reasons:

  • The column Student_Percentage has no data type. Every column needs one, so we use INT.
  • The name Sorya has no quotes. Without quotes, MySQL reads it as a column name and fails with “Unknown column”. Text values need quotes: 'Sorya'.

Example: rejecting bad data

From here on we use a small bank table:

SQL 
CREATE TABLE account (
  acc_no  INT PRIMARY KEY,
  owner   VARCHAR(20) NOT NULL,
  balance DECIMAL(10,2) NOT NULL
);
INSERT INTO account VALUES (101, 'Anitha', 1000), (102, 'Bharath', 300), (103, 'Charan', 2500);

A BEFORE trigger can stop a change with SIGNAL. SIGNAL raises an error, so the statement fails and nothing is saved. SQLSTATE '45000' means “a user-defined error”.

SQL 
DELIMITER //
CREATE TRIGGER account_bi BEFORE INSERT ON account
FOR EACH ROW
BEGIN
  IF NEW.balance < 0 THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Balance cannot be negative';
  END IF;
END//
DELIMITER ;

INSERT INTO account VALUES (105, 'Esha', -50);
Output 
ERROR 1644 (45000): Balance cannot be negative

A matching BEFORE UPDATE trigger, account_bu, has the same body. Together they make sure no balance can go below zero, whatever program changes the table.

Why DELIMITER?

The body between BEGIN and END has its own semicolons. The mysql client would stop at the first one. DELIMITER // tells the client to end statements with // for a while, so the whole trigger is sent at once. DELIMITER ; sets it back. DELIMITER is a client command, not SQL. A one-statement trigger, like the one in the last section, does not need it.

A CHECK constraint (see Constraints), CHECK (balance >= 0), would also do this simple job, and is the better choice when it is enough. A trigger is needed when the rule looks at other tables or at the old value.

Example: an audit log

AFTER triggers can record every change in a log table. The log keeps the old and the new balance.

SQL 
CREATE TABLE balance_log (
  log_id      INT AUTO_INCREMENT PRIMARY KEY,
  acc_no      INT,
  action      VARCHAR(10),
  old_balance DECIMAL(10,2),
  new_balance DECIMAL(10,2),
  logged_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TRIGGER account_ai AFTER INSERT ON account
FOR EACH ROW
INSERT INTO balance_log (acc_no, action, old_balance, new_balance)
VALUES (NEW.acc_no, 'INSERT', NULL, NEW.balance);

CREATE TRIGGER account_au AFTER UPDATE ON account
FOR EACH ROW
INSERT INTO balance_log (acc_no, action, old_balance, new_balance)
VALUES (NEW.acc_no, 'UPDATE', OLD.balance, NEW.balance);

CREATE TRIGGER account_ad AFTER DELETE ON account
FOR EACH ROW
INSERT INTO balance_log (acc_no, action, old_balance, new_balance)
VALUES (OLD.acc_no, 'DELETE', OLD.balance, NULL);

Now run three ordinary statements:

SQL 
INSERT INTO account VALUES (104, 'Divya', 500);
UPDATE account SET balance = balance - 200 WHERE acc_no = 101;
DELETE FROM account WHERE acc_no = 102;

SELECT log_id, acc_no, action, old_balance, new_balance FROM balance_log;
Output 
+--------+--------+--------+-------------+-------------+
| log_id | acc_no | action | old_balance | new_balance |
+--------+--------+--------+-------------+-------------+
|      1 |    104 | INSERT |        NULL |      500.00 |
|      2 |    101 | UPDATE |     1000.00 |      800.00 |
|      3 |    102 | DELETE |      300.00 |        NULL |
+--------+--------+--------+-------------+-------------+

The INSERT trigger uses only NEW, the DELETE trigger uses only OLD, and the UPDATE trigger uses both.

If a trigger fails, the whole statement fails. For InnoDB tables, every change the statement made is undone, including rows changed before the error and rows the triggers wrote. Try the “fails on the second row” statement below to see this.

Viewing and dropping triggers

SQL 
SHOW TRIGGERS;                         -- all triggers in the current database
SHOW TRIGGERS LIKE 'account';          -- triggers on tables named like 'account'
DROP TRIGGER account_ad;
DROP TRIGGER IF EXISTS account_ad;     -- no error if it is already gone
  • MySQL has no ALTER TRIGGER. To change a trigger, drop it and create it again.
  • A table can have more than one trigger for the same timing and event. They run in the order they were created, unless FOLLOWS or PRECEDES sets the order.
  • A trigger belongs to its table. If you drop the table, its triggers are dropped too.

Limits and good practice

MySQL triggers have some limits:

  • A trigger cannot change the table it is defined on (error 1442). Use SET NEW.column in a BEFORE trigger instead.
  • A trigger can be made only on a base table, not on a view or a temporary table.
  • TRUNCATE TABLE does not run DELETE triggers.
  • Changes made by foreign key actions such as ON DELETE CASCADE do not run triggers.

Advantages

  • Rules are enforced in one place, for every program that uses the table.
  • They run automatically, so nobody can forget.
  • They can check values before they are saved.
  • They make audit logs easy.

Disadvantages

  • They run “silently”, so the effects of a statement can surprise people.
  • Long trigger code slows down every INSERT, UPDATE or DELETE.
  • Triggers that fire other triggers are hard to follow.
  • Logic is split between the program and the database.
Common mistake

Some notes say triggers “are not compiled” and that “it is not possible to find and debug the errors in triggers”. That is too strong. MySQL checks a trigger's syntax, and the NEW and OLD column names, when you create it. Other mistakes, such as a missing table, are reported as normal errors when the trigger runs. Debugging is harder than in normal code, because you cannot call a trigger directly. A common way is to write values into a log table, as in the audit example.

In real life

Banking

Every change to a balance is copied to a history table by an AFTER UPDATE trigger, so auditors can see each step.

Online shops

When an order row is inserted, a trigger reduces the stock count of the product and flags it if stock runs low.

Timestamps

A BEFORE UPDATE trigger sets a last_modified column on every change, so the app never forgets to do it.

Key points

  • A trigger is SQL that runs automatically on INSERT, UPDATE or DELETE on a table.
  • It follows the event-condition-action model.
  • BEFORE triggers can change NEW or stop the change. AFTER triggers react to a change already made.
  • MySQL triggers are row-level: FOR EACH ROW. They run once per changed row.
  • INSERT has only NEW, DELETE has only OLD, and UPDATE has both.
  • SIGNAL SQLSTATE '45000' raises an error and makes the whole statement fail.
  • Use DELIMITER in the mysql client for a trigger body with BEGIN ... END.
  • Keep triggers short. Prefer a CHECK constraint when it is enough.
