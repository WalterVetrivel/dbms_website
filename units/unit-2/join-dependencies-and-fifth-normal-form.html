Join Dependencies and Fifth Normal Form

A multivalued dependency tells us when a table can be split into two parts without loss. Some tables cannot be split into two, but can be split into three. A join dependency describes this, and fifth normal form is the last step of normalization.

Join dependency

Definition

Let R1, R2, ..., Rn be sets of attributes whose union is R. The join dependency *(R1, R2, ..., Rn) holds on R if every legal instance r of R equals the natural join of its projections:

r = πR1(r) ⋈ πR2(r) ⋈ ... ⋈ πRn(r)

  • In other words, a JD says “splitting R into R1, ..., Rn is always lossless”.
  • A JD with two parts is an MVD. *(R1, R2) holds exactly when (R1 ∩ R2) →→ R1 holds.
  • A JD is trivial if one of the Ri is all of R. A trivial JD holds in every relation.

Example: take R(A, B, C, D) with the JD *((A, B, C), (C, D)). Then R can always be split into (A, B, C) and (C, D). Joining them back on C gives no spurious rows.

Common mistake

Some notes write this JD as “*(A, B, C, D), (C, D)”. Each part goes in its own brackets: *((A, B, C), (C, D)). The first part is (A, B, C), not all four attributes.

A table that needs three parts

A firm records which seller sells which product for which company. It has one business rule:

The rule

If a seller represents a company, the company makes a product, and the seller sells that kind of product, then the seller sells that product for that company.

Supply(seller, company, product)
sellercompanyproduct
RaviGodrejAC
RaviLGFridge
KumarGodrejFridge
RaviGodrejFridge
  • The key is all three attributes. There is no non-trivial FD, so the table is in BCNF.
  • There is no non-trivial MVD either. For example, seller →→ company fails: Ravi has companies Godrej and LG and products AC and Fridge, but (Ravi, LG, AC) is not in the table. So the table is in 4NF.

Every split into two is lossy

Split into (seller, company) and (company, product), and join on company. Kumar represents Godrej, and Godrej makes ACs, so the join adds (Kumar, Godrej, AC). That row was never true: Kumar does not sell ACs. The other two-way splits also add a false row.

The split into three is lossless

Add the third projection, (seller, product), and join all three. The false row needs (Kumar, AC) in Seller_Product, which is not there, so it drops out. The join gives back exactly the four rows.

So the table satisfies the JD *((seller, company), (company, product), (seller, product)). This JD is what the business rule says, in the language of joins.

Fifth normal form (5NF)

Definition

A relation R is in fifth normal form if every non-trivial join dependency that holds on R is implied by the candidate keys of R. 5NF is also called project-join normal form (PJNF).

  • A JD is implied by the keys when each of its parts contains a key, or when the parts can be joined one by one on keys. Such a split never removes any redundancy.
  • In practice: a table is in 5NF if it is in 4NF and cannot be split further without loss, except in trivial ways that follow from its keys.
  • Every 5NF table is in 4NF, because an MVD is a JD with two parts.
  • Supply is in 4NF but not in 5NF. Its JD has three parts, and none of them contains the key (all three attributes).
How rare is it?

A table in 4NF but not in 5NF needs a rule that links three or more things in a cycle, like the seller rule. Such rules are rare, so most 4NF tables are already in 5NF. 5NF is mostly asked about in theory and exams.

Decomposing into 5NF

Split the table on its join dependency, one table per part:

5NF tables 
Seller_Company(seller, company)
Company_Product(company, product)
Seller_Product(seller, product)
  • Each table states one simple fact: who represents whom, who makes what, and who sells what.
  • The rule is now built into the design. Recording that Kumar sells ACs is one row in Seller_Product; the join then shows Kumar selling Godrej ACs automatically.
  • In the single table, the same change would need us to work out and insert every row the rule implies.
Common mistake

Some notes say this table has the MVD seller →→ {company, product}, so it is not in 4NF, and split it into two tables before reaching three. But seller →→ {company, product} is trivial, because seller ∪ {company, product} is the whole relation. The table is already in 4NF. As shown above, every split into two is lossy. The correct 5NF step goes straight to the three tables.

All the normal forms

Normal forms from 1NF to 5NF
Normal formConditionRemoves
1NFAtomic values onlyRepeating groups
2NF1NF, and no non-prime attribute depends on part of a keyPartial dependencies
3NFFor every FD X → A: X is a superkey or A is primeTransitive dependencies
BCNFFor every FD X → Y: X is a superkeyAll FD redundancy
4NFFor every MVD X →→ Y: X is a superkeyIndependent multi-valued facts
5NFEvery JD is implied by the candidate keysRedundancy from join dependencies

Each form includes the ones above it: 5NF ⊂ 4NF ⊂ BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF. Every step must be lossless. Up to 3NF, every step can also keep all FDs.

The 5NF tables in SQL

SQL 
CREATE TABLE Seller_Company (
  seller  VARCHAR(20),
  company VARCHAR(20),
  PRIMARY KEY (seller, company)
);

CREATE TABLE Company_Product (
  company VARCHAR(20),
  product VARCHAR(20),
  PRIMARY KEY (company, product)
);

CREATE TABLE Seller_Product (
  seller  VARCHAR(20),
  product VARCHAR(20),
  PRIMARY KEY (seller, product)
);

INSERT INTO Seller_Company VALUES ('Ravi', 'Godrej'), ('Ravi', 'LG'), ('Kumar', 'Godrej');
INSERT INTO Company_Product VALUES ('Godrej', 'AC'), ('Godrej', 'Fridge'), ('LG', 'Fridge');
INSERT INTO Seller_Product VALUES ('Ravi', 'AC'), ('Ravi', 'Fridge'), ('Kumar', 'Fridge');

-- Joining all three gives back exactly the four original rows.
SELECT sc.seller, sc.company, cp.product
FROM Seller_Company sc
JOIN Company_Product cp ON cp.company = sc.company
JOIN Seller_Product sp ON sp.seller = sc.seller AND sp.product = cp.product
ORDER BY sc.seller DESC, sc.company, cp.product;
Output 
+--------+---------+---------+
| seller | company | product |
+--------+---------+---------+
| Ravi   | Godrej  | AC      |
| Ravi   | Godrej  | Fridge  |
| Ravi   | LG      | Fridge  |
| Kumar  | Godrej  | Fridge  |
+--------+---------+---------+

Leave out the last JOIN line and the result has five rows, including the false (Kumar, Godrej, AC). The third table is what makes the join exact.

In real life

Medical reps

A rep covers some pharma companies and some kinds of medicine. If the rep sells every covered company's medicine of a covered kind, the rule is a three-way join dependency.

Faculty and labs

A faculty member handles some subjects and some labs, and each lab supports some subjects. If they teach every supported subject in their labs, store the three pairs separately.

Supply chains

Supplier, part and project tables in procurement systems are the classic textbook case for 5NF.

Key points

  • *(R1, ..., Rn) holds if R always equals the join of its projections on R1, ..., Rn.
  • An MVD is a join dependency with two parts.
  • Some tables are lossy for every split into two but lossless for a split into three.
  • 5NF (PJNF): every non-trivial JD is implied by the candidate keys.
  • To reach 5NF, split the table on its join dependency, one table per part.
  • 5NF ⊂ 4NF ⊂ BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF.
