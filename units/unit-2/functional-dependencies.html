Functional Dependencies

A functional dependency is a rule such as “one roll number always has one name”. These rules decide the keys of a table and whether the table has redundancy. This page explains the rules, how to reason with them, and the three calculations asked in every exam: attribute closure, candidate keys and canonical cover.

Learning outcomes

  • Name the types of functional dependencies with examples.
  • Use Armstrong's axioms to derive new dependencies.
  • Compute an attribute closure, find all candidate keys and find a canonical cover.

What is a functional dependency?

Look at this table. Every time RollNo is 1, Name is Anitha. One roll number never has two names.

Student
RollNoNameDept
1AnithaCSE
2BharathIT
3AnithaECE
Definition

Let X and Y be sets of attributes of a relation R. The functional dependency X → Y holds on R if any two tuples that have the same value for X also have the same value for Y.

In symbols: if t1[X] = t2[X], then t1[Y] = t2[Y]. We read X → Y as “X functionally determines Y”. X is the determinant (left side) and Y is the dependent (right side).

  • RollNo → Name holds: a roll number gives exactly one name.
  • Name → RollNo does not hold: “Anitha” has roll numbers 1 and 3.
  • If a table had two rows with RollNo 1, one with Anitha and one with Divya, then RollNo → Name would fail on that table.
Note

An FD is a rule about every possible table, not only the rows you see today. We decide FDs from the meaning of the data. One table can show that an FD fails, but no table can prove that an FD holds.

An FD generalizes the idea of a key. K is a superkey of R exactly when K → R, that is, K determines every attribute.

Types of functional dependencies

We use Marks(RegNo, CourseID, StudentName, CourseName, Marks, Dept, HOD), where a student is in one department and each department has one HOD.

  • A prime attribute is part of some candidate key. A non-prime attribute is not part of any candidate key.
  • Partial dependencies break 2NF, and transitive dependencies break 3NF. See First, Second and Third Normal Forms.

Armstrong's axioms

From some FDs we can infer (derive) others. Armstrong's axioms are three rules for this. X, Y, Z and W are sets of attributes.

Armstrong's axioms and the extra rules
RuleStatementExample
ReflexivityIf Y ⊆ X, then X → YAB → A
AugmentationIf X → Y, then XZ → YZA → B gives AC → BC
TransitivityIf X → Y and Y → Z, then X → ZA → B and B → C give A → C
UnionIf X → Y and X → Z, then X → YZA → B and A → C give A → BC
DecompositionIf X → YZ, then X → Y and X → ZA → BC gives A → B
PseudotransitivityIf X → Y and WY → Z, then WX → ZA → B and CB → D give CA → D
  • The first three are the axioms. The last three can be proved from them, so they are derived rules.
  • The axioms are sound: they never produce a false FD. They are complete: they produce every FD that follows from F.

Closure of a set of FDs

Definition

The closure of a set of FDs F, written F+, is the set of all FDs that can be inferred from F.

F+ is very large, because it contains every trivial FD too. With 5 attributes it has thousands of FDs. So in practice we do not list F+. Instead we compute the closure of an attribute set, which answers the same questions much faster.

Two sets of FDs F and G are equivalent if F+ = G+. A canonical cover is a smaller set equivalent to F.

Attribute closure

Definition

The closure of an attribute set X under F, written X+, is the set of all attributes that X determines.

Algorithm 
result := X
repeat
  for each FD  Y → Z  in F do
    if Y ⊆ result then result := result ∪ Z
until result does not change
return result

Worked example

R(A, B, C, D, E) with F = {A → BC, CD → E, B → D, E → A}. Find A+.

Computing A+
StepFD usedResult
StartReflexivity{A}
1A → BC{A, B, C}
2B → D{A, B, C, D}
3CD → E{A, B, C, D, E}

A+ contains every attribute, so A is a superkey. In the same way, B+ = {B, D}, C+ = {C} and D+ = {D}. Both E+ and (CD)+ are {A, B, C, D, E}.

Uses of attribute closure

  • Superkey test: X is a superkey if X+ contains all attributes of R.
  • FD test: X → Y is in F+ if Y ⊆ X+.
  • Computing F+: for each subset X, every Y ⊆ X+ gives X → Y.

Finding candidate keys

A candidate key is a minimal set X with X+ = all attributes. A quick method:

  1. An attribute that never appears on a right side must be in every key, because nothing else determines it.
  2. An attribute that appears only on right sides is never needed in a key.
  3. Start with the attributes from step 1. If their closure is everything, that is the only key.
  4. Otherwise, add the other attributes one at a time, then two at a time, and test each closure. Skip any set that contains a key already found.

For F = {A → BC, CD → E, B → D, E → A}, every attribute is on some right side. Testing single attributes gives the keys A and E. Testing pairs without A or E gives BC and CD:

  • (BC)+: B → D gives BCD, CD → E gives BCDE, E → A gives ABCDE. So BC is a key.
  • (BD)+ = {B, D} and (DE)+ contains E, which is already a key.

The candidate keys are A, E, BC and CD. All five attributes are prime.

Common mistake

The notes' solution for this example lists D+ as {ABCDE} and (CD)+ as {ABCD}. The correct values are D+ = {D} and (CD)+ = {ABCDE}. The notes also miss the candidate key BC. Always test every combination, not just the ones in the FDs.

Canonical cover

Definitions
  • An attribute of an FD is extraneous if we can remove it without changing F+.
  • A canonical cover Fc (minimal cover) is a set of FDs equivalent to F. It has no extraneous attribute and no redundant FD, and no two of its FDs have the same left side.

A canonical cover lets the DBMS check fewer, smaller FDs on every update. To find one:

  1. Split every right side into single attributes (decomposition rule).
  2. Remove extraneous left-side attributes. In XA → B, A is extraneous if B ⊆ X+.
  3. Remove redundant FDs. X → B is redundant if B ⊆ X+ computed without that FD.
  4. Combine FDs with the same left side (union rule).

Worked example

F = {A → C, AC → D, B → ADE}.

Finding the canonical cover

2. Left sidesIn AC → D: A+ = {A, C, D} contains D, so C is extraneousA → C, A → D, B → A, B → D, B → E
3. RedundantWithout B → D: B+ = {A, B, C, D, E} still has D, so remove it. The others are needed.A → C, A → D, B → A, B → E

So Fc = {A → CD, B → AE}.

Exam tip

Remove extraneous left-side attributes before you remove redundant FDs. Doing it the other way can leave a redundant FD in the answer. Your notes remove redundant FDs first; in this example both orders give the same answer.

Proving a key with the inference rules

R(A, B, C, D, E, F, G, H, I, J) with F = {AB → C, A → DE, B → F, F → GH, D → IJ}. Show that AB is a key.

  1. A → DE (given), so A → D and A → E (decomposition).
  2. D → IJ (given) and A → D give A → IJ (transitivity).
  3. A → DEIJ (union), and A → A (reflexivity), so A → ADEIJ (union).
  4. B → F (given) and F → GH (given) give B → GH (transitivity), so B → BFGH (union with B → B and B → F).
  5. From steps 3 and 4: AB → ADEIJ and AB → BFGH (augmentation), and AB → C (given).
  6. Union: AB → ABCDEFGHIJ, so AB is a superkey.
  7. A+ = {A, D, E, I, J} and B+ = {B, F, G, H}. Neither alone is a superkey, so AB is minimal: a candidate key.

The page First, Second and Third Normal Forms splits this relation into 2NF and then 3NF tables.

In real life

PIN code

PIN code → District and District → State. So PIN code → State is a transitive dependency. Postal software stores the state only once for each district.

IFSC

IFSC → BankName, Branch, City. A payment form only asks for the IFSC and fills in the rest, because the FD guarantees one answer.

Train number

TrainNo → TrainName, but (TrainNo, Date) → Status. The status depends on the whole key, not on the train number alone.

Key points

  • X → Y: tuples that agree on X must agree on Y. FDs come from the meaning of the data.
  • Types: trivial, non-trivial, full, partial (on part of a key) and transitive (through a non-key).
  • Armstrong's axioms: reflexivity, augmentation and transitivity. Union, decomposition and pseudotransitivity are derived from them.
  • F+ is every FD implied by F. X+ is every attribute X determines.
  • X is a superkey if X+ is all attributes; a candidate key if it is also minimal.
  • Attributes never on a right side are in every candidate key.
  • Canonical cover: split right sides, remove extraneous left-side attributes, remove redundant FDs, combine.
