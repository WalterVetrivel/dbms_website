ER-to-Relational Mapping

An E-R diagram is a picture; a DBMS stores tables. ER-to-relational mapping is the set of rules that turns each part of the diagram into tables, primary keys and foreign keys. Follow the steps below, then watch the widget map the university, bank and car insurance diagrams.

The idea

In the logical design step, we turn the E-R diagram into a relational schema. Every entity set and many relationship sets become tables. The lines of the diagram become foreign keys.

We use the university diagram from E-R Diagrams. Its main parts are:

  • Student(ID, Name (First, Last), Phone (multivalued), DOB, Age (derived))
  • Course(CourseID, Title, Credits) and Instructor(InstID, IName, Salary)
  • Section, a weak entity set of Course, with the partial key SecNo
  • Takes (M : N, with Grade), Teaches (M : N) and Advisor (1 : N, Instructor to Student)

Elmasri and Navathe give the mapping as seven steps. We follow them in order.

Step 1: strong entity sets

Rule

For each strong entity set, make a table with all its simple attributes. Its key becomes the primary key of the table.

  • A composite attribute is stored as its parts. Name becomes two columns, First and Last.
  • A derived attribute is not stored. Age is calculated from DOB when needed.
  • A multivalued attribute is left out for now. It gets its own table in step 6.
SQL 
CREATE TABLE Student (
  ID     CHAR(10),
  First  VARCHAR(30),
  Last   VARCHAR(30),
  DOB    DATE,
  PRIMARY KEY (ID)
);

CREATE TABLE Course (
  CourseID CHAR(6),
  Title    VARCHAR(50),
  Credits  INT,
  PRIMARY KEY (CourseID)
);

Instructor(InstID, IName, Salary) is mapped the same way.

Step 2: weak entity sets

Rule

For each weak entity set, make a table with its attributes plus the primary key of its owner. The primary key is owner's key + partial key. The owner's key is also a foreign key, usually with ON DELETE CASCADE.

SQL 
CREATE TABLE Section (
  CourseID  CHAR(6),
  SecNo     INT,
  Semester  VARCHAR(10),
  PRIMARY KEY (CourseID, SecNo),
  FOREIGN KEY (CourseID) REFERENCES Course (CourseID)
    ON DELETE CASCADE
);
  • ON DELETE CASCADE says: when a course is deleted, delete its sections too. A section cannot exist without its course.
  • The identifying relationship Sec_of needs no table. The foreign key CourseID already stores it.

Step 3: 1 : 1 relationships

Rule

Pick one of the two tables, S. Add the primary key of the other table, T, to S as a foreign key. Choose for S the entity set with total participation, so the column is never NULL.

Example: Manages is 1 : 1 between Employee and Department, and every department has a manager. Department has total participation, so the foreign key goes into Department:

SQL 
CREATE TABLE Department (
  DeptID   INT,
  DName    VARCHAR(30),
  MgrID    CHAR(5) NOT NULL UNIQUE,   -- the manager
  MgrSince DATE,                      -- attribute of Manages
  PRIMARY KEY (DeptID),
  FOREIGN KEY (MgrID) REFERENCES Employee (EmpID)
);

UNIQUE keeps the relationship one to one: no employee can manage two departments. Attributes of the relationship, such as MgrSince, go into the same table.

Step 4: 1 : N relationships

Rule

Add the primary key of the “one” side as a foreign key in the table of the “many” side. Put the attributes of the relationship there too. No new table is needed.

Advisor is 1 : N from Instructor to Student. One instructor has many students, and each student has one advisor. So Student gets InstID:

SQL 
ALTER TABLE Student
  ADD InstID CHAR(5) NOT NULL,   -- total participation: never NULL
  ADD FOREIGN KEY (InstID) REFERENCES Instructor (InstID);
Exam tip

Ask “which side is many?” The foreign key always goes into the many side. If you put it on the one side, an instructor row would need many InstID values for many students, which a column cannot hold.

The other approach: a separate table

Your notes show two approaches for a relationship with a key constraint:

  • Approach 1: make a separate table, such as Advisor(ID, InstID). Its primary key is the key of the many side, ID.
  • Approach 2: add the foreign key to the many side, as above. This is usually better. It needs one table fewer, and a query for a student's advisor needs no join. The cost is NULL values when many students have no advisor.

Step 5: M : N relationships

Rule

Make a new table for the relationship. Its columns are the primary keys of the participating entity sets, as foreign keys, plus the attributes of the relationship. The primary key is the combination of the foreign keys.

SQL 
CREATE TABLE Takes (
  ID        CHAR(10),
  CourseID  CHAR(6),
  Grade     CHAR(2),
  PRIMARY KEY (ID, CourseID),
  FOREIGN KEY (ID)       REFERENCES Student (ID),
  FOREIGN KEY (CourseID) REFERENCES Course (CourseID)
);

A foreign key cannot work here. A student takes many courses, so Student would need many CourseID values in one row. The new table holds one row for each (student, course) pair.

Common mistake

The notes' Works_In table copies EName, Salary, DeptName and Building into the relationship table. Those are attributes of the entity sets, and copying them causes redundancy. A relationship table holds only the keys of the entity sets and the relationship's own attributes. Also, a table name cannot contain a space (“Works In”), and MySQL needs the referenced column after REFERENCES, as in REFERENCES Employee (EmpID).

Step 6: multivalued attributes

Rule

For each multivalued attribute, make a new table with the primary key of the owner and the attribute. Both together form the primary key.

SQL 
CREATE TABLE Student_Phone (
  ID     CHAR(10),
  Phone  VARCHAR(15),
  PRIMARY KEY (ID, Phone),
  FOREIGN KEY (ID) REFERENCES Student (ID)
);

A student with three phone numbers has three rows here. We never store “9876543210, 9443012345” in one column, because a relational column holds one atomic value.

Step 7: relationships of degree 3 or more

A ternary relationship, such as Sells(Product, Supplier, Customer) with Price, becomes a new table. It holds the three primary keys as foreign keys and the attribute Price. Usually all three keys together form the primary key.

Schema 
Sells(ProductID, SupplierID, CustomerID, Price)

Mapping specialization and generalization

An extended E-R (EER) diagram can show a superclass with subclasses. Example: InventoryItem(ID, Name) with the subclasses Book(Publisher) and DVD(Manufacturer). There are three ways to map it:

Three ways to map InventoryItem, Book and DVD
MethodTablesDrawback
1. A table for the superclass and each subclassInventoryItem(ID, Name), Book(ID, Publisher), DVD(ID, Manufacturer)Needs a join to see all the data of a book
2. Tables for the subclasses onlyBook(ID, Name, Publisher), DVD(ID, Name, Manufacturer)An item that is neither a book nor a DVD has no table
3. One table for the superclass onlyInventoryItem(ID, Name, Publisher, Manufacturer)Many NULLs: a book has no Manufacturer, a DVD has no Publisher

In method 1, ID in Book and DVD is both the primary key and a foreign key to InventoryItem.

Summary: E-R construct to table

How each E-R construct maps to the relational model
E-R constructRelational construct
Strong entity setTable; key becomes the primary key
Weak entity setTable; primary key = owner's key + partial key; foreign key to the owner
1 : 1 relationship setForeign key (UNIQUE) in one table, preferably the total side
1 : N relationship setForeign key in the table of the many side
M : N relationship setNew table; primary key = both foreign keys
n-ary relationship setNew table with all the foreign keys
Simple attributeColumn
Composite attributeOne column for each part
Multivalued attributeNew table (owner key, value)
Derived attributeNot stored; computed in queries or views

After mapping, check each table for redundancy with normalization. The steps from an E-R diagram to normalized relations are: map the diagram, list the functional dependencies of each table, then split any table that breaks a normal form.

In real life

Online shopping

Order contains Product is M : N, so the shop has an OrderItem(OrderID, ProductID, Quantity) table. Every shopping site has a table like this.

UPI payments

One bank account has many UPI IDs (1 : N), so the UPI ID table stores the account number as a foreign key.

College ERP

A student's parents' phone numbers are multivalued. The ERP keeps them in a separate StudentContact table, one row for each number.

Key points

  • Strong entity set: a table with its simple attributes; its key is the primary key.
  • Weak entity set: a table whose primary key is the owner's key + the partial key.
  • 1 : N: the foreign key goes into the many side. 1 : 1: into either side, preferably the total side.
  • M : N: a new table whose primary key is both foreign keys, plus the relationship attributes.
  • Multivalued attribute: a new table (owner key, value). Composite: one column per part. Derived: not stored.
  • A relationship table holds only keys and the relationship's own attributes.
