Sub Queries

A subquery is a query inside another query. It lets you ask a question whose answer depends on another question, such as “who earns more than the average?”. This page covers every kind of subquery, shows how each one runs, and fixes some common myths.

Learning outcomes

After this page you can
  • Write single-row and multiple-row subqueries and pick the right operator for each.
  • Use IN, ANY, ALL and EXISTS correctly.
  • Explain how a correlated subquery runs and why it can be slow.
  • Use subqueries in FROM, SELECT and HAVING, and inside INSERT, UPDATE and DELETE.

What is a subquery

Definition

A subquery (or inner query) is a SELECT statement written inside another SQL statement. The statement around it is the outer query (or main query). The outer query uses the result of the subquery.

The rules:

  • A subquery is always written in brackets: ( SELECT ... ).
  • It can appear in the WHERE, HAVING, FROM and SELECT clauses.
  • It can be used inside SELECT, INSERT, UPDATE and DELETE statements.
  • It can be used with =, <, >, <=, >=, <>, IN, ANY, ALL and EXISTS.
  • A subquery that returns more than one row needs IN, ANY, ALL or EXISTS. A plain = or > needs a single value.

We name subqueries by what they return:

Kinds of subquery
KindReturnsUsed with
Single-row (scalar)One value=, <, >, <=, >=, <>
Multiple-rowOne column, many rowsIN, NOT IN, ANY, ALL
Table (derived table)Many rows and columnsFROM clause
CorrelatedAny of the above, once per outer rowUses a column of the outer query
Common mistake

Some notes say a subquery cannot use ORDER BY, and that GROUP BY “does the same job”. Both parts are wrong.

  • GROUP BY makes groups. It does not sort. ORDER BY sorts.
  • MySQL allows ORDER BY in a subquery. It matters together with LIMIT, as in (SELECT ID FROM EMPLOYEE ORDER BY SALARY DESC LIMIT 1). Without LIMIT, the order of a subquery's rows has no effect on the final result.

Some notes also say a subquery must be on the right side of the operator. That is only the usual style. WHERE (SELECT AVG(SALARY) FROM EMPLOYEE) < SALARY is also valid.

Single-row subqueries

A single-row subquery returns exactly one value. The outer query compares each row with that value. Aggregate functions such as AVG and MAX (see Aggregate Functions) are a common way to get one value.

Who earns more than the company average?

SQL 
SELECT NAME, SALARY
FROM EMPLOYEE
WHERE SALARY > (SELECT AVG(SALARY) FROM EMPLOYEE);
Output 
+---------+----------+
| NAME    | SALARY   |
+---------+----------+
| Alina   |  6500.00 |
| Kathrin |  8500.00 |
| Jackson | 10000.00 |
+---------+----------+
  1. The subquery runs first and returns 5000.
  2. The outer query becomes WHERE SALARY > 5000.
  3. Three rows pass.

We cannot write WHERE SALARY > AVG(SALARY). An aggregate is not allowed in WHERE, because WHERE looks at one row at a time. The subquery solves this.

Who earns the highest salary?

SQL 
SELECT NAME, SALARY
FROM EMPLOYEE
WHERE SALARY = (SELECT MAX(SALARY) FROM EMPLOYEE);
Output 
+---------+----------+
| NAME    | SALARY   |
+---------+----------+
| Jackson | 10000.00 |
+---------+----------+
Common mistake

Using = with a subquery that returns many rows. This query fails, because there are three IT salaries:

SQL 
SELECT NAME FROM EMPLOYEE
WHERE SALARY = (SELECT SALARY FROM EMPLOYEE WHERE DEPT = 'IT');
Output 
ERROR 1242 (21000): Subquery returns more than 1 row

Use IN, ANY or ALL instead, as shown next. If the subquery returns no rows, its value is NULL, and the comparison is never true.

Multiple-row subqueries

A multiple-row subquery returns one column with many rows. It needs an operator that works on a list.

IN

IN is true when the value equals any value in the list. This is the example from the notes:

SQL 
SELECT *
FROM EMPLOYEE
WHERE ID IN (SELECT ID FROM EMPLOYEE WHERE SALARY > 4500);
Output 
+----+---------+------+-----------+------+----------+
| ID | NAME    | AGE  | ADDRESS   | DEPT | SALARY   |
+----+---------+------+-----------+------+----------+
|  4 | Alina   |   29 | UK        | IT   |  6500.00 |
|  5 | Kathrin |   34 | Bangalore | HR   |  8500.00 |
|  7 | Jackson |   25 | Mizoram   | IT   | 10000.00 |
+----+---------+------+-----------+------+----------+

The subquery returns the list (4, 5, 7). The outer query keeps the rows whose ID is in that list. Here a plain WHERE SALARY > 4500 would do the same. The subquery form is useful when the list comes from another table.

ANY and ALL

  • > ANY (list) is true if the value is greater than at least one value in the list. That means greater than the smallest one.
  • > ALL (list) is true if the value is greater than every value in the list. That means greater than the largest one.
  • = ANY is the same as IN. <> ALL is the same as NOT IN.

The HR salaries are 8500 and 4500.

SQL 
SELECT NAME, DEPT, SALARY
FROM EMPLOYEE
WHERE SALARY > ANY
  (SELECT SALARY FROM EMPLOYEE
   WHERE DEPT = 'HR');
Output 
+---------+------+----------+
| NAME    | DEPT | SALARY   |
+---------+------+----------+
| Alina   | IT   |  6500.00 |
| Kathrin | HR   |  8500.00 |
| Jackson | IT   | 10000.00 |
+---------+------+----------+
SQL 
SELECT NAME, DEPT, SALARY
FROM EMPLOYEE
WHERE SALARY > ALL
  (SELECT SALARY FROM EMPLOYEE
   WHERE DEPT = 'HR');
Output 
+---------+------+----------+
| NAME    | DEPT | SALARY   |
+---------+------+----------+
| Jackson | IT   | 10000.00 |
+---------+------+----------+

ANY keeps everyone above 4500. ALL keeps only those above 8500.

Watch out for NOT IN and NULL

If the subquery list contains a NULL, NOT IN returns no rows at all. x NOT IN (1, NULL) means x <> 1 AND x <> NULL, and x <> NULL is never true. Add WHERE column IS NOT NULL to the subquery, or use NOT EXISTS.

Correlated subqueries

Definition

A correlated subquery uses a column of the outer query. So its result is different for each outer row, and it runs again for every outer row. A subquery that does not use the outer query is non-correlated: it runs once.

Who earns more than the average of their own department?

SQL 
SELECT NAME, DEPT, SALARY
FROM EMPLOYEE e
WHERE SALARY > (SELECT AVG(SALARY)
                FROM EMPLOYEE
                WHERE DEPT = e.DEPT);
Output 
+---------+-------+----------+
| NAME    | DEPT  | SALARY   |
+---------+-------+----------+
| John    | Sales |  2000.00 |
| Alina   | IT    |  6500.00 |
| Kathrin | HR    |  8500.00 |
| Jackson | IT    | 10000.00 |
+---------+-------+----------+

The alias e names the outer table. Inside the subquery, e.DEPT means “the department of the outer row we are checking now”.

  1. Outer row John (Sales). The subquery finds the Sales average, 1750. 2000 > 1750, so John is kept.
  2. Outer row Stephan (Sales). Average 1750 again. 1500 is not greater, so he is skipped.
  3. Outer row David (IT). The IT average is 6166.67. 2000 is not greater, so he is skipped.
  4. The same check runs for the other four rows. In total the subquery runs 7 times.

John is in the result even though he earns less than the company average. He is compared only with Sales.

The same pattern finds the top earner of each department:

SQL 
SELECT NAME, DEPT, SALARY
FROM EMPLOYEE e
WHERE SALARY = (SELECT MAX(SALARY)
                FROM EMPLOYEE
                WHERE DEPT = e.DEPT);
Output 
+---------+-------+----------+
| NAME    | DEPT  | SALARY   |
+---------+-------+----------+
| John    | Sales |  2000.00 |
| Kathrin | HR    |  8500.00 |
| Jackson | IT    | 10000.00 |
+---------+-------+----------+

If two people in a department share the top salary, both are returned.

EXISTS and NOT EXISTS

EXISTS (subquery) is true if the subquery returns at least one row. It does not care what the row contains, so we often write SELECT 1. EXISTS is almost always used with a correlated subquery.

Which employees work in a department where someone earns more than 8000?

SQL 
SELECT NAME
FROM EMPLOYEE e
WHERE EXISTS (SELECT 1
              FROM EMPLOYEE x
              WHERE x.DEPT = e.DEPT
                AND x.SALARY > 8000);
Output 
+---------+
| NAME    |
+---------+
| David   |
| Alina   |
| Kathrin |
| Harry   |
| Jackson |
+---------+

IT has Jackson (10000) and HR has Kathrin (8500), so everyone in IT and HR is listed. With NOT EXISTS, the result is the other department: John and Stephan.

NOT EXISTS is the safe way to ask “which rows have no match?”, because NULL values do not break it the way they break NOT IN.

Subqueries in FROM, SELECT and HAVING

In FROM: a derived table

A subquery in FROM returns a whole table, called a derived table. The outer query reads it like any other table. MySQL needs an alias for it.

SQL 
SELECT d.DEPT, d.avg_sal
FROM (SELECT DEPT, AVG(SALARY) AS avg_sal
      FROM EMPLOYEE
      GROUP BY DEPT) AS d
WHERE d.avg_sal > 5000;
Output 
+------+-------------+
| DEPT | avg_sal     |
+------+-------------+
| HR   | 6500.000000 |
| IT   | 6166.666667 |
+------+-------------+

The same result also comes from GROUP BY with HAVING (see GROUP BY and HAVING). The derived table is handy when you want to filter or join a summary table.

In SELECT: a scalar subquery

A single-row subquery can be a column of the result. Here it shows how far each salary is below the top salary:

SQL 
SELECT NAME, SALARY,
       (SELECT MAX(SALARY) FROM EMPLOYEE) - SALARY AS below_top
FROM EMPLOYEE
WHERE DEPT = 'Sales' OR ID = 3;
Output 
+---------+---------+-----------+
| NAME    | SALARY  | below_top |
+---------+---------+-----------+
| John    | 2000.00 |   8000.00 |
| Stephan | 1500.00 |   8500.00 |
| David   | 2000.00 |   8000.00 |
+---------+---------+-----------+

In HAVING

HAVING can compare a group's total with a subquery. Which departments pay more than twice the company average in total?

SQL 
SELECT DEPT, SUM(SALARY) AS total
FROM EMPLOYEE
GROUP BY DEPT
HAVING SUM(SALARY) > (SELECT AVG(SALARY) FROM EMPLOYEE) * 2;
Output 
+------+----------+
| DEPT | total    |
+------+----------+
| HR   | 13000.00 |
| IT   | 18500.00 |
+------+----------+

Twice the average is 10000. Sales has a total of 3500, so it is left out.

Subqueries in INSERT, UPDATE and DELETE

INSERT with a subquery

INSERT ... SELECT copies the rows that a query returns into another table. First we make an empty backup table with the same columns:

SQL 
CREATE TABLE EMPLOYEE_BKP LIKE EMPLOYEE;

INSERT INTO EMPLOYEE_BKP
SELECT * FROM EMPLOYEE
WHERE ID IN (SELECT ID FROM EMPLOYEE);

This copies all 7 rows. The WHERE clause here is only to show the syntax; INSERT INTO EMPLOYEE_BKP SELECT * FROM EMPLOYEE; does the same. Note that INSERT ... SELECT has no VALUES keyword.

UPDATE with a subquery

Set the salary to 0.25 times its value for every employee aged 29 or more. The subquery reads the backup table:

SQL 
UPDATE EMPLOYEE
SET SALARY = SALARY * 0.25
WHERE AGE IN (SELECT AGE FROM EMPLOYEE_BKP WHERE AGE >= 29);
Output 
+----+---------+------+----------+
| ID | NAME    | AGE  | SALARY   |
+----+---------+------+----------+
|  1 | John    |   20 |  2000.00 |
|  2 | Stephan |   26 |  1500.00 |
|  3 | David   |   27 |  2000.00 |
|  4 | Alina   |   29 |  1625.00 |
|  5 | Kathrin |   34 |  2125.00 |
|  6 | Harry   |   42 |  1125.00 |
|  7 | Jackson |   25 | 10000.00 |
+----+---------+------+----------+

Three rows change: Alina, Kathrin and Harry.

DELETE with a subquery

Delete every employee aged 29 or more:

SQL 
DELETE FROM EMPLOYEE
WHERE AGE IN (SELECT AGE FROM EMPLOYEE_BKP WHERE AGE >= 29);
Output 
+----+---------+------+----------+
| ID | NAME    | AGE  | SALARY   |
+----+---------+------+----------+
|  1 | John    |   20 |  2000.00 |
|  2 | Stephan |   26 |  1500.00 |
|  3 | David   |   27 |  2000.00 |
|  7 | Jackson |   25 | 10000.00 |
+----+---------+------+----------+
Why the backup table?

In MySQL, an UPDATE or DELETE cannot change a table and also read the same table in a subquery. For example, DELETE FROM EMPLOYEE WHERE AGE IN (SELECT AGE FROM EMPLOYEE WHERE AGE >= 29); is rejected with error 1093 (“You can't specify target table for update in FROM clause”). Reading a different table, like EMPLOYEE_BKP, avoids the problem.

Common mistake

Some notes write the UPDATE subquery as SELECT AGE FROM CUSTOMERS_BKP. There is no CUSTOMERS_BKP table in that example. The backup table is EMPLOYEE_BKP.

Subquery or join

Many subqueries can also be written as a join (see Joins). Both forms below find the top earner of each department:

SQL 
SELECT e.NAME, e.DEPT, e.SALARY
FROM EMPLOYEE e
JOIN (SELECT DEPT, MAX(SALARY) AS top
      FROM EMPLOYEE
      GROUP BY DEPT) AS m
  ON e.DEPT = m.DEPT AND e.SALARY = m.top;
When to use which
Use a subquery whenUse a join when
You compare with a single value, such as an averageYou need columns from both tables in the result
You test whether a match exists (EXISTS, NOT EXISTS)You combine many rows from both sides
The question reads naturally as “a question inside a question”A correlated subquery would run once per row on a big table

The MySQL optimizer rewrites many subqueries into joins on its own, so the speed is often the same. Write the clearest form first. Check the plan with EXPLAIN if the query is slow.

In real life

Above-average products

A shop's report lists products that sell better than the average of their own category: a correlated subquery on category.

Customers with no orders

A marketing team finds customers where NOT EXISTS an order in the last year, and sends them a reminder offer.

Archiving old data

A nightly job copies old rows into an archive table with INSERT ... SELECT, then deletes them from the main table.

Key points

  • A subquery is a SELECT in brackets inside another statement. It can be in WHERE, HAVING, FROM or SELECT.
  • A single-row subquery returns one value and works with =, <, > and the like. Using = with many rows gives error 1242.
  • A multiple-row subquery needs IN, ANY or ALL. > ANY means above the smallest; > ALL means above the largest.
  • A correlated subquery uses a column of the outer query and runs once per outer row.
  • EXISTS tests whether the subquery returns any row. NOT EXISTS is safer than NOT IN when NULL values are possible.
  • A subquery in FROM is a derived table and needs an alias.
  • ORDER BY is allowed in a subquery; it matters together with LIMIT. GROUP BY groups rows; it does not sort.
  • In MySQL, UPDATE and DELETE cannot read the table they change in a subquery (error 1093).
