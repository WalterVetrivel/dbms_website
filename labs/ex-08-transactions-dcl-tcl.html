Aim

Aim
  • To use database transactions along with TCL to handle the purchase of a game.
  • To use DCL commands to control access to the database.

Read these topics first

You need the sample data from Exercise 4 (it puts two games in user 1's cart) and the CurrentPrice column from Exercise 6. If you use the starter script, run the Exercise 6 set-up after it.

Two meanings of “transaction”

The Transactions table stores purchases in the store. A database transaction is a group of SQL statements that succeed or fail together. This exercise uses a database transaction to add a row to the Transactions table.

Steps

  1. Check the tables. Transactions (with TransactionID as AUTO_INCREMENT), PurchaseHistory and Cart must exist, and the cart must have rows.
  2. Write the checkout as one transaction for user 1:
    • start the transaction;
    • insert a row into Transactions with today's date and the user ID;
    • get the new TransactionID with LAST_INSERT_ID();
    • copy each game in the cart into PurchaseHistory, with the transaction ID and the game's current price;
    • delete those rows from Cart;
    • commit.
  3. Use DCL: create a user named customer with the password “password”, give it SELECT on Games, and make sure it cannot INSERT, UPDATE or DELETE.
Syntax 
START TRANSACTION;
  ...statements...
COMMIT;                       -- or ROLLBACK;

SET @Variable = value;
SELECT LAST_INSERT_ID() INTO @Variable;
INSERT INTO Table1 (Col1, Col2) SELECT @Variable, Col FROM Table2 WHERE Condition;

CREATE USER 'user'@'localhost' IDENTIFIED BY 'password';
GRANT SELECT ON database.TableName TO 'user'@'localhost';
REVOKE INSERT ON database.TableName FROM 'user'@'localhost';

The checkout transaction

MySQL 
START TRANSACTION;

SET @UserID = 1;
INSERT INTO Transactions (TransactionDate, UserID) VALUES (CURDATE(), @UserID);

SET @T_ID = 0;
SELECT LAST_INSERT_ID() INTO @T_ID;

INSERT INTO PurchaseHistory (TransactionID, GameID, SalePrice)
  SELECT @T_ID, Cart.GameID, Games.CurrentPrice
  FROM Cart INNER JOIN Games ON Cart.GameID = Games.GameID
  WHERE Cart.UserID = @UserID;

DELETE FROM Cart WHERE UserID = @UserID;

COMMIT;

Line by line

START TRANSACTION;
Begins a transaction. Until COMMIT, the changes are not permanent and other connections do not see them. MySQL normally commits every statement on its own (autocommit); START TRANSACTION turns that off until the next COMMIT or ROLLBACK.
SET @UserID = 1;
A user variable. Names start with @. It keeps its value until you disconnect, so later statements can use it instead of typing 1 again.
INSERT INTO Transactions (TransactionDate, UserID) VALUES (CURDATE(), @UserID);
Adds the purchase. TransactionID is left out, so AUTO_INCREMENT gives it the next number. CURDATE() is today's date.
SELECT LAST_INSERT_ID() INTO @T_ID;
LAST_INSERT_ID() returns the AUTO_INCREMENT value just made by this connection, so two customers checking out at the same moment each get their own number. INTO stores it in @T_ID. (The record first sets @T_ID to 0; that line is harmless but not needed.)
INSERT INTO PurchaseHistory (...) SELECT @T_ID, Cart.GameID, Games.CurrentPrice ...
INSERT ... SELECT: instead of VALUES, the rows come from a query. Each cart row becomes one PurchaseHistory row. @T_ID is the same in every row.
FROM Cart INNER JOIN Games ON Cart.GameID = Games.GameID
The cart has only IDs, so join Games to get each game's CurrentPrice, the price paid today.
WHERE Cart.UserID = @UserID
Only user 1's cart, not everyone's.
DELETE FROM Cart WHERE UserID = @UserID;
Empties the user's cart, because the games are bought.
COMMIT;
Makes all four changes permanent together. If anything failed before this point, run ROLLBACK and none of them happen.
Why one transaction?

Imagine the power fails after the INSERT into PurchaseHistory but before the cart is emptied. Without a transaction, the user has paid and still has the games in the cart. Inside a transaction, MySQL undoes the unfinished work when it restarts. This is atomicity, the A in ACID.

The record uses only COMMIT. The other TCL commands are ROLLBACK and SAVEPOINT. Try them on the cart.

SAVEPOINT undoes part of it

MySQL 
START TRANSACTION;
INSERT INTO Cart VALUES (3, 106);
SAVEPOINT AfterFirstGame;
INSERT INTO Cart VALUES (3, 112);
ROLLBACK TO SAVEPOINT AfterFirstGame;
COMMIT;
SELECT * FROM Cart WHERE UserID = 3
UserIDGameID
3106

MySQL manual: SAVEPOINT and ROLLBACK TO SAVEPOINT

SAVEPOINT AfterFirstGame
Marks a point inside the transaction.
ROLLBACK TO SAVEPOINT AfterFirstGame
Undoes only the work after the mark (the second game). The transaction stays open.
COMMIT
Saves what is left: the first game only.
DDL cannot be rolled back

CREATE, ALTER and DROP commit the open transaction at once in MySQL. A ROLLBACK after them has nothing left to undo.

DCL: users and privileges

Run these as the root user. A new user has no privileges at all, so we grant the four table privileges and then revoke the three that change data. That leaves only SELECT, as the record asks.

MySQL 
CREATE USER 'customer'@'localhost' IDENTIFIED BY 'password';
GRANT SELECT, INSERT, UPDATE, DELETE ON games_store.Games TO 'customer'@'localhost';
REVOKE INSERT, UPDATE, DELETE ON games_store.Games FROM 'customer'@'localhost';
SHOW GRANTS FOR 'customer'@'localhost';

MySQL manual: CREATE USER, GRANT, REVOKE, SHOW GRANTS

CREATE USER 'customer'@'localhost'
A MySQL account is a user name and a host. 'localhost' means this account can log in only from the same computer.
IDENTIFIED BY 'password'
Sets the password. Use a strong one outside the lab.
GRANT SELECT, INSERT, UPDATE, DELETE ON games_store.Games
Gives these four privileges on one table. Writing games_store.Games works even when no database is selected. games_store.* would mean every table in the database.
TO 'customer'@'localhost'
The account that receives them.
REVOKE INSERT, UPDATE, DELETE ... FROM 'customer'@'localhost'
Takes these three back. Note GRANT ... TO but REVOKE ... FROM.
Output of SHOW GRANTS 
+-----------------------------------------------------------------+
| Grants for customer@localhost                                   |
+-----------------------------------------------------------------+
| GRANT USAGE ON *.* TO `customer`@`localhost`                    |
| GRANT SELECT ON `games_store`.`games` TO `customer`@`localhost` |
+-----------------------------------------------------------------+

USAGE means “may log in, but nothing else”. The only real privilege left is SELECT on Games.

Test it as the new user

Open a new command prompt and log in as customer: mysql -u customer -p, then type password.

The customer can read games but cannot change prices or see other users' data. This is the principle of least privilege: give each account only what it needs.

To remove the account after the lab: DROP USER 'customer'@'localhost';.

Changes from the record

  • CURDATE() instead of NOW(). TransactionDate is a DATE column. NOW() also gives the time, which MySQL drops with a warning note. CURDATE() gives just the date. (To keep the time, make the column DATETIME, as the record's step 1 suggests with its DateAndTime name.)
  • The check query uses @T_ID. The record's WHERE TransactionID = (SELECT TransactionID FROM Transactions WHERE UserID = @UserID) fails with “Subquery returns more than 1 row” once the user has bought more than once.
  • The password is 'password'. The record's step asks for 'password' but its query uses an empty password.
  • GRANT before REVOKE. The record revokes INSERT, UPDATE and DELETE that were never granted. MySQL 8.4 refuses that with ERROR 1147 (42000): There is no such grant defined for user 'customer' on host 'localhost' on table 'Games'. Granting all four first and then revoking three shows both commands working. (REVOKE IF EXISTS ... is another way: it turns the error into a warning.)
  • games_store.Games instead of Games, so GRANT works even without USE.
  • ROLLBACK and SAVEPOINT are added so that all three TCL commands are practiced.

Viva questions

What is a transaction? State the ACID properties.

A transaction is a unit of work: a group of operations that must all succeed or all fail. ACID: Atomicity (all or nothing), Consistency (valid state to valid state), Isolation (transactions do not disturb each other) and Durability (committed changes survive failures). See ACID Properties.

Name the TCL and DCL commands.

TCL (Transaction Control Language): COMMIT, ROLLBACK and SAVEPOINT (with START TRANSACTION to begin). DCL (Data Control Language): GRANT and REVOKE. See SQL DCL and TCL Commands.

What is the difference between COMMIT and ROLLBACK?

COMMIT makes the transaction's changes permanent. ROLLBACK undoes every change since the transaction started.

What is a savepoint?

A named point inside a transaction. ROLLBACK TO SAVEPOINT undoes only the work after it, and the transaction continues. See Save Points.

What is autocommit?

MySQL's default mode, in which each statement is committed as soon as it finishes. START TRANSACTION suspends it until COMMIT or ROLLBACK. SET autocommit = 0; turns it off for the session.

Why use LAST_INSERT_ID() instead of SELECT MAX(TransactionID)?

LAST_INSERT_ID() is kept per connection, so it always returns your own new ID. MAX could return another customer's ID if they inserted at the same moment.

What is the principle of least privilege?

Give each user only the privileges needed for their job. The customer account can read games but cannot change them. See Access Control Based on Privileges.
